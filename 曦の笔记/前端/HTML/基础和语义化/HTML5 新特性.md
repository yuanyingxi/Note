# 1. 语义化标签
## 1.1 什么是语义化标签？

语义化标签是指 **标签本身就能表达内容的含义和作用**，而不是单纯用一个普通容器包裹内容。

例如：

- `<div>`：通用容器，本身没有明确的业务含义。
    
- `<header>`：表示页面或区域的头部。
    
- `<nav>`：表示导航区域。
    
- `<footer>`：表示页面或区域的底部。
    

语义化标签可以让 HTML 结构更清晰，方便开发者阅读和维护，也有利于搜索引擎理解页面结构和辅助技术识别内容。

## 1.2 常见语义化标签

|标签|作用|
|---|---|
|`<header>`|页面或区域的头部|
|`<nav>`|导航区域|
|`<main>`|页面主要内容，一个页面通常只有一个主要的 `<main>`|
|`<article>`|独立、完整的内容，如文章、帖子|
|`<section>`|对相关内容进行分组，通常具有独立主题|
|`<aside>`|侧边栏、补充信息|
|`<footer>`|页面或区域的底部|
|`<figure>`|图片、图表等相对独立的内容|
|`<figcaption>`|为 `<figure>` 中的内容提供说明|
|`<time>`|表示日期或时间|
|`<mark>`|标记需要突出显示的文本|
|`<details>`|可展开或收起的详情区域|
|`<summary>`|`<details>` 的标题，通常可以点击展开或收起|

## 1.3 示例

```html
<header>
  <h1>网站名称</h1>
</header>

<nav>
  <a href="/home">首页</a>
  <a href="/about">关于我们</a>
</nav>

<main>
  <article>
    <h2>文章标题</h2>
    <section>
      <p>文章正文内容</p>
    </section>
  </article>

  <aside>相关推荐</aside>
</main>

<footer>
  版权所有
</footer>
```

理解即可：页面的整体结构由不同的语义化标签组织起来，浏览器再结合 CSS 展示页面。

**面试重点：** 语义化标签与 `<div>` 的区别主要在于语义，而不是外观。大部分语义化标签也可以通过 CSS 修改样式。

# 2. Web Storage 本地存储
## 2.1 什么是 Web Storage？

Web Storage 是**浏览器提供的本地存储机制**，可以在**客户端保存数据**，不需要每次都向服务器请求这些数据。

常见用途：

- 保存用户的页面偏好设置。
    
- 记住搜索关键词、筛选条件。
    
- 临时保存页面状态。
    
- 在同源的多个标签页之间同步部分状态。
    

Web Storage 主要包括 `localStorage` 和 `sessionStorage`。

## 2.2 localStorage 与 sessionStorage 的区别

`localStorage` 和 `sessionStorage` 都是浏览器提供的本地存储机制，可以在浏览器中保存数据。主要区别在于**数据的保存时间和访问范围**。

|对比项|`localStorage`|`sessionStorage`|
|---|---|---|
|保存时间|长期保存，除非被删除或清除|当前标签页会话期间有效|
|关闭标签页后|数据通常仍然保留|数据通常会被清除|
|访问范围|同源的不同标签页可以共享数据|通常仅当前标签页可以访问|
|常见用途|保存用户偏好设置等长期数据|保存当前标签页临时使用的数据|

### 2.2.1 什么是标签页？

**标签页（Tab）就是浏览器顶部用于切换不同网页的页面区域。**

例如，在 Chrome 浏览器中打开两个网页：

```text
浏览器
┌────────────┬────────────┐
│ 标签页 A    │ 标签页 B    │
├────────────┴────────────┤
│                         │
│       网页内容           │
│                         │
└─────────────────────────┘
```

标签页 A 和标签页 B 是两个独立的标签页，即使它们打开的是同一个网站，也不代表它们的 `sessionStorage` 是共享的。

### 2.2.2 什么是当前标签页会话？

这里的会话可以简单理解为：**一个标签页从打开到关闭期间的浏览过程**。

例如，在标签页 A 中访问 `https://example.com/page1`，然后跳转到 `https://example.com/page2`：

- 如果使用 `sessionStorage` 保存数据，只要仍在同一个标签页会话中，并且页面同源，就可以继续读取这些数据。
    
- 如果关闭标签页 A，再重新打开网站，原来的 `sessionStorage` 数据通常就不存在了。
    
- 如果使用 `localStorage` 保存数据，关闭标签页甚至关闭浏览器后，数据通常仍然保留，下次访问同源网站时仍然可以读取。
    

### 2.2.3 什么是同源？

**同源要求协议、主机名和端口都相同。**

例如：

- `https://example.com/page1` 和 `https://example.com/page2`：同源。
    
- `http://example.com` 和 `https://example.com`：不同源，因为协议不同。
    
- `https://example.com` 和 `https://test.example.com`：不同源，因为主机名不同。
    

同源的页面可以共享 `localStorage` 中的数据，但不同源的页面不能直接访问彼此的本地存储。

### 2.2.4 常用 API

两者的 API 相同，常用方法如下：

|方法|作用|
|---|---|
|`setItem(key, value)`|保存数据|
|`getItem(key)`|获取数据|
|`removeItem(key)`|删除指定数据|
|`clear()`|清空当前存储区域的数据|

**记忆重点：** `localStorage` 适合长期保存的数据，`sessionStorage` 适合当前标签页临时使用的数据。两者都只能直接存储字符串，且读写操作是同步的。

## 2.3 常用 API

```js
// 保存数据
localStorage.setItem("name", "Alice");

// 获取数据
const name = localStorage.getItem("name");

// 删除指定数据
localStorage.removeItem("name");

// 清空当前源下的全部 localStorage 数据
localStorage.clear();
```

`sessionStorage` 的使用方式相同：

```js
sessionStorage.setItem("token", "abc123");

const token = sessionStorage.getItem("token");
```

常用方法：

|方法|作用|
|---|---|
|`setItem(key, value)`|保存数据|
|`getItem(key)`|获取数据，不存在时返回 `null`|
|`removeItem(key)`|删除指定数据|
|`clear()`|清空对应的存储区域|

## 2.4 为什么需要 JSON.stringify 和 JSON.parse？

**Web Storage 只能直接存储字符串。**

如果要保存对象或数组，需要先将其转换为 JSON 字符串，读取后再解析。

```js
const user = {
  name: "Alice",
  age: 20
};

// 对象转 JSON 字符串后保存
localStorage.setItem("user", JSON.stringify(user));

// 读取字符串并还原为对象
const data = JSON.parse(localStorage.getItem("user"));

console.log(data.name); // Alice
```

- `JSON.stringify()`：将 JavaScript 对象转换为 JSON 字符串。
    
- `JSON.parse()`：将 JSON 字符串解析为 JavaScript 数据。
    

## 2.5 本地存储与后端数据库的区别

|对比项|浏览器本地存储|后端数据库|
|---|---|---|
|存储位置|用户浏览器|服务器端|
|主要用途|页面状态、偏好设置等|用户、订单、业务数据等|
|多用户共享|不适合直接共享|可以通过后端业务实现共享|
|安全性|用户可以查看和修改，不可信|由后端控制访问权限|

注意：

1. 本地存储的数据不等于服务器数据库中的数据，清除浏览器数据可能导致本地数据丢失。
    
2. 不要把密码、敏感凭证等重要信息随意存入本地存储。
    
3. 不要信任前端传来的数据，后端仍然需要进行身份认证、权限校验和参数校验。
    
4. `localStorage` 和 `sessionStorage` 的读写是同步的，大量操作可能影响页面响应。
    

## 2.6 了解：storage 事件

当同源的另一个页面修改 `localStorage` 时，当前页面可以通过 `storage` 事件接收通知。

```js
window.addEventListener("storage", (event) => {
  console.log(event.key);      // 修改的键
  console.log(event.oldValue); // 修改前的值
  console.log(event.newValue); // 修改后的值
});
```

注意：事件通常在**其他符合条件的页面**触发，而不是在执行修改操作的当前页面触发。

# 3. WebSocket 全双工通信
## 3.1 WebSocket 是什么？

WebSocket 是一种支持客户端与服务器**全双工通信**的网络协议。

全双工指通信双方都可以主动发送数据，而不必每次都由客户端先发起 HTTP 请求。

传统 HTTP 请求通常采用：

```text
客户端 ── 请求 ──> 服务器
客户端 <── 响应 ── 服务器
```

WebSocket 建立连接后：

```text
客户端 <══════════> 服务器
       双向通信
```

连接建立后，双方可以通过同一个持久连接多次发送和接收数据，不需要每次发送消息都重新建立连接。

WebSocket 的常见特点：

- **全双工**：客户端和服务器都能主动发送消息。
    
- **持久连接**：连接建立后可以持续使用。
    
- **低额外开销**：后续消息不需要重复携带完整的 HTTP 请求头。
    
- **支持文本和二进制数据**：适合传输 JSON 消息、二进制内容等。
    

## 3.2 为什么需要 WebSocket？

假设开发一个聊天系统，用户 A 给用户 B 发送消息。

如果只使用普通 HTTP，用户 B 的页面如何及时知道自己收到了新消息？

一种简单方式是让客户端不断请求服务器，这就是轮询。

### 3.2.1 短轮询

客户端每隔一段时间发起一次 HTTP 请求，询问服务器有没有新消息。

```text
客户端 ── 查询 ──> 服务器
客户端 <── 无新消息 ── 服务器

等待一段时间后再次请求
```

缺点：

- 没有新消息时，也会不断发送请求。
    
- 请求过于频繁会增加网络和服务器开销。
    
- 消息通常需要等到下一次轮询才能被发现。
    

### 3.2.2 长轮询

客户端发起请求后，服务器暂时不返回响应，而是等待有新消息或达到超时时间后再响应。

客户端收到响应后，再发起下一次请求。

优点是可以减少没有数据时的频繁请求；缺点是仍然需要反复建立请求，并且服务器需要管理大量等待中的请求。

### 3.2.3 WebSocket

客户端与服务器先建立连接，连接保持可用。

当有新消息时，**服务器可以主动推送给客户端**，而**不必等待客户端再次查询**。

因此，WebSocket 特别适合需要**及时通信**的业务。

## 3.3 WebSocket 的连接建立流程

WebSocket 并不是一开始就直接使用 WebSocket 协议建立连接，而是先通过 HTTP 握手请求升级协议。

流程如下：

```text
客户端                         服务器
  |                             |
  |------ HTTP 握手请求 -------->|
  |      请求升级为 WebSocket    |
  |                             |
  |<----- HTTP 101 响应 ---------|
  |      Switching Protocols    |
  |                             |
  |<==== WebSocket 双向通信 ====>|
```

关键知识点：

1. 客户端发送带有**协议升级**信息的 HTTP 请求。
    
2. 服务器同意升级后，通常返回 `101 Switching Protocols`。
    
3. 握手成功后，双方开始通过 WebSocket 进行双向通信。
    

常见请求头：

- `Upgrade: websocket`：请求升级到 WebSocket 协议。
    
- `Connection: Upgrade`：表明请求涉及协议升级。
    

常见响应状态码：

- `101 Switching Protocols`：服务器同意切换协议。
    

连接地址通常使用：

- `ws://`：WebSocket 连接。
    
- `wss://`：通过 TLS 加密的 WebSocket 连接，类似 HTTPS 与 HTTP 的关系。
    

不需要记忆握手中的哈希计算过程，理解 HTTP 握手、协议升级和持久连接这三个步骤即可。

## 3.4 WebSocket 在业务开发中的应用

|场景|使用原因|
|---|---|
|即时聊天|服务器能够主动推送新消息|
|实时通知|新通知到达时可以及时推送|
|在线游戏|需要频繁交换游戏状态|
|实时协作|多个用户需要同步编辑结果|
|金融行情|需要持续更新价格等数据|
|直播弹幕|需要实时推送弹幕消息|

## 3.5 WebSocket、HTTP、SSE 与长轮询的区别

| 对比项     | HTTP 请求 / 短轮询 | 长轮询             | SSE            | WebSocket  |
| ------- | ------------- | --------------- | -------------- | ---------- |
| 通信方向    | 请求与响应         | 请求与响应           | 服务端到客户端        | 双向         |
| 连接特点    | 反复发起请求        | 请求暂时挂起，结束后再发起   | 基于 HTTP 的持续事件流 | 持久双向连接     |
| 服务端主动推送 | 需客户端再次请求      | 有新数据时通过等待中的请求响应 | 支持             | 支持         |
| 客户端主动发送 | 支持 HTTP 请求    | 支持 HTTP 请求      | 需通过其他请求实现      | 支持         |
| 断线处理    | 由应用决定何时再次请求   | 需要重新发起请求        | 浏览器原生支持自动重连    | 通常需要应用实现重连 |
| 典型场景    | 普通业务接口、低频查询   | 需要减少轮询频率的场景     | 通知、实时状态更新      | 聊天、实时协作、游戏 |

补充理解：

- **HTTP**：最常见的请求响应方式，适合查询数据、提交表单、创建订单等普通业务。
    
- **长轮询**：服务器暂时等待数据，适合不想频繁查询但又需要及时获得更新的场景。
    
- **SSE（Server-Sent Events）**：主要用于服务器向客户端持续推送文本事件，浏览器通过 `EventSource` 接收。
    
- **WebSocket**：双方都需要主动发送消息时更合适。
    

选择时记住：

- 普通业务接口：通常使用 HTTP。
    
- 只需要服务器推送通知：可以考虑 SSE。
    
- 需要客户端和服务器频繁双向通信：可以考虑 WebSocket。
    

## 4. 本章面试速记
## 4.1 什么是 HTML 语义化？

使用能表达内容含义的标签组织页面结构，例如使用 `<nav>` 表示导航、`<main>` 表示主要内容，而不是全部使用 `<div>`。这样可以提高结构可读性，并有利于辅助技术和搜索引擎理解页面。

## 4.2 localStorage 和 sessionStorage 有什么区别？

`localStorage` 默认持续保存，除非被清除；`sessionStorage` 通常在当前标签页会话结束后清除。两者都按同源规则隔离，且都只能直接存储字符串。

## 4.3 为什么对象存入 localStorage 前要使用 JSON.stringify？

因为 Web Storage 直接存储的是字符串。使用 `JSON.stringify()` 将对象转成 JSON 字符串，读取后使用 `JSON.parse()` 还原。

## 4.4 WebSocket 和 HTTP 有什么区别？

HTTP 通常采用客户端发起请求、服务器返回响应的模式；WebSocket 在握手升级成功后支持持久的双向通信，服务器可以主动推送消息。

## 4.5 WebSocket 为什么适合即时聊天？

聊天系统既需要客户端发送消息，也需要服务器主动向接收方推送消息。WebSocket 可以保持连接并支持双向通信，避免客户端不断轮询服务器。

## 4.6 WebSocket 是如何建立连接的？

客户端先发送 HTTP 协议升级请求，服务器通常通过 `101 Switching Protocols` 响应同意升级，之后双方通过 WebSocket 进行双向通信。

## 4.7 SSE 和 WebSocket 有什么区别？

SSE 主要用于服务端向客户端推送事件，浏览器原生支持自动重连；WebSocket 支持双向通信，更适合聊天、实时协作等场景。
