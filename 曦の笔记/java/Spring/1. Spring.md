# 1. Spring 基础与核心思想
## 1.1 什么是 Spring？

Spring 是一个轻量级的 Java 开发框架，主要用于简化企业级应用开发。

Spring 的核心功能：

|核心功能|作用|
|---|---|
|IoC（控制反转）|将对象的创建和依赖关系管理交给 Spring 容器|
|DI（依赖注入）|将对象需要的依赖注入到对象中|
|AOP（面向切面编程）|将日志、事务、权限校验等通用功能从业务代码中分离|
|事务管理|提供统一的事务管理机制|
|Spring MVC|提供 Web 请求处理框架|

Spring 最核心的思想是：通过 IoC 降低对象之间的耦合，通过 AOP 将通用功能从业务代码中分离。

## 1.2 IoC、DI、DIP 分别是什么？

这三个概念经常一起出现，但含义不同。

**（1）IoC：控制反转（Inversion of Control）**

**IoC 是一种设计思想，指将对象的创建和依赖管理交给外部容器负责。**

传统开发中，对象需要依赖其他对象时，通常由自己通过 `new` 创建：

```java
public class UserService {
    private UserDao userDao = new UserDao();
}
```

这种方式存在一个问题：`UserService` 直接依赖具体的 `UserDao` 实现。如果以后需要更换 DAO 实现，就需要修改原来的代码。

使用 Spring 后：

```java
@Service
public class UserService {

    private final UserDao userDao;

    public UserService(UserDao userDao) {
        this.userDao = userDao;
    }
}
```

**对象由 Spring 容器创建，依赖也由 Spring 容器负责组装。**

所谓控制反转，就是：

- 原来：业务代码主动创建对象、管理依赖。
    
- 现在：Spring 容器负责创建对象、管理依赖。
    

这里反转的是对象创建和依赖管理的控制权。

**（2）DI：依赖注入（Dependency Injection）**

DI 是实现 IoC 的一种方式。

简单来说，就是对象不再自己创建依赖，而是由外部将需要的对象传递进来。

常见方式：

- 构造器注入
    
- Setter 注入
    
- 字段注入
    

例如：

```java
@Service
public class UserService {

    private final UserDao userDao;

    public UserService(UserDao userDao) {
        this.userDao = userDao;
    }
}
```

这里 Spring 将 `UserDao` 对象传入 `UserService`，就是依赖注入。

注意：DI 不一定需要 Spring，自己通过构造器传递对象，也属于依赖注入。

**（3）DIP：依赖倒置原则（Dependency Inversion Principle）**

**DIP 是面向对象设计中的一条原则：**

- **高层模块不应该依赖低层模块，两者都应该依赖抽象。**
    
- **抽象不应该依赖具体实现，具体实现应该依赖抽象。**
    

例如：

```java
public interface MessageSender {
    void send();
}
```

```java
public class SmsSender implements MessageSender {
    public void send() {}
}
```

```java
public class UserService {

    private final MessageSender messageSender;

    public UserService(MessageSender messageSender) {
        this.messageSender = messageSender;
    }
}
```

`UserService` 依赖的是 `MessageSender` 接口，而不是具体的短信发送实现。

**三者的关系：**

|概念|本质|
|---|---|
|IoC|一种设计思想，将对象创建和依赖管理的控制权交给外部|
|DI|实现 IoC 的一种方式，将依赖对象传递给需要它的对象|
|DIP|一种设计原则，让高层模块和低层模块都依赖抽象|

## 1.3 Spring IoC 容器是什么？

IoC 容器是 Spring 实现控制反转的核心。

它主要负责：

1. 创建 Bean 对象。
    
2. 为 Bean 注入依赖。
    
3. 管理 Bean 的生命周期。
    
4. 管理 Bean 的作用域。
    
5. 在需要时提供 Bean 对象。
    

其中，**Bean 就是由 Spring IoC 容器管理的对象**。

例如：

```java
@Component
public class UserService {
}
```

Spring 扫描到 `@Component` 后，会将其注册为 Bean 定义，并根据配置创建和管理对应的对象。

Spring 中常见的 IoC 容器接口：

- `BeanFactory`：IoC 容器的基础接口。
    
- `ApplicationContext`：在 BeanFactory 基础上提供更多功能的应用上下文。
    

## 1.4 IoC 和 AOP 是通过什么机制实现的？
### 1.4.1 AOP（面向切面编程）是什么？

AOP（Aspect-Oriented Programming），即**面向切面编程**。

**它的核心思想是：将多个业务方法中重复出现的公共功能提取出来，统一处理，而不需要在每个业务方法中重复编写这些代码。**

**代理模式是实现 AOP 的一种常见方式，Spring AOP 主要就是通过动态代理实现的。**

例如，一个系统有用户登录、下单、支付等业务方法，它们都需要记录操作日志。

如果不使用 AOP：

```java
public void login() {
    // 记录日志
    // 登录业务逻辑
}

public void createOrder() {
    // 记录日志
    // 创建订单业务逻辑
}

public void pay() {
    // 记录日志
    // 支付业务逻辑
}
```

每个方法都需要编写日志代码，容易产生重复。

使用 AOP 后，可以将日志功能单独提取出来，由 Spring 在调用目标方法时统一处理：

```text
       用户调用业务方法
              |
              v
          AOP 代理
              |
              v
          记录日志
              |
              v
        执行原业务方法
              |
              v
          返回结果
```

这样，业务方法只需要关注自己的核心业务，不需要重复编写日志代码。

**AOP 常见的应用场景：**

- 日志记录：统一记录方法的调用信息。
    
- 权限校验：执行方法前检查用户是否具有相应权限。
    
- 事务管理：在方法执行前后统一处理事务。
    
- 性能统计：记录方法执行耗时。

### 1.4.2 AOP 的实现机制

Spring AOP 主要通过**动态代理（Dynamic Proxy）** 实现。

#### （1）先理解什么是代理对象

假设我们有一个用户服务 `UserService`，负责处理用户业务。

```java
public class UserService {
    public void login() {
        System.out.println("执行用户登录");
    }
}
```

如果我们希望在登录前后记录日志，可以在 `UserService` 外面增加一个代理对象。

```text
       调用者
          |
          v
       代理对象
          |
          +----> 记录调用日志
          |
          v
    真实对象 UserService
          |
          v
       执行登录业务
```

此时，调用者不再直接调用 `UserService`，而是先调用代理对象。

代理对象可以在调用真实对象的方法前后添加额外功能，例如记录日志、权限校验等。

#### （2）什么是动态代理？

理解了代理对象，再理解动态代理就简单了。

**动态代理就是在程序运行时，动态地创建代理对象，而不需要开发者提前手动编写一个代理类。**

例如，我们有很多业务类：

- `UserService`：用户业务。
    
- `OrderService`：订单业务。
    
- `PaymentService`：支付业务。
    

它们都需要记录日志。

如果使用普通的静态代理，就需要针对不同的业务类提前编写对应的代理类，容易产生重复代码。

而动态代理可以在程序运行时根据目标对象动态创建代理对象，从而减少手动编写代理类的工作。

#### （3）Spring AOP 如何使用动态代理？

Spring 容器管理的 Bean 如果需要应用 AOP 增强，Spring 就可以为它创建代理对象。

调用过程如下：

```text
       调用者调用业务方法
                |
                v
          Spring 代理对象
                |
                v
         执行额外功能
         （例如记录日志）
                |
                v
         调用真实对象方法
                |
                v
          执行业务逻辑
                |
                v
         执行后置额外功能
         （例如记录执行结果）
                |
                v
            返回结果
```

这样，业务类不需要自己编写日志、权限校验等公共功能，Spring 可以通过代理对象统一处理。

#### （4）Spring 动态代理的两种方式

Spring AOP 常见的动态代理方式有两种：

**① JDK 动态代理**

- 基于 Java 提供的动态代理机制。
    
- 通过实现目标对象的接口创建代理对象。
    
- 目标类需要实现接口。
    

**② CGLIB 动态代理**

- 通过继承目标类创建代理对象。
    
- 不要求目标类实现接口。
    
- 通过覆盖目标类的方法实现代理增强（`final` 方法等不能通过这种方式覆盖）。
    

#### （5）总结

- **代理对象**：位于调用者和真实对象之间，可以在方法调用前后添加额外功能。
    
- **动态代理**：在程序运行时动态创建代理对象，不需要手动编写对应的代理类。
    
- **JDK 动态代理**：通过实现接口创建代理对象。
    
- **CGLIB 动态代理**：通过继承目标类创建代理对象。
    

**核心理解：Spring AOP 利用动态代理创建代理对象，让调用者通过代理对象调用业务方法，从而在不直接修改原有业务代码的情况下，添加日志、权限校验、事务管理等额外功能。**

### 1.4.3 IoC 的实现机制

Spring IoC 容器主要通过 **BeanDefinition、工厂模式、反射和依赖注入** 等机制，实现对象的创建、管理和依赖关系的组装。

下面以 `UserService` 依赖 `UserRepository` 为例。

#### （1）BeanDefinition：保存 Bean 的定义信息

BeanDefinition 是 Spring 用来描述 Bean 的定义信息的对象。

它相当于一份对象创建说明书，记录 Spring 应该如何创建和管理某个 Bean。

常见信息包括：

- Bean 对应的 Java 类。
    
- Bean 的作用域，例如 singleton（单例）或 prototype（原型）。
    
- 创建 Bean 时需要的构造参数。
    
- 需要注入的属性或依赖关系。
    
- 初始化和销毁方法等。
    

例如：

```java
@Component
public class UserService {

    @Autowired
    private UserRepository userRepository;
}
```

Spring 扫描到 `@Component` 后，会解析相关配置，生成对应的 BeanDefinition。

**注意：BeanDefinition 保存的是 Bean 的定义信息，不是实际创建出来的 Bean 对象。**

#### （2）工厂模式：统一创建和管理对象

Spring IoC 容器可以理解为一个对象工厂。

传统方式下，我们需要自己创建对象：

```java
UserRepository userRepository = new UserRepository();

UserService userService = new UserService();
```

使用 Spring 后，对象交由 IoC 容器创建和管理：

```java
UserService userService =
        applicationContext.getBean(UserService.class);
```

我们不需要自己调用 `new` 创建和管理这些 Bean，而是从容器中获取对象。

Spring 容器会根据 BeanDefinition 中的信息，负责创建 Bean，并管理其生命周期。

**核心作用：将对象的创建和管理交给 IoC 容器，而不是由业务代码自己负责。**

#### （3）反射：在运行时创建对象和处理依赖

**反射是 Java 提供的一种机制，可以让程序在运行时获取类的信息，就是通过找到 JVM 内存里的 `Class` 对象，顺着这个对象去翻找类的信息（属性、方法），然后在内存里动态创建对象或调用方法的过程。**

Spring 可以利用反射等技术，根据 BeanDefinition 中的信息创建和处理对象。

例如：

```java
Class<?> clazz = UserService.class;

// 通过反射创建对象
Object userService = clazz.getDeclaredConstructor().newInstance();
```

除了创建对象，Spring 还可以利用反射访问对象的字段、调用方法等，从而完成属性注入等操作。

例如，通过反射将 `UserRepository` 对象设置到 `UserService` 的依赖字段中。

**核心作用：让 Spring 能够在运行时动态地创建和操作对象，而不需要业务代码手动完成这些操作。**

#### （4）依赖注入（DI）：自动组装对象之间的依赖关系

依赖注入是 IoC 的一种具体实现方式。

它的作用是：对象不再自己创建所依赖的对象，而是由 Spring 容器将需要的依赖传递给它。

例如：

```java
@Component
public class UserRepository {
}
```

```java
@Component
public class UserService {

    @Autowired
    private UserRepository userRepository;
}
```

`UserService` 需要使用 `UserRepository`，但它没有自己调用 `new UserRepository()` 创建对象。

Spring 容器会找到对应的 `UserRepository` Bean，并将其注入到 `UserService` 中。

常见的依赖注入方式有：

- **构造器注入**：通过构造方法传入依赖对象。
    
- **Setter 注入**：通过 Setter 方法设置依赖对象。
    
- **字段注入**：直接将依赖对象注入成员变量，例如使用 `@Autowired`。
    

#### （5）整体执行过程

将上面的机制联系起来：

```text
              Spring 启动
                  |
                  v
          扫描配置、识别 Bean
                  |
                  v
          生成 BeanDefinition
                  |
                  v
          IoC 容器读取定义信息
                  |
                  v
            创建 Bean 对象
                  |
                  v
          处理 Bean 之间的依赖
                  |
                  v
              依赖注入
                  |
                  v
          完成 Bean 的初始化
                  |
                  v
          Bean 交由容器管理
```

其中：

- **BeanDefinition**：提供创建 Bean 所需的定义信息。
    
- **工厂模式**：由 IoC 容器统一创建和管理对象。
    
- **反射**：辅助 Spring 在运行时创建和操作对象。
    
- **依赖注入**：将 Bean 之间需要的依赖关系组装起来。
    

**总结：** Spring IoC 容器根据 BeanDefinition 中的定义信息，利用工厂机制创建和管理 Bean，并通过依赖注入自动组装对象之间的依赖关系，反射等技术则为运行时创建和操作对象提供支持。

## 1.5 依赖注入有哪些方式？

Spring 常见的依赖注入方式有三种。

**（1）构造器注入**

通过构造方法传入依赖对象。

```java
@Service
public class UserService {

    private final UserDao userDao;

    public UserService(UserDao userDao) {
        this.userDao = userDao;
    }
}
```

特点：

- 创建对象时就必须提供依赖。
    
- 依赖关系明确。
    
- 可以使用 `final` 修饰依赖字段。
    
- 方便单元测试。
    

**（2）Setter 注入**

通过 Setter 方法设置依赖。

```java
@Service
public class UserService {

    private UserDao userDao;

    @Autowired
    public void setUserDao(UserDao userDao) {
        this.userDao = userDao;
    }
}
```

特点：

- 依赖可以在对象创建后设置。
    
- 适合可选依赖。
    
- 对象创建后，依赖可能还没有完成注入。
    

**（3）字段注入**

直接在属性上使用 `@Autowired`。

```java
@Service
public class UserService {

    @Autowired
    private UserDao userDao;
}
```

特点：

- 写法简单。
    
- 不需要编写构造方法或 Setter。
    
- 依赖关系不够明显。
    
- 不方便脱离 Spring 容器进行单元测试。
    

### 1.6 为什么更推荐构造器注入？

Spring 通常更推荐构造器注入。

主要原因：

1. **依赖明确**：通过构造方法就能知道当前类需要哪些依赖。
    
2. **保证必要依赖存在**：创建对象时必须提供依赖，避免依赖为 `null`。
    
3. **方便测试**：可以直接通过 `new` 创建对象并传入 Mock 对象。
    
4. **支持 final**：依赖字段可以声明为 `final`，避免引用被重新赋值。
    
5. **更容易发现循环依赖**：构造器循环依赖无法通过三级缓存解决，通常会在容器启动时暴露问题。
    

实际开发中：

- 必须依赖：优先构造器注入。
    
- 可选依赖：可以考虑 Setter 注入。
    

## 1.7 @Autowired 和 @Resource 有什么区别？

两者都可以用于依赖注入，主要区别在于依赖查找方式。

|对比|@Autowired|@Resource|
|---|---|---|
|来源|Spring|Java 标准注解|
|默认匹配方式|按类型|优先按名称|
|指定名称|配合 @Qualifier|使用 name 属性|
|常见使用位置|构造器、字段、Setter 等|字段、Setter 方法|

**@Autowired：**

默认按类型查找 Bean。

如果存在多个相同类型的 Bean，可以通过 `@Qualifier` 指定具体名称。

```java
@Autowired
@Qualifier("wechatPaymentService")
private PaymentService paymentService;
```

也可以使用 `@Primary` 指定默认优先注入的 Bean。

**@Resource：**

可以通过 `name` 指定 Bean 名称：

```java
@Resource(name = "wechatPaymentService")
private PaymentService paymentService;
```

如果没有指定 `name`，通常先根据字段名或属性名查找，再根据类型进行匹配。

注意：Spring Boot 3.x 使用 `jakarta.annotation.Resource`，Spring Boot 2.x 常见的是 `javax.annotation.Resource`。

## 1.8 如果让你设计一个 Spring IoC，会考虑哪些方面？

如果让我设计一个简单的 IoC 容器，我会从以下几个方面考虑：

### 1.8.1 Bean 定义管理

首先需要有一个地方保存 Bean 的定义信息，例如使用 `BeanDefinition`。

**BeanDefinition 是 Spring 用来描述 Bean 定义信息的对象，可以理解为创建 Bean 的说明书。**

它记录的信息包括：

- Bean 对应的 Java 类。
    
- Bean 的作用域，例如 Singleton、Prototype。
    
- 创建对象需要的构造参数。
    
- 初始化和销毁方法等。
    

例如，Spring 扫描到 `UserService` 类上的 `@Component` 后，会生成对应的 BeanDefinition，后续根据这些信息创建和管理 Bean。

注意：**BeanDefinition 是定义信息，不是实际创建出来的 Bean 对象。**

#### 1.8.2 Bean 的创建与依赖注入

IoC 容器需要根据 BeanDefinition 创建对象，并处理对象之间的依赖关系。

例如：

```text
OrderService 依赖 UserRepository
          |
          v
   IoC 容器创建对象
          |
          v
   查找 UserRepository
          |
          v
   将其注入 OrderService
```

常见的依赖注入方式包括：

- 构造器注入。
    
- Setter 注入。
    
- 字段注入。
    

如果同一个类型存在多个 Bean，还需要支持通过名称、`@Qualifier` 等方式指定具体注入哪个 Bean。

### 1.8.3 Bean 的作用域与缓存

**容器需要支持不同的 Bean 作用域，控制对象的创建和复用。**

常见的作用域：

- **Singleton（单例）**：同一个容器中，同一个 Bean 通常只创建一个实例，后续获取时复用该对象。
    
- **Prototype（原型）**：每次向容器获取该 Bean 时，都会创建一个新的实例。
    

例如，可以使用 Map 保存单例 Bean，避免重复创建。

另外，还需要考虑多线程同时获取 Bean 时的并发安全问题。

### 1.8.4 Bean 的生命周期管理

容器需要管理 Bean 从创建到销毁的过程。

主要包括：

1. 创建 Bean 实例。
    
2. 注入依赖。
    
3. 执行初始化操作。
    
4. Bean 正常使用。
    
5. 容器关闭时执行销毁操作。
    

例如，可以提供初始化方法和销毁方法，让 Bean 在初始化时加载资源，在销毁时释放资源。

### 1.8.5 扩展能力与异常处理

还需要考虑容器的扩展能力和错误处理。

- **AOP 支持**：允许通过动态代理为 Bean 添加日志、事务管理等额外功能。
    
- **扩展接口**：允许开发者在 Bean 创建和初始化等阶段执行自定义逻辑。
    
- **异常处理**：当 Bean 创建失败、依赖无法找到或存在多个无法区分的候选 Bean 时，提供清晰的异常信息。
    

### 1.8.6 总结

设计一个简单的 Spring IoC 容器，主要需要考虑：

1. **Bean 定义管理**：记录 Bean 的创建和管理信息。
    
2. **对象创建与依赖注入**：负责创建 Bean，并组装依赖关系。
    
3. **作用域与缓存**：控制 Bean 的创建方式和对象复用。
    
4. **生命周期管理**：管理 Bean 的初始化和销毁。
    
5. **扩展与异常处理**：支持 AOP、扩展接口，并处理创建过程中的异常。
    

核心就是：**让 IoC 容器负责对象的创建、依赖组装和生命周期管理，而不是让业务代码自己管理这些工作。**

# 2. Spring AOP
## 2.1 什么是 AOP？

AOP（Aspect-Oriented Programming），即**面向切面编程**。

**它主要解决的问题是：将多个业务模块中重复出现的通用功能抽取出来，避免这些功能分散在业务代码中。**

例如，一个项目中有：

- 用户模块
    
- 订单模块
    
- 支付模块
    

这些模块都需要记录日志、进行权限校验、管理事务。

如果每个业务方法都手动编写这些代码，就会产生大量**重复代码**。

**AOP 可以将这些通用功能单独抽取出来，通过代理机制在指定方法执行前后自动执行。**

```text
          业务方法调用
                |
                v
             代理对象
                |
                v
         执行 AOP 增强逻辑
         （日志、权限、事务）
                |
                v
             目标方法
                |
                v
             返回结果
```

AOP 中：

- 核心业务：真正需要完成的业务功能，例如下单、支付。
    
- 横切关注点：多个业务模块共同需要的功能，例如日志、事务、权限校验。
    

## 2.2 AOP 中的常见术语

|名称|含义|
|---|---|
|Aspect（切面）|将切点和通知组织在一起，定义需要增强的功能|
|Join Point（连接点）|程序执行过程中可以被增强的位置，Spring AOP 主要是方法执行|
|Pointcut（切点）|用于匹配哪些方法需要执行增强逻辑|
|Advice（通知）|实际执行的增强逻辑|
|Target Object（目标对象）|被代理的原始对象|
|AOP Proxy（代理对象）|Spring 创建的代理对象|
|Weaving（织入）|将增强逻辑应用到目标方法的过程|

**其中最重要的是：**

- **切面（Aspect）：将切点和通知组合在一起，定义一组增强规则。**
    
- **切点（Pointcut）：指定哪些方法需要被增强，也就是确定增强的目标。**
    
- **通知（Advice）：定义增强的具体代码，以及这些代码在目标方法执行前、执行后还是发生异常时运行。**

## 2.3 Spring AOP 有哪些应用场景？

常见应用：

1. **事务管理**：通过 `@Transactional` 自动管理事务。Spring 可以通过 AOP，在业务方法执行前开启事务，在方法执行后提交事务，如果发生异常则回滚事务。
    
2. **日志记录**：统一记录方法调用参数、返回值、执行时间。
    
3. **权限校验**：在方法执行前检查用户权限。
    
4. **异常处理与监控**：统一收集异常、统计方法执行情况。
    

这些功能都具有一个共同特点：**它们不是业务方法的核心逻辑，但又需要在多个业务模块中重复使用。**

## 2.4 Spring AOP 的实现原理

Spring AOP 主要通过**动态代理**实现。其核心思路是：为需要增强的 Bean 创建代理对象，在调用业务方法时，通过代理对象执行公共增强逻辑，再调用原始业务方法。

可以分成三个步骤：

### 2.4.1 第一步：解析切面

**Spring 解析 `@Aspect` 标注的切面类，识别其中的切点和通知**，确定：

- **切面（Aspect）**：将切点和通知组织在一起，定义一套增强规则。
    
- **切点（Pointcut）**：指定哪些业务方法需要增强。
    
- **通知（Advice）**：编写具体的增强代码，以及这些代码在目标方法执行前、执行后还是发生异常时运行。
    

例如，我们可以创建一个切面类，统一记录业务方法的执行日志：

```java
@Aspect
@Component
public class LogAspect {

    // 指定需要增强的方法
    @Pointcut("execution(* com.example.service..*(..))")
    public void serviceMethods() {}

    // 编写具体的日志增强逻辑
    @Before("serviceMethods()")
    public void before() {
        System.out.println("记录操作日志");
    }
}
```

其中：

- `@Pointcut` 用来指定哪些方法需要增强。
    
- `@Before` 表示在目标方法执行之前运行通知方法。
    
- `before()` 就是具体的公共增强方法。

**这段代码表达：只要你的类在 `com.example.service` 包下，不管你是谁，不管你带什么参数，只要这个方法被调用了，我就要在它执行前（@Before）插一脚，强行打印一句 `记录操作日志`。**

### 2.4.2 第二步：创建代理对象

**Spring 在 Bean 创建过程中检查该 Bean 是否需要进行 AOP 增强（就是在看这个类里的方法有没有匹配上 `@Pointcut` 的表达式）。**

如果需要，就为目标对象创建代理对象，并由 Spring IoC 容器管理。

例如，A、B、C 三个业务类都需要增强，那么 Spring 会分别为它们创建代理对象：

```text
Spring IoC 容器
    |
    |-- AService 代理对象 ---> AService 真实对象
    |
    |-- BService 代理对象 ---> BService 真实对象
    |
    |-- CService 代理对象 ---> CService 真实对象
```

注意：

- 每个需要增强的 Bean 都有对应的代理对象。
    
- 代理对象是在**运行时创建**的，不需要开发者手动编写。
    
- 代理对象由 **Spring 容器管理**，不需要专门放在 `common` 包中。
    

**公共增强逻辑只需要编写一次，不需要在每个代理对象中重复编写。**

例如，上面的 `LogAspect.before()` 就是公共增强方法。A、B、C 对应的代理对象在执行匹配的业务方法时，都可以通过相应的通知调用这段日志代码。

### 2.4.3 第三步：执行代理方法

其他 Bean 通过 Spring 注入业务对象时，通常拿到的是代理对象。

因此，业务代码仍然可以正常调用方法，不需要手动调用代理对象：

```java
@Service
public class OrderService {

    private final AService aService;

    public OrderService(AService aService) {
        this.aService = aService;
    }

    public void createOrder() {
        aService.doA();
    }
}
```

实际调用过程：

```text
OrderService 调用 aService.doA()
              |
              v
        AService 代理对象
              |
              v
        执行公共增强逻辑
        （例如记录日志）
              |
              v
        AService 真实对象
              |
              v
        执行 doA() 业务方法
              |
              v
             返回
```

**代理对象负责拦截方法调用，并按照配置执行通知和目标方法；切面中的通知方法则提供具体的公共增强代码。**

### 2.4.4 实际开发中的例子：事务管理

Spring 的声明式事务管理也是 AOP 的典型应用。

可以将 AOP 理解为一种**拦截方法调用，并在原有业务方法执行过程中插入额外处理逻辑的机制**。

例如，日志记录和事务管理都可以通过这种方式实现：

- **日志记录**：在业务方法执行之前添加日志记录，或者在执行之后记录结果。
    
- **事务管理**：在业务方法执行之前开启事务，在执行结束后根据执行结果提交或回滚事务。
    

例如：

```java
@Service
public class AccountService {

    @Transactional
    public void transfer() {
        // 从 A 账户扣款
        // 给 B 账户加款
    }
}
```

这里的 `@Transactional` 用来声明 `transfer()` 方法需要事务管理。

- **`@Transactional`：Spring 提供的声明式事务功能，底层利用 AOP 的代理和拦截机制实现事务管理。你直接使用注解即可，不需要自己编写事务切面。**
    
- **`@Aspect`：用于自定义切面，可以自己定义切点和通知，为业务方法添加公共功能，例如日志记录、操作审计等。**

**`@Transactional` 本身并不是一个特殊的 `@Aspect`，而是告诉 Spring：这个方法需要应用事务管理功能。**

Spring 内部通过事务拦截器和 AOP 代理机制，在调用该方法时执行事务管理逻辑。

**实际调用过程：**

```text
调用方调用 transfer()
          |
          v
      代理对象
          |
          v
      事务拦截器
          |
          v
       开启事务
          |
          v
   执行 transfer() 业务方法
          |
          v
       判断执行结果
          |
     ┌────┴────┐
     v         v
  正常返回    符合回滚规则的异常
     |         |
     v         v
  提交事务   回滚事务
```

这样，`transfer()` 中参与当前事务的数据库操作就可以作为一个整体处理：

- **提交事务**：扣款和收款操作一起提交。
    
- **回滚事务**：发生符合回滚规则的异常时，撤销当前事务中尚未提交的数据库修改。
    

从而保证这组数据库操作满足事务的原子性：要么一起提交，要么一起回滚。

开发者不需要自己编写开启事务、提交事务和回滚事务的代码，只需要使用 `@Transactional` 声明事务边界，由 Spring 提供的事务机制完成这些工作。

**总结：AOP 通过拦截方法调用，在原有业务逻辑的基础上添加公共功能。日志记录是在业务执行前后添加日志，事务管理则是在业务执行前后添加事务处理逻辑。**

## 2.5 JDK 动态代理和 CGLIB 动态代理有什么区别？

**Spring AOP 常见的两种动态代理方式：JDK 动态代理通过实现接口创建代理对象，CGLIB 动态代理通过继承业务实现类创建代理对象。**

**（1）JDK 动态代理**

- 基于**接口实现**，要求目标类实现接口。
    
- Spring 在运行时创建一个**实现相同接口的代理对象**。
    
- 通过代理对象调用方法时，可以加入增强逻辑。
    

**（2）CGLIB 动态代理**

- 基于**继承实现**，不要求目标类实现接口。
    
- Spring 在运行时创建**目标类的子类作为代理对象**。
    
- `final` 类不能被继承，`final` 方法不能被重写，因此无法通过这种方式增强。
    

**简单对比：**

| 对比     | JDK 动态代理    | CGLIB 动态代理                |
| ------ | ----------- | ------------------------- |
| 实现方式   | 实现接口        | 继承目标类                     |
| 是否要求接口 | 是           | 否                         |
| 主要限制   | 只能代理接口定义的方法 | `final` 类和 `final` 方法无法增强 |

**补充：** Spring Boot 2.x、3.x 中，Spring AOP 默认通常使用 CGLIB 创建代理对象，即使目标类实现了接口，也可能使用 CGLIB。

可以通过以下配置切换：

```yaml
spring:
  aop:
    proxy-target-class: false
```

## 2.6 动态代理和静态代理有什么区别？

**代理模式是为其他对象提供一个代理对象，通过代理对象控制对目标对象的访问。**

### 2.6.1 静态代理

**由程序员提前编写代理类，编译时就已经确定代理类。**

特点：

- 需要手动编写代理类。
    
- 每个目标类通常需要对应的代理实现。
    
- 代码重复较多，维护成本较高。
    

### 2.6.2 动态代理

**在程序运行期间动态生成代理对象。**

特点：

- 不需要手动为每个目标类编写代理类。
    
- 可以统一处理方法调用。
    
- 更适合框架层面的通用增强。
    

**Spring AOP 使用动态代理，主要是为了自动完成代理对象创建、方法匹配和增强逻辑执行。**

## 2.7 AOP 有哪些常用注解？

| 注解                | 作用                                           |
| ----------------- | -------------------------------------------- |
| `@Aspect`         | 声明一个切面类                                      |
| `@Pointcut`       | 定义切点，指定匹配的方法（可以匹配单个方法，也可以通过表达式匹配整个包下的多个类和方法） |
| `@Before`         | 目标方法执行前执行                                    |
| `@After`          | 目标方法执行后执行，无论是否发生异常                           |
| `@AfterReturning` | 目标方法正常返回后执行                                  |
| `@AfterThrowing`  | 目标方法抛出异常后执行                                  |
| `@Around`         | 环绕通知，可以控制目标方法是否执行                            |

其中 `@Around` 功能最强，可以通过 `proceed()` 控制是否继续执行目标方法。

## 2.8 Spring AOP 有哪些限制？

Spring AOP 主要通过代理对象拦截方法调用，因此使用时需要注意以下几点：

**（1）自己通过 `new` 创建的对象不会自动获得 AOP 增强**

Spring AOP 主要针对 Spring IoC 容器管理的 Bean 创建代理对象。

**如果自己通过 `new` 创建对象，这个对象不会经过 Spring 的代理创建过程，因此调用它的方法时不会自动触发 Spring AOP 增强。**

**（2）同一个类内部通过 `this.xxx()` 调用方法，通常不会触发 AOP 增强**

例如：

```java
@Service
public class UserService {

    public void methodA() {
        this.methodB();
    }

    public void methodB() {
        System.out.println("执行业务方法");
    }
}
```

如果 `methodB()` 配置了 AOP 增强，那么通过 `this.methodB()` 调用时，通常不会触发增强。

**原因是：**

1. **外部调用（生效）**：  
    Controller 中注入和调用的，实际上是 Spring 生成的**代理对象（Proxy）**。代理对象拦截了请求，在执行真实方法前后，插入了开启事务、提交/回滚事务的代码。
    
2. **内部调用（失效）**：  
    在真实对象的代码内部，通过 `this.methodB()` 调用时，`this` 永远指向当前的**真实对象（Target）** 本身，而不是代理对象。这个调用是在**对象内部**直接发生的，**没有触发代理对象的拦截逻辑**。既然没有经过代理，Spring 自然无法在执行 `methodB` 前后植入事务代码。

**（3）Spring AOP 主要针对方法执行进行增强**

Spring AOP 主要拦截方法调用，不能像某些其他 AOP 实现方式一样，直接对任意字段访问、对象构造等操作进行增强。

**（4）CGLIB 动态代理存在继承限制**

CGLIB 通过继承目标类并重写方法实现增强，因此：

- `final` 类不能被继承代理。
    
- `final` 方法不能被重写增强。
    
- `private` 方法不能通过这种方式增强。
    

**注意：** JDK 动态代理和 CGLIB 的实现方式不同，具体限制也不同。

其中第（2）点非常重要，后面学习 Spring 事务失效时还会涉及这个问题。

## 2.9 什么是反射？Spring 为什么需要反射？

**反射是 Java 提供的一种机制，允许程序在运行时获取类的信息，并动态操作对象。**

例如：

```java
Class<?> clazz = User.class;

// 获取对象
Object object = clazz.getDeclaredConstructor().newInstance();

// 获取方法
Method method = clazz.getDeclaredMethod("getName");

// 调用方法
method.invoke(object);
```

反射常见用途：

1. 获取类、方法、字段、构造器等信息。
    
2. 在运行时创建对象。
    
3. 在运行时调用方法。
    
4. 在运行时访问和修改字段。
    

**Spring 使用反射的典型场景：**

- **IoC：根据 BeanDefinition 创建对象、注入依赖。**
    
- **AOP：结合动态代理，在运行时处理方法调用。**
    

# 3. Spring 循环依赖与三级缓存
## 3.1 什么是循环依赖？

循环依赖指的是多个 Bean 之间相互依赖，形成一个依赖闭环。

例如：

```java
@Service
public class A {
    @Autowired
    private B b;
}
```

```java
@Service
public class B {
    @Autowired
    private A a;
}
```

依赖关系：

```text
       A
       |
       v
       B
       |
       v
       A
```

A 需要 B，B 又需要 A。

如果 Spring 按照普通方式创建对象：

1. 创建 A 时发现需要 B。
    
2. 创建 B 时发现需要 A。
    
3. 创建 A 时又发现需要 B。
    
4. 不断重复，无法完成创建。
    

Spring 通过三级缓存解决了部分单例 Bean 的循环依赖问题。

## 3.2 Spring 哪些循环依赖可以解决？

循环依赖主要分为三种情况：

|注入方式|Bean 作用域|是否能通过三级缓存解决|
|---|---|---|
|构造器注入|Singleton|不能|
|Setter / 字段注入|Prototype|不能|
|Setter / 字段注入|Singleton|可以，满足相关条件时|

原因：

**（1）构造器注入无法解决**

因为构造器注入必须先获得依赖对象，才能创建当前对象。

A 创建时需要 B，B 创建时又需要 A。

此时 A 和 B 都还没有完成实例化，Spring 无法提前暴露对象引用。

**（2）Prototype 无法解决**

Prototype（原型）Bean 每次获取时都会创建新对象，不会像 Singleton 一样长期保存在单例缓存中。

Spring 的三级缓存机制主要用于处理单例 Bean 的循环依赖，因此无法通过它解决 Prototype Bean 的循环依赖。

**（3）Singleton 的 Setter / 字段注入可以解决**

因为这两种方式可以先创建对象，再注入依赖。

Spring 可以在对象实例化后、属性注入之前，提前暴露对象引用。

这样就能解决部分循环依赖。

注意：Spring Boot 2.6 起默认禁止循环依赖。需要允许时，可以配置：

```yaml
spring:
  main:
    allow-circular-references: true
```

但这不代表所有循环依赖都能解决。

## 3.3 Spring 三级缓存分别是什么？

Spring 在 `DefaultSingletonBeanRegistry` 中维护了三个重要缓存。

| 缓存   | 名称                      | 存储内容                          |
| ---- | ----------------------- | ----------------------------- |
| 一级缓存 | `singletonObjects`      | 完全初始化完成的 Bean                 |
| 二级缓存 | `earlySingletonObjects` | 提前暴露的 Bean 引用                 |
| 三级缓存 | `singletonFactories`    | 用于生成早期 Bean 引用的 ObjectFactory |

### 3.3.1 一级缓存：singletonObjects

**存放完全初始化完成的 Bean。**

Bean 已经完成：

- 实例化。
    
- 属性注入。
    
- 初始化方法执行。
    
- 必要的 AOP 代理创建。
    

可以直接提供给其他对象使用。

### 3.3.2 二级缓存：earlySingletonObjects

**存放提前暴露的 Bean 引用。**

此时 Bean 已经实例化，但是可能还没有完成属性注入和初始化。

其中存放的可能是：

- 原始对象。
    
- 提前创建的 AOP 代理对象。
    

### 3.3.3 三级缓存：singletonFactories

存放的是 `ObjectFactory` 工厂对象，而不是 Bean 本身。

**它的作用是：在需要解决循环依赖时，动态获取 Bean 的早期引用（空壳对象）。**

如果 Bean 需要 AOP 代理，工厂可以通过相关机制提前生成代理对象；如果不需要，则返回原始对象。

#### 早期引用

**定义：一个已经通过反射执行了构造方法分配了内存，但尚未执行属性填充（Populate）和初始化方法（Initialize）的 Java 对象实例。**

## 3.4 Spring 如何通过三级缓存解决循环依赖？

假设：

- A 依赖 B。
    
- B 依赖 A。
    
- 两个 Bean 都是 Singleton。
    
- 使用字段注入。
    

整个过程如下：

**第一步：创建 A 对象**

Spring 首先调用 A 的构造方法，创建 A 的原始对象。

此时 A 已经实例化，但还没有注入 B。

随后，Spring 将 A 对应的 `ObjectFactory` 放入三级缓存。

```text
一级缓存：空

二级缓存：空

三级缓存：
A -> ObjectFactory
```

**第二步：注入 A 的依赖，创建 B**

Spring 发现 A 依赖 B，于是开始创建 B。

同样先调用 B 的构造方法，然后将 B 对应的 `ObjectFactory` 放入三级缓存。

```
一级缓存：空

二级缓存：空

三级缓存：
A -> ObjectFactory
B -> ObjectFactory
```

**第三步：B 需要注入 A**

Spring 发现 B 依赖 A，于是尝试获取 A。

按照以下顺序查找：

```
一级缓存 singletonObjects
          |
          | 没找到
          v
二级缓存 earlySingletonObjects
          |
          | 没找到
          v
三级缓存 singletonFactories
          |
          | 找到 A 的 ObjectFactory
          v
调用 getObject()
          |
          v
获取 A 的早期引用
```

获取到 A 的**早期引用**后：

- 将 A 的早期引用放入二级缓存。
    
- 从三级缓存中移除 A 对应的工厂。
    
- 将 A 注入 B。
    

此时 B 已经获得了 A 的引用。

**第四步：完成 B 的初始化**

B 已经获得全部依赖，执行初始化方法。

完成后将 B 放入一级缓存。

**第五步：完成 A 的初始化**

由于 B 已经创建完成，可以将 B 注入 A。

随后完成 A 的初始化，将 A 放入一级缓存。

最终：

```text
一级缓存 singletonObjects：
A -> 完整的 A 对象
B -> 完整的 B 对象

二级缓存 earlySingletonObjects：空

三级缓存 singletonFactories：空
```

这样 A 和 B 就都创建完成了。

## 3.5 为什么 Spring 需要三级缓存？二级缓存不行吗？

如果只考虑普通对象的循环依赖，二级缓存就可以解决。

但 Spring 还需要考虑 AOP 代理，因此使用三级缓存来处理提前暴露的对象引用。

假设：

- A 依赖 B。
    
- B 依赖 A。
    
- A 需要进行 AOP 增强。
    

### 3.5.1 如果只有二级缓存，会有什么问题？

假设 A 实例化后，Spring 直接将原始 A 对象放入二级缓存。

创建过程：

1. Spring 创建 A 的原始对象，将它放入二级缓存。
    
2. 创建 B 时，发现 B 依赖 A，于是从二级缓存获取 A。
    
3. B 注入的是原始 A 对象。
    
4. A 完成初始化后，Spring 为 A 创建 AOP 代理对象。
    

此时就出现了问题：

```text
B 中持有的引用：原始 A 对象

Spring 容器最终提供：代理 A 对象
```

两者不是同一个对象。

当 B 调用 A 的方法时，可能直接调用原始对象，绕过代理对象，导致 AOP 增强无法生效。

### 3.5.2 三级缓存如何解决？

三级缓存存放的不是原始对象，而是一个 `ObjectFactory`（对象工厂）。

这个工厂可以在需要提前获取 A 时，判断是否需要创建 AOP 代理对象，并返回相应的引用。

创建过程：

1. Spring 创建 A 的原始对象。
    
2. 将 A 对应的 `ObjectFactory` 放入三级缓存。
    
3. 创建 B 时，发现 B 依赖 A。
    
4. Spring 调用三级缓存中的工厂，获取 A 的提前暴露引用。
    
5. 如果 A 需要 AOP 代理，就返回代理 A；否则返回原始 A。
    
6. 将获取到的引用放入二级缓存，后续依赖 A 的 Bean 可以直接复用。
    

这样，B 提前注入的引用就可以与 Spring 最终提供的引用保持一致。

### 3.5.3 总结

|缓存|存放内容|作用|
|---|---|---|
|一级缓存|完全创建好的单例 Bean|存放正常创建完成的对象|
|二级缓存|提前暴露的对象引用|存放已经获取到的早期引用|
|三级缓存|`ObjectFactory` 对象工厂|按需获取早期引用，兼容 AOP 代理|

**核心区别：**

- 二级缓存：直接存放提前暴露的对象引用。
    
- 三级缓存：存放对象工厂，需要时通过工厂获取提前暴露的引用。
    

三级缓存的核心价值是：**让 Spring 在循环依赖发生时，有机会提前创建并暴露 AOP 代理对象，避免其他 Bean 注入原始对象，而容器最终却提供代理对象的问题。**

## 3.6 三级缓存的数据结构是什么？

|缓存|Java 数据结构|Value 类型|
|---|---|---|
|一级缓存|`Map<String, Object>`|Bean 对象|
|二级缓存|`Map<String, Object>`|早期 Bean 引用|
|三级缓存|`Map<String, ObjectFactory<?>>`|ObjectFactory 工厂对象|

三个缓存的 Key 都是 Bean 的名称。

注意：三级缓存保存的不是 Bean 对象，而是用于获取 Bean 早期引用的工厂。

# 5. Spring 事务管理
## 5.1 什么是 Spring 事务？

**事务是保证一组数据库操作具有一致性的机制。**

例如转账：

```text
账户 A 扣除 100 元
       |
       v
账户 B 增加 100 元
```

这两个操作应该同时成功或同时失败。

如果 A 扣款成功，但 B 增加余额失败，就会产生数据不一致。

Spring 提供了统一的事务管理机制，让开发者不需要直接编写大量底层事务控制代码。

Spring 主要提供两种事务管理方式：

- 编程式事务：通过代码主动控制事务。
    
- 声明式事务：通过注解或配置声明事务规则。
    

实际开发中最常见的是声明式事务。

## 5.2 Spring 声明式事务的实现原理是什么？

Spring 的声明式事务主要通过：

**AOP 代理 + 事务拦截器 + 事务管理器** 实现。

例如：

```java
@Transactional
public void transfer() {
    // 扣除账户 A 的余额
    // 增加账户 B 的余额
}
```

当外部通过 Spring 代理对象调用这个方法时：

```text
调用方
  |
  v
代理对象
  |
  v
TransactionInterceptor
  |
  v
PlatformTransactionManager
  |
  v
开启事务
  |
  v
执行目标方法
  |
  v
正常返回？
  |
  +------ 是 ------> 提交事务
  |
  +------ 否 ------> 根据回滚规则决定是否回滚
```

具体过程：

1. 调用方通过代理对象调用方法。
    
2. `TransactionInterceptor` 拦截方法调用。
    
3. 读取 `@Transactional` 中的事务配置。
    
4. 事务管理器根据传播行为决定是否创建事务。
    
5. 执行业务方法。
    
6. 根据执行结果和异常回滚规则提交或回滚事务。
    
7. 清理事务资源。
    

常见的事务管理器接口是 `PlatformTransactionManager`。

需要注意：Spring 负责协调事务，真正执行数据库提交和回滚的是底层数据库及其事务资源。

普通数据库事务也不会自动保证 Redis、HTTP 请求和其他数据库操作一起原子提交。

## 5.3 Spring 事务在什么情况下会失效？

这是一道非常常见的面试题。

主要有以下几种情况：

**（1）对象没有交给 Spring 管理**

```java
UserService userService = new UserService();
userService.update();
```

自己通过 `new` 创建的对象没有经过 Spring 的事务代理。

即使方法上有 `@Transactional`，也不会自动开启事务。

**（2）同一个类内部通过 this 调用**

```java
@Service
public class UserService {

    public void update() {
        this.save();
    }

    @Transactional
    public void save() {
        // 数据库操作
    }
}
```

因为 Spring 声明式事务依赖 AOP 代理。

外部调用时：

```text
调用方 -> 代理对象 -> 目标方法
```

但内部使用 `this.save()` 时：

```text
目标方法 -> this.save()
```

直接调用了当前对象的方法，没有经过代理对象。

因此 `save()` 上的事务注解不会生效。

注意：如果 `update()` 本身已经处于事务中，那么 `save()` 中的数据库操作仍然可能参与外层事务。失效的是 `save()` 自己的事务增强，而不是说数据库操作一定没有事务。

**（3）方法无法被代理**

例如：

- `private` 方法不能通过 Spring AOP 代理增强（两种动态代理一个是基于接口一个是继承，`private` 方法他们都看不到）。
    
- CGLIB 不能代理 `final` 类。
    
- CGLIB 不能增强 `final` 方法。
    

另外，JDK 动态代理主要拦截接口暴露的方法。

Spring 6.0 起，类代理默认也支持可代理的 `protected` 和包可见方法，但为了减少版本和代理方式差异，业务事务方法通常使用 `public`。

**（4）异常不符合默认回滚规则**

Spring 默认情况下：

- `RuntimeException`：回滚。
    
- `Error`：回滚。
    
- 受检异常（Checked Exception）：默认不回滚。
    

例如：

```java
@Transactional
public void update() throws Exception {
    // 数据库操作
    throw new Exception();
}
```

默认情况下，受检异常不会触发事务回滚。

如果希望所有异常都回滚，可以配置：

```java
@Transactional(rollbackFor = Exception.class)
```

**（5）异常被捕获，没有继续抛出**

```java
@Transactional
public void update() {
    try {
        // 数据库操作
        throw new RuntimeException();
    } catch (Exception e) {
        // 只捕获异常，没有继续抛出
    }
}
```

事务拦截器没有发现异常，并且事务也没有被标记为 `rollback-only`，就可能正常提交。

**（6）跨线程执行**

Spring 常见的 JDBC 本地事务资源绑定在当前线程。

如果在事务方法中创建新线程执行数据库操作，新线程不会自动继承外层事务。

**（7）事务管理器与实际数据库资源不匹配**

例如多数据源场景中，使用了错误的事务管理器，导致 SQL 操作没有使用当前事务管理器管理的连接。

**总结：**

遇到事务失效，重点检查：

1. 对象是否由 Spring 管理？
    
2. 方法调用是否经过代理？
    
3. 方法是否能够被代理？
    
4. 异常是否符合回滚规则？
    
5. 是否跨线程执行？
    
6. 事务管理器是否正确？
    

## 5.4 Spring 事务使用 this 调用是否生效？

**结论：this 调用不会触发被调用方法自身的事务增强。**

例如：

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder() {
        this.saveLog();
    }

    @Transactional(
        propagation = Propagation.REQUIRES_NEW
    )
    public void saveLog() {
        // 保存日志
    }
}
```

外部通过代理调用 `createOrder()`：

1. `createOrder()` 开启事务。
    
2. 执行 `this.saveLog()`。
    
3. 内部调用绕过代理。
    
4. `saveLog()` 上的 `REQUIRES_NEW` 不会生效。
    

因此，`saveLog()` 的数据库操作仍可能参与外层事务，而不是创建独立事务。

解决方法：

将 `saveLog()` 拆到另一个 Service 中，通过 Spring 注入的 Bean 调用。

```text
OrderService
     |
     v
LogService 代理对象
     |
     v
saveLog()
     |
     v
开启独立事务
```

## 5.5 Spring 事务的传播行为有哪些？

**事务传播行为用于规定：当一个事务方法调用另一个事务方法时，被调用的方法应该如何处理当前事务。**

Spring 一共有七种传播行为。

|传播行为|当前存在事务|当前不存在事务|
|---|---|---|
|REQUIRED|加入当前事务|创建新事务|
|REQUIRES_NEW|挂起当前事务，创建新事务|创建新事务|
|NESTED|在当前事务中建立保存点|创建新事务|
|SUPPORTS|加入当前事务|非事务方式执行|
|NOT_SUPPORTED|挂起当前事务，非事务方式执行|非事务方式执行|
|MANDATORY|加入当前事务|抛出异常|
|NEVER|抛出异常|非事务方式执行|

**重点理解前三种：**

**（1）REQUIRED：默认传播行为**

**如果当前存在事务，就加入当前事务。**

**如果不存在事务，就创建一个新事务。**

```text
方法 A（事务）
   |
   v
方法 B（REQUIRED）
   |
   v
加入 A 的事务
```

适用于多个操作需要一起成功或失败的场景。

**（2）REQUIRES_NEW**

**无论当前是否存在事务，都创建一个新的独立事务。**

如果当前存在事务，则先挂起外层事务。

```text
外层事务 A
     |
     v
   挂起
     |
     v
独立事务 B
     |
     v
   提交
     |
     v
恢复外层事务 A
```

例如：订单失败后，希望失败日志仍然能够独立保存。

可以让日志服务使用 `REQUIRES_NEW`。

**（3）NESTED**

**如果当前存在事务，就在当前事务内部创建一个保存点（就是存档点，本身还是属于外部事物）。**

如果当前不存在事务，则创建新事务。

```text
外层事务 A
     |
     v
创建保存点
     |
     v
执行内部操作 B
     |
     v
B 执行失败
     |
     v
回滚到保存点
     |
     v
A 可以继续执行
```

注意：**NESTED 不是完全独立的事务。**

如果外层事务最终回滚，内部事务已经执行的修改也会一起回滚。

另外，NESTED 需要底层事务管理器支持保存点。

## 5.6 REQUIRES_NEW 和 NESTED 有什么区别？

两者都可以让内部操作单独处理失败，但底层机制不同。

| 对比        | REQUIRES_NEW    | NESTED     |
| --------- | --------------- | ---------- |
| 实现方式      | 创建独立物理事务        | 使用保存点      |
| 与外层事务关系   | 完全独立            | 属于外层事务     |
| 内部回滚      | 回滚自己的事务         | 回滚到**保存点** |
| 内部提交后外层回滚 | 内部提交结果保留        | 内部修改也会回滚   |
| 资源        | JDBC 场景通常需要额外连接 | 通常复用外层连接   |

记忆：

- `REQUIRES_NEW`：真正开启一个独立事务。
    
- `NESTED`：在当前事务里面创建保存点。
    

## 5.7 为什么捕获了异常，事务还是回滚了？

这通常与 `rollback-only` 标记有关。

例如：

- A 方法调用 B 方法。
    
- A 和 B 都使用默认的 `REQUIRED`。
    
- B 执行过程中抛出运行时异常。
    

执行流程：

```text
A 开启事务
    |
    v
调用 B
    |
    v
B 抛出 RuntimeException
    |
    v
事务被标记为 rollback-only
    |
    v
A 捕获异常
    |
    v
A 继续执行并正常返回
    |
    v
尝试提交事务
    |
    v
发现 rollback-only
    |
    v
最终回滚
```

甚至可能抛出 `UnexpectedRollbackException`。

**原因是：A 和 B 实际上共享同一个物理事务。**

- **B 抛出异常：异常向外传播，B 的事务拦截器发现运行时异常后，将共享事务标记为 `rollback-only`。**
    
- **A 捕获异常：A 虽然捕获了异常，可以继续执行，但这并不会自动清除 `rollback-only` 标记，也不能直接恢复为正常提交状态。**

## 5.8 @Transactional 中的隔离级别和 readOnly 有什么作用？
### 5.8.1 隔离级别

**隔离级别用于控制多个并发事务之间的数据可见性。**

Spring 支持以下隔离级别：

|隔离级别|含义|
|---|---|
|DEFAULT|使用底层数据库默认隔离级别|
|READ_UNCOMMITTED|读未提交|
|READ_COMMITTED|读已提交|
|REPEATABLE_READ|可重复读|
|SERIALIZABLE|串行化|

注意：Spring 的 `DEFAULT` 并不代表固定使用某种隔离级别，而是使用底层数据库的默认设置。

### 5.8.2 readOnly

**`readOnly = true` 表示当前事务主要用于读取数据。**

例如：

```java
@Transactional(readOnly = true)
public User getUser(Long id) {
    return userMapper.selectById(id);
}
```

它主要是向事务管理器、JDBC 驱动或 ORM 提供只读提示，可能帮助进行性能优化。

注意：

- `readOnly = true` 不等于所有情况下都禁止写操作。
    
- 不能将它当成数据库权限控制。
    
- 是否真正限制写入取决于底层实现。
    

# 6. Spring Bean 生命周期
## 6.1 什么是 Bean？

**Bean 是由 Spring IoC 容器创建、管理的对象。**

例如：

```java
@Service
public class UserService {
}
```

Spring 扫描到这个类后，会根据 Bean 定义创建对象，并将其交给 IoC 容器管理。

Bean 的生命周期就是：从创建对象到初始化完成，再到最终销毁的整个过程。

### 6.2 Bean 的生命周期有哪些阶段？

Bean 的生命周期主要分为以下几个阶段：

```text
       1. 实例化（Instantiation）
                 |
                 v
       2. 属性注入（Populate）
                 |
                 v
       3. 初始化前处理
          BeanPostProcessor
          postProcessBeforeInitialization()
                 |
                 v
       4. 初始化（Initialization）
          @PostConstruct
          InitializingBean
          init-method
                 |
                 v
       5. 初始化后处理
          BeanPostProcessor
          postProcessAfterInitialization()
                 |
                 v
       6. Bean 创建完成
          放入单例缓存（Singleton）
                 |
                 v
       7. 容器关闭
                 |
                 v
       8. 销毁（Destruction）
          @PreDestroy
          DisposableBean
          destroy-method
```

下面分别解释。

**（1）实例化**

**Spring 根据 BeanDefinition 创建对象。**

本质上就是调用构造方法，创建 Java 对象。

此时对象已经存在，但是属性可能还没有注入。

**（2）属性注入**

Spring 将 Bean 所依赖的其他对象注入进来。

例如：

```java
@Autowired
private UserDao userDao;
```

Spring 会将对应的 `UserDao` Bean 注入 `UserService`。

**（3）初始化前处理**

Spring 调用 BeanPostProcessor 的：

```java
postProcessBeforeInitialization()
```

**允许开发者在 Bean 初始化之前对对象进行处理。**

**（4）初始化**

**Spring 执行 Bean 的初始化逻辑。**

常见方式：

- `@PostConstruct`
    
- `InitializingBean` 接口的 `afterPropertiesSet()`
    
- `@Bean` 的 `initMethod`
    

**（5）初始化后处理**

Spring 调用：

```java
postProcessAfterInitialization()
```

允许开发者在 Bean 初始化后进一步处理对象。

AOP 代理对象通常也在这个阶段创建，因此最终放入容器的对象可能是代理对象，而不是原始对象。

注意：遇到循环依赖时，代理对象也可能通过提前暴露机制提前生成，不能简单地认为所有 AOP 代理都只在这个阶段创建。

**（6）Bean 创建完成**

完成相关处理后，Bean 可以正常使用。

对于默认的 Singleton Bean，Spring 会将其放入单例缓存。

**（7）销毁**

**Spring 容器关闭时，会调用受容器管理的 Bean 的销毁回调。**

例如释放数据库连接、关闭线程池等资源。

注意：Spring 的销毁回调是资源清理，不是直接释放 JVM 内存。对象内存最终仍由垃圾回收器管理。

**简单来说，可以把 Spring 容器创建 Bean 的过程视为：实例化（new） -> 属性注入（塞依赖） -> 初始化 -> 使用中 -> 销毁。**

## 6.3 Bean 初始化和销毁有哪些方式？

Spring 提供了几种常见方式。

**（1）使用 @PostConstruct 和 @PreDestroy**

```java
@Component
public class UserService {

    @PostConstruct
    public void init() {
        // 初始化逻辑
    }

    @PreDestroy
    public void destroy() {
        // 销毁逻辑
    }
}
```

**（2）实现 InitializingBean 和 DisposableBean**

```java
@Component
public class UserService
        implements InitializingBean, DisposableBean {

    @Override
    public void afterPropertiesSet() {
        // 初始化逻辑
    }

    @Override
    public void destroy() {
        // 销毁逻辑
    }
}
```

**（3）通过 @Bean 指定初始化和销毁方法**

```java
@Configuration
public class AppConfig {

    @Bean(
        initMethod = "init",
        destroyMethod = "destroy"
    )
    public UserService userService() {
        return new UserService();
    }
}
```

**实际开发中，`@PostConstruct` 和 `@PreDestroy` 比较常见。**

注意：Spring Boot 3.x 使用 `jakarta.annotation` 包下的注解，Spring Boot 2.x 常见的是 `javax.annotation`。

## 6.4 BeanFactoryPostProcessor 和 BeanPostProcessor 有什么区别？

这是 Bean 生命周期中比较重要的两个扩展接口。

**它们最大的区别是：处理的对象不同，执行的时机也不同。**

### 6.4.1 BeanFactoryPostProcessor

处理的是 **BeanDefinition**，也就是 **Bean 的定义信息**。

执行时机：普通 Bean 实例化之前。

它可以**修改 Bean 的定义信息**，例如：

- 修改 Bean 的属性配置。
    
- 修改 Bean 的作用域。
    
- 修改其他 Bean 元数据。
    

**可以理解为：在对象创建之前，修改对象的生产说明书。**

### 6.4.2 BeanPostProcessor

**处理的是已经创建出来的 Bean 实例。**

执行时机：**Bean 初始化前后**。

它可以：

- 修改 Bean 对象。
    
- 包装 Bean 对象。
    
- 返回代理对象。
    

**Spring AOP 的自动代理创建器就是典型的 BeanPostProcessor。**

**对比：**

| 对比   | BeanFactoryPostProcessor | BeanPostProcessor |
| ---- | ------------------------ | ----------------- |
| 处理对象 | BeanDefinition           | Bean 实例           |
| 执行时机 | Bean 实例化之前               | Bean 初始化前后        |
| 主要作用 | 修改 Bean 定义               | 处理或包装 Bean 对象     |
| 典型应用 | 修改配置元数据                  | 创建 AOP 代理         |

记忆：

- **BeanFactoryPostProcessor：修改对象的生产说明书。**
    
- **BeanPostProcessor：处理已经创建出来的对象。**

## 6.5 Spring 有哪些扩展点？

Spring 提供了很多扩展接口，允许开发者在框架运行的不同阶段加入自定义逻辑。

常见的有：

| 扩展点                                 | 作用                  |
| ----------------------------------- | ------------------- |
| BeanFactoryPostProcessor            | 修改 Bean 定义          |
| BeanDefinitionRegistryPostProcessor | 注册或修改 Bean 定义       |
| BeanPostProcessor                   | 初始化前后处理 Bean        |
| ImportSelector                      | 根据条件选择需要导入的配置类      |
| ImportBeanDefinitionRegistrar       | 动态注册 BeanDefinition |
| HandlerInterceptor                  | 拦截 Spring MVC 请求    |
| ApplicationListener                 | 监听 Spring 容器事件      |

其中最需要掌握的是：

1. BeanFactoryPostProcessor。
    
2. BeanPostProcessor。
    
3. BeanDefinitionRegistryPostProcessor。
    

# 7. Bean 作用域与容器
## 7.1 Spring Bean 默认是单例还是多例？

**Spring Bean 默认是 Singleton，即单例作用域。**

例如：

```java
@Service
public class UserService {
}
```

在同一个 Spring 容器中，通过同一个 Bean 定义多次获取 `UserService`，通常得到的是**同一个对象**。

```java
UserService a = context.getBean(UserService.class);
UserService b = context.getBean(UserService.class);

System.out.println(a == b); // true
```

**这里的单例是指：同一个 Spring 容器中的同一个 Bean 定义对应一个共享实例。**

不是整个 JVM 中只能存在一个对象。

如果创建两个 Spring 容器，它们可以分别创建自己的 `UserService`。

## 7.2 Spring Bean 的作用域有哪些？

Spring 常见的 Bean 作用域：

|作用域|含义|
|---|---|
|Singleton|单例，同一个容器中的同一个 Bean 定义共享一个实例|
|Prototype|原型，每次向容器获取 Bean 都创建新对象|
|Request|每个 HTTP 请求创建一个 Bean|
|Session|每个 HTTP Session 创建一个 Bean|
|Application|每个 ServletContext 创建一个 Bean|
|WebSocket|每个 WebSocket Session 对应一个 Bean|

其中：

- **Singleton 和 Prototype 是常见的核心作用域。**
    
- Request、Session、Application、WebSocket 主要用于 Web 应用。
    

可以通过 `@Scope` 指定作用域：

```java
@Component
@Scope("prototype")
public class UserService {
}
```

## 7.3 Bean 是否都是单例？单例 Bean 是否线程安全？

**Bean 默认是单例，但也可以设置成其他作用域。**

另外，**Spring 不会因为 Bean 是单例，就自动保证它的线程安全。**

例如：

```java
@Service
public class UserService {

    private Long currentUserId;

    public void handle(Long userId) {
        this.currentUserId = userId;
    }
}
```

假设两个请求同时访问这个 Bean：

```text
线程 A：currentUserId = 1
线程 B：currentUserId = 2
```

**由于两个线程共享同一个 UserService，可能出现线程 A 读取到线程 B 修改后的数据。**

这就是线程安全问题。

**解决方法：**

- **尽量使用局部变量存储请求数据。**
    
- **不要在单例 Bean 中随意保存可变的请求状态。**
    
- **必须共享状态时，使用锁、原子类或并发容器等机制。**
    

因此，**单例只代表对象共享，不代表线程安全**。

## 7.4 单例 Bean 中注入 Prototype Bean，每次使用都会创建新对象吗？

**不会。**

例如：

```java
@Component
@Scope("prototype")
public class TaskContext {
}
```

```java
@Service
public class TaskService {

    @Autowired
    private TaskContext taskContext;

}
```

虽然 `TaskContext` 是 Prototype，但 `TaskService` 是 Singleton。

创建 `TaskService` 时，Spring 会解析一次依赖，并将当时创建的 `TaskContext` 注入进去。

之后每次使用 `taskContext`，都是**同一个对象**。

**如果希望每次使用都创建新的 Prototype Bean，可以使用 `ObjectProvider`：**

```java
@Service
public class TaskService {

    private final ObjectProvider<TaskContext> provider;

    public TaskService(ObjectProvider<TaskContext> provider) {
        this.provider = provider;
    }

    public void execute() {
        TaskContext context = provider.getObject();
    }
}
```

每次调用 `getObject()`，Spring 都会重新获取一个 Prototype Bean。

## 7.5 Spring 容器中存放的是什么？

**Spring 容器**中不只是 **Bean 对象**，还包括**管理 Bean 所需要的信息和基础设施**。

主要包括：

**（1）BeanDefinition**

**Bean 的定义信息**，例如：

- Bean 类型。
    
- Bean 作用域。
    
- 构造参数。
    
- 属性信息。
    
- 初始化和销毁方法。
    

可以理解为对象的生产说明书。

**（2）Bean 实例**

已经创建的 **Bean 对象**。

其中 Singleton Bean 通常保存在单例缓存中。

Prototype Bean 不会像 Singleton 一样长期保存在单例缓存中。

**（3）其他管理信息**

例如：

- Bean 名称和别名。
    
- Bean 之间的依赖关系。
    
- BeanPostProcessor 等扩展组件。
    
- 环境配置、事件发布等基础设施。
    

## 7.6 BeanFactory 和 ApplicationContext 有什么区别？

两者都是 Spring IoC 容器相关的**核心接口**。

### 7.6.1 BeanFactory

是 Spring IoC 容器的**基础接口**，定义了容器管理 Bean 的基本能力。

主要包括：

- **获取 Bean**：通过名称或类型从容器中获取 Bean，例如 `getBean()`。
    
- **管理 Bean**：维护 Bean 的定义、作用域和生命周期。
    
- **依赖管理**：根据 Bean 的依赖关系，完成对象的创建和依赖注入。
    

**实际开发中通常不需要直接操作 BeanFactory，而是使用它的扩展接口 `ApplicationContext`。**

### 7.6.2 ApplicationContext

**是 BeanFactory 的扩展，提供了更多企业级功能。**

例如：

- 事件发布。
    
- 国际化。
    
- 资源加载。
    
- 环境配置。
    
- 自动注册和执行相关后置处理器。
    

另外，两者在 Bean 创建时机上也有区别：

- 普通 BeanFactory 通常按需创建 Bean。
    
- ApplicationContext 在刷新容器时，通常会提前创建非懒加载的 Singleton Bean。
    

**实际开发中，我们主要使用 ApplicationContext。**

## 7.7 BeanFactory 和 FactoryBean 有什么区别？

两者名称很相似，但作用完全不同。

### （1）BeanFactory：管理 Bean 的容器

是 Spring IoC 容器的**基础接口**，负责**管理 Bean**，例如创建、获取 Bean，以及管理 Bean 之间的依赖关系。

### （2）FactoryBean：专门生产 Bean 的工厂

是 Spring 提供的一个**特殊接口**，允许**开发者自定义 Bean 的创建过程**。

**主要作用：**

当某个对象需要通过**特殊方式创建**时，可以使用 FactoryBean 封装创建逻辑。

例如：

- MyBatis 的 `MapperFactoryBean`：创建 Mapper 接口对应的代理对象。
    
- 其他需要通过工厂方法或特殊逻辑创建的对象，也可以使用 FactoryBean。
    

**获取方式：**

假设容器中有一个名为 `userMapper` 的 FactoryBean：

```java
context.getBean("userMapper");  // 获取工厂生产的对象

context.getBean("&userMapper"); // 获取 FactoryBean 本身
```

**记忆：**

- **BeanFactory：管理 Bean 的容器。**
    
- **FactoryBean：自定义 Bean 创建过程的工厂。**
