# 1. MVC 分层介绍一下
## 1.1 什么是 MVC？

MVC 全称是 **Model-View-Controller**，即模型、视图、控制器，是一种软件设计模式。

它的核心思想是：**将数据、业务处理和界面展示分离，降低代码之间的耦合度。**

MVC 主要包含三个部分：

|组成|作用|举例|
|---|---|---|
|Model（模型）|负责数据的存储和业务处理|用户数据、业务逻辑|
|View（视图）|负责展示数据，与用户进行交互|HTML 页面|
|Controller（控制器）|接收用户请求，调用 Model 处理业务，并返回处理结果|Controller 类|

**（1）Model：模型**

**负责承载数据和处理业务。**

在传统 MVC 中，Model 既可以表示**数据对象**，也可以包含**业务处理逻辑**。

在常见的 Spring Boot 后端项目中，通常会进一步拆分为：

- Entity：负责表示数据实体。
    
- Service：负责处理业务逻辑。
    
- Mapper / DAO：负责访问数据库。
    

**（2）View：视图**

负责将**数据展示给用户**，例如 HTML 页面。

**（3）Controller：控制器**

负责**接收用户请求**，**调用**相应的**业务逻辑**，并将**处理结果返回**给用户。

## 1.2 MVC 的工作流程

例如，用户访问一个查询用户信息的页面：

```
用户
 |
 | 发送请求
 v
Controller
 |
 | 调用
 v
Model
 |
 | 返回处理结果
 v
Controller
 |
 | 返回视图
 v
View
 |
 | 展示页面
 v
用户
```

具体步骤：

1. 用户通过 View 发起请求。
    
2. Controller 接收请求，并调用 Model 处理业务。
    
3. Model 完成数据查询或业务处理，将结果返回给 Controller。
    
4. Controller 根据处理结果选择对应的 View。
    
5. View 将数据渲染成页面，返回给用户。
    

**注意：MVC 是一种设计模式，Spring MVC 则是 Spring 提供的 Web 框架，用来帮助我们实现 MVC 架构。**

在现在常见的前后端分离项目中，Controller 通常返回 JSON 数据，而不是直接返回 HTML 页面。

# 2. SpringMVC 的处理流程是什么？
## 2.1 什么是 SpringMVC？

Spring MVC 是 Spring 提供的 Web 框架，基于 Java Servlet API 构建，主要负责处理 HTTP 请求和响应。

它的核心组件是 **DispatcherServlet（前端控制器）**。

DispatcherServlet 会**统一接收客户端请求**，然后**将请求分发给合适的 Controller 处理**，最后将处理结果返回给客户端。

## 2.2 SpringMVC 的处理流程

以一个普通的 HTTP 请求为例：

```text
客户端发送 HTTP 请求
          |
          v
       Filter
          |
          v
   DispatcherServlet
          |
          v
    HandlerMapping
          |
          v
       Handler
          |
          v
    HandlerAdapter
          |
          v
    Controller 方法
          |
          v
      Service
          |
          v
      Mapper
          |
          v
        数据库
```

业务处理完成后，根据 Controller 的返回类型，有不同的响应处理方式：

**情况一：返回页面**

```text
Controller
    |
    v
返回 View 名称 / ModelAndView
    |
    v
  ViewResolver
    |
    v
  View 页面渲染
    |
    v
返回 HTTP 响应
```

**情况二：返回 JSON 数据（前后端分离项目常见）**

```text
Controller
    |
    v
返回 Java 对象
    |
    v
HttpMessageConverter
    |
    v
序列化为 JSON
    |
    v
写入 HTTP 响应体
```

其中，`HttpMessageConverter`（HTTP 消息转换器）负责将 Java 对象转换成 HTTP 响应内容，或者将请求内容转换成 Java 对象。

例如，常见的 Jackson 就可以将 Java 对象序列化为 JSON。

## 2.3 具体处理步骤

1. **接收请求：** 客户端发送 HTTP 请求，请求经过 Filter 后进入 DispatcherServlet。
    
2. **查找处理器：** DispatcherServlet 调用 HandlerMapping，根据 URL、请求方法等信息找到能够处理请求的 Handler。
    
3. **选择适配器：** DispatcherServlet 根据 Handler 找到对应的 HandlerAdapter。
    
4. **执行拦截器：** 执行拦截器的 `preHandle()` 方法。如果返回 `false`，则后续处理会中止。
    
5. **执行 Controller：** HandlerAdapter 解析请求参数、完成数据转换和校验，然后调用 Controller 方法。
    
6. **处理返回值：** 根据 Controller 的返回结果，选择视图解析方式或 HTTP 消息转换方式。
    
7. **完成请求：** 如果需要返回页面，则进行视图渲染；最后执行拦截器的 `afterCompletion()` 等回调，完成请求处理。
    

如果请求处理过程中出现异常，则会交给 Spring MVC 的异常处理机制处理，例如 `@ExceptionHandler` 和 `@ControllerAdvice`。

## 2.4 补充：Filter 和 Interceptor 的区别

两者都可以对请求进行拦截，但执行位置和作用范围不同。

|对比|Filter（过滤器）|Interceptor（拦截器）|
|---|---|---|
|所属|Servlet 规范|Spring MVC|
|执行位置|DispatcherServlet 之前等 Servlet 过滤链环节|DispatcherServlet 内部的 MVC 处理流程|
|拦截范围|符合配置的 Web 请求|Spring MVC 中匹配到的 Handler 请求|
|主要作用|编码处理、跨域处理、请求过滤等|登录校验、权限检查、请求日志等|

可以简单理解：

- Filter：在请求进入 Spring MVC 之前进行处理。
    
- Interceptor：在 Spring MVC 处理 Controller 请求的过程中进行拦截。

# 3. @Controller 和 @RestController 有什么区别？

两者主要区别在于 **Controller 方法的返回值如何处理**。

### 3.1 @Controller

`@Controller` 表示这是一个 Spring MVC 控制器。

默认情况下，如果方法返回 String，Spring MVC 会将它作为视图名称处理。

例如：

```java
@Controller
public class UserController {

    @GetMapping("/user")
    public String getUser() {
        return "user";
    }
}
```

这里返回的 `"user"` 表示逻辑视图名称，Spring MVC 会通过 ViewResolver 找到对应的页面。

如果希望返回 JSON 数据，需要在方法上添加 `@ResponseBody`：

```
@Controller
public class UserController {

    @ResponseBody
    @GetMapping("/user")
    public User getUser() {
        return new User(1L, "Tom");
    }
}
```

此时，返回的 User 对象会被消息转换器转换成 JSON 数据，并写入 HTTP 响应体。

### 3.2 @RestController

`@RestController` 相当于：

```
@Controller
@ResponseBody
```

也就是说，`@RestController` 默认会让类中所有请求处理方法都采用响应体返回方式。

例如：

```
@RestController
public class UserController {

    @GetMapping("/user")
    public User getUser() {
        return new User(1L, "Tom");
    }
}
```

返回的 User 对象会被转换为 JSON 数据，而不是视图名称。

### 3.3 两者的区别总结

|注解|默认返回值处理方式|
|---|---|
|@Controller|通常将 String 作为视图名称|
|@RestController|将返回值作为响应体内容|

**实际开发中：**

- 如果需要返回 HTML 页面，通常使用 `@Controller`。
    
- 如果是前后端分离项目，Controller 主要返回 JSON 数据，通常使用 `@RestController`。

## 4. @RequestParam、@PathVariable 和 @RequestBody 有什么区别？

这三个注解都可以用于接收 HTTP 请求中的数据，主要区别在于 **数据来源不同**。

### 4.1 @RequestParam

用于获取 URL 查询参数或表单参数。

例如：

```
GET /users?page=1&size=10
```

Controller：

```
@GetMapping("/users")
public String getUsers(
        @RequestParam("page") Integer page,
        @RequestParam("size") Integer size) {

    return "查询第 " + page + " 页";
}
```

这里：

- `page` 从请求参数中获取，值为 1。
    
- `size` 从请求参数中获取，值为 10。
    

常用属性：

|属性|作用|
|---|---|
|value / name|指定请求参数名称|
|required|是否必须提供，默认 true|
|defaultValue|设置默认值|

例如：

```
@RequestParam(value = "page", defaultValue = "1")
Integer page
```

当请求没有提供 page 参数时，默认使用 1。

### 4.2 @PathVariable

用于获取 URL 路径中的变量。

例如：

```
GET /users/1001
```

Controller：

```
@GetMapping("/users/{id}")
public String getUser(@PathVariable("id") Long id) {
    return "用户 ID：" + id;
}
```

这里的 `id` 来自 URL 路径中的 `{id}`，值为 1001。

### 4.3 @RequestBody

用于获取 HTTP 请求体（Request Body）中的数据。

常见场景是接收前端传递的 JSON 数据。

例如，请求：

```
POST /users
Content-Type: application/json
```

请求体：

```
{
    "name": "Tom",
    "age": 20
}
```

Controller：

```
@PostMapping("/users")
public String createUser(@RequestBody User user) {
    return "用户名：" + user.getName();
}
```

Spring MVC 会通过 `HttpMessageConverter` 将 JSON 数据转换成 User Java 对象。

### 4.4 三者区别总结

|注解|数据来源|常见使用场景|
|---|---|---|
|@RequestParam|URL 查询参数、表单参数|分页查询、条件查询|
|@PathVariable|URL 路径|根据用户 ID 查询|
|@RequestBody|HTTP 请求体|接收 JSON 数据|

例如，一个修改用户信息的接口：

```
@PutMapping("/users/{id}")
public void updateUser(
        @PathVariable("id") Long id,
        @RequestBody UpdateUserRequest request) {

    // id 从 URL 路径中获取
    // request 从 JSON 请求体中获取
}
```

注意：

1. `@RequestBody` 并不是只能用于 POST 请求，PUT、PATCH 等请求也可以使用。
    
2. `@RequestBody` 负责将请求数据转换成 Java 对象，不代表数据一定通过校验。需要校验时，可以结合 `@Valid` 或 `@Validated` 使用。

## 5. SpringMVC 怎么统一处理异常？

### 5.1 为什么需要统一异常处理？

假设项目中有很多 Controller，如果每个 Controller 都单独编写异常处理代码，就会出现大量重复代码。

例如：

```
@RestController
public class UserController {

    @GetMapping("/user")
    public User getUser() {
        try {
            // 业务逻辑
            return null;
        } catch (Exception e) {
            // 单独处理异常
            return null;
        }
    }
}
```

这样不仅代码重复，而且不方便统一维护异常响应格式。

因此，Spring MVC 提供了全局异常处理机制。

### 5.2 @RestControllerAdvice 和 @ExceptionHandler

通常使用：

- `@RestControllerAdvice`：定义全局异常处理类。
    
- `@ExceptionHandler`：指定某个异常对应的处理方法。
    

例如：

```
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<String> handleException(
            IllegalArgumentException e) {

        return ResponseEntity
                .badRequest()
                .body("请求参数不合法");
    }
}
```

其中：

**@RestControllerAdvice：**

表示这是一个全局 Controller 增强类，可以统一处理多个 Controller 的异常。

**@ExceptionHandler：**

指定当前方法负责处理哪一种异常。

例如：

```
@ExceptionHandler(IllegalArgumentException.class)
```

表示当匹配到 `IllegalArgumentException` 时，执行对应的异常处理方法。

### 5.3 单个 Controller 和全局异常处理的区别

|方式|作用范围|
|---|---|
|Controller 内部的 @ExceptionHandler|当前 Controller|
|@RestControllerAdvice + @ExceptionHandler|多个 Controller，可统一处理异常|

### 5.4 底层原理

Spring MVC 内部通过 `HandlerExceptionResolver` 异常解析器体系处理请求过程中出现的异常。

当 Controller 执行过程中出现异常时，Spring MVC 会尝试找到合适的异常处理器。

`@ExceptionHandler` 和 `@RestControllerAdvice` 就是基于这套机制实现的。

注意：普通 Filter 在 DispatcherServlet 之前抛出的异常，不会直接交给 ControllerAdvice 处理。因此，Filter 中的异常通常需要在 Filter 或更外层进行处理。

## 6. HandlerMapping 和 HandlerAdapter 有什么区别？

这两个都是 Spring MVC 中的重要组件，主要负责请求处理流程中的不同工作。

可以先记住：

- **HandlerMapping：负责找到谁来处理请求。**
    
- **HandlerAdapter：负责调用找到的 Handler。**
    

### 6.1 HandlerMapping（处理器映射器）

作用：根据客户端请求的信息，找到能够处理该请求的 Handler。

例如：

```
@RestController
public class UserController {

    @GetMapping("/users")
    public String getUsers() {
        return "用户列表";
    }
}
```

当客户端访问：

```
GET /users
```

HandlerMapping 会根据请求 URL、请求方法等信息，找到对应的 `getUsers()` 方法。

在注解式 Controller 中，常见的实现是：

`RequestMappingHandlerMapping`

它负责解析 `@RequestMapping`、`@GetMapping` 等注解，并建立请求路径与 Controller 方法之间的映射关系。

### 6.2 HandlerAdapter（处理器适配器）

作用：负责调用 Handler，执行具体的请求处理逻辑。

例如，HandlerMapping 找到了 `UserController` 中的 `getUsers()` 方法之后，HandlerAdapter 就负责调用这个方法。

在注解式 Controller 中，常见的实现是：

`RequestMappingHandlerAdapter`

它除了调用 Controller 方法，还会处理：

- 请求参数解析。
    
- 数据绑定和类型转换。
    
- 参数校验。
    
- 方法返回值处理。
    

### 6.3 为什么需要 HandlerAdapter？

因为 Spring MVC 中的 Handler 不一定都是同一种类型。

例如：

- 使用 `@Controller` / `@RestController` 编写的 Controller 方法。
    
- 实现了 `Controller` 接口的处理器。
    
- 实现了 `HttpRequestHandler` 接口的处理器。
    

不同类型的 Handler，调用方式可能不同。

如果让 DispatcherServlet 直接负责判断 Handler 类型并调用，就需要编写大量判断逻辑。

因此 Spring MVC 引入 HandlerAdapter，将不同 Handler 的调用方式统一起来。

### 6.4 两者区别总结

|组件|主要职责|
|---|---|
|HandlerMapping|根据请求找到对应的 Handler|
|HandlerAdapter|根据 Handler 类型选择合适的方式执行它|

整体流程：

```
客户端发送请求
       |
       v
DispatcherServlet
       |
       v
HandlerMapping
       |
       | 找到 Handler
       v
HandlerAdapter
       |
       | 调用 Handler
       v
Controller 方法
       |
       v
返回处理结果
```

记忆方式：

**HandlerMapping 负责找人，HandlerAdapter 负责让找到的人干活。**
