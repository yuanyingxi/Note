# 1. Java 如何实现网络 I/O 高并发编程？
## 1.1 什么是网络 I/O？

I/O（Input/Output）即输入输出。

在**网络编程**中，I/O 主要指应用程序通过网络连接接收和发送数据的过程。

例如，一个聊天服务器需要同时处理大量客户端连接：

- 接收客户端发送的消息。
    
- 将消息转发给其他客户端。
    
- 处理客户端的断开和重新连接。
    

这些操作都涉及网络 I/O。

## 1.2 传统 BIO 为什么难以支持大量并发连接？

BIO（Blocking I/O）是一种同步阻塞 I/O 模型。

传统 BIO 通常采用**一个客户端连接对应一个处理线程**的方式。

例如：

```text
客户端 A ──> 线程 A
客户端 B ──> 线程 B
客户端 C ──> 线程 C
客户端 D ──> 线程 D
```

每个线程负责处理对应客户端的网络通信。

但是，网络通信并不是一直有数据传输。

例如：

```java
int len = socket.getInputStream().read(buffer);
```

**当 TCP 接收缓冲区中没有数据时，`read()` 会阻塞当前线程，直到有数据到达、连接结束或发生异常。**

这意味着：

- 线程 A 正在等待客户端 A 发送数据。
    
- 线程 B 正在等待客户端 B 发送数据。
    
- 线程 C 正在等待客户端 C 发送数据。
    

即使客户端暂时没有发送任何数据，这些线程仍然需要占用一定的内存和系统资源。

**当客户端数量不断增加时，就需要创建越来越多的线程**，带来以下问题：

1. **内存消耗增加**：每个线程都需要一定的栈空间。
    
2. **上下文切换开销增加**：线程数量过多时，操作系统需要花费更多时间调度线程。
    
3. **线程管理成本增加**：线程的创建、销毁和调度都会产生额外开销。
    

因此，传统的 BIO 模型在大量并发连接场景下扩展性较差。

## 1.3 NIO 如何解决这个问题？

NIO（Non-blocking I/O）可以通过**I/O 多路复用**，让**少量线程管理大量客户端连接**。

核心思想是：

**不需要为每个客户端连接创建一个独立线程，而是让一个线程同时监听多个连接，只处理已经准备好进行 I/O 操作的连接。**

例如：

```text
客户端 A ──┐
客户端 B ──┤
客户端 C ──┼──> Selector ──> 一个线程
客户端 D ──┤
客户端 E ──┘
```

假设有 1000 个客户端连接：

- BIO：传统方式可能需要 1000 个线程分别等待客户端数据。
    
- NIO：可以由少量线程监听这 1000 个连接，只有连接就绪时才进行相应的读写操作。
    

这样就减少了大量线程阻塞等待带来的资源消耗。

例如，聊天服务器中，很多用户可能长时间保持连接，但并不是每时每刻都在发送消息。这种场景就非常适合使用 NIO。

**注意：NIO 并不是让一个线程同时执行 1000 个读写操作，而是让一个线程监听多个连接，哪个连接准备好了，就处理哪个连接。**

# 2. BIO、NIO、AIO 有什么区别？

Java 中常见的 I/O 模型可以分为 BIO、NIO 和 AIO。

## 2.1 BIO（Blocking I/O）

BIO 是同步阻塞 I/O。

特点：

- **阻塞**：当线程执行读写操作时，如果数据尚未准备好，**线程需要等待**。
    
- **同步**：由应用程序线程主动执行读写操作，并等待操作结果。
    
- **典型模型**：**一个客户端**连接对应**一个处理线程**。
    

执行流程：

```text
客户端发送请求
      |
      v
服务器线程调用 read()
      |
      v
检查 TCP 接收缓冲区
      |
      +---- 没有数据 ----> 线程阻塞等待
      |                       |
      |                       v
      |                    数据到达
      |                       |
      +-----------------------+
      |
      v
读取数据
      |
      v
处理请求
```

优点：

- 编程模型简单。
    
- 代码容易理解。
    
- 适合连接数量较少的场景。
    

缺点：

- 每个连接通常需要独立线程处理。
    
- 大量连接会消耗较多线程资源。
    
- 线程阻塞等待时，无法继续处理其他连接的 I/O。
    

## 2.2 NIO（Non-blocking I/O）

NIO 是同步非阻塞 I/O。

Java 1.4 引入了 `java.nio` 包，提供了 `Channel`、`Buffer`、`Selector` 等组件。

特点：

- **非阻塞**：读写操作不会因为等待数据就绪而一直阻塞线程。
    
- **同步**：数据真正的读取和写入仍然由应用程序线程完成。
    
- **I/O 多路复用**：可以通过**一个 Selector 监听多个连接**。
    

执行流程：

```text
客户端 A ──┐
客户端 B ──┤
客户端 C ──┼──> Selector
客户端 D ──┤       |
客户端 E ──┘       v
              监听就绪事件
                   |
                   v
             找到就绪连接
                   |
                   v
              执行 read()
                   |
                   v
                处理数据
```

优点：

- 少量线程可以管理大量连接。
    
- 减少线程阻塞等待。
    
- 适合高并发网络通信。
    

缺点：

- 编程模型相对复杂。
    
- 需要自己管理连接状态、缓冲区和读写事件。
    
- 需要正确处理数据分批读取和写入的问题。
    

## 2.3 AIO（Asynchronous I/O）

AIO 是异步非阻塞 I/O，也称为 NIO.2，是 Java 7 引入的异步 I/O API。

它与 NIO 的主要区别在于：**NIO 是应用程序等待 I/O 就绪后自己执行读写，而 AIO 是提交读写操作后，由系统或运行时在操作完成时通知应用程序。**

#### NIO（同步非阻塞）—— “就绪通知”

- **底层**：NIO 的 Selector 只负责告诉你“数据到了”，**你必须自己调用 `read()` 方法，把数据从内核态拷贝到用户态**。这个拷贝过程是占用你线程的。

#### AIO（异步非阻塞）—— “完成通知”

- **底层**：AIO 提交读取请求后，**操作系统内核会在后台把数据从网线读完，并且直接帮你拷贝到 Java 程序指定的内存里**。全部搞定后，操作系统再通知你的程序：“数据已经放在你家床上了，你可以直接用

例如：

```text
应用程序
    |
    v
提交异步读取请求
    |
    v
立即返回，不等待读取完成
    |
    v
系统或运行时处理 I/O
    |
    v
读取操作完成
    |
    v
通知应用程序
    |
    v
执行后续处理
```

特点：

- **异步**：提交 I/O 请求后，不需要等待操作完成。
    
- **非阻塞**：调用线程可以继续执行其他任务。
    
- **完成通知**：I/O 操作完成后，通过回调或 Future 等方式通知应用程序。
    

优点：

- 应用程序不需要主动等待 I/O 操作完成，。
    
- 适合异步任务编排。
    

缺点：

- 编程模型相对复杂。
    
- Java AIO 在不同操作系统上的底层实现和实际性能表现存在差异。
    
- 并不是所有场景下都比 NIO 更高效。
    

## 2.4 BIO、NIO、AIO 对比

| 对比维度  | BIO            | NIO                | AIO           |
| ----- | -------------- | ------------------ | ------------- |
| 中文名称  | 同步阻塞 I/O       | 同步非阻塞 I/O          | 异步非阻塞 I/O     |
| 阻塞情况  | 读写等待时阻塞        | 通道读写不会因等待数据就绪而一直阻塞 | 提交操作后不等待完成    |
| 数据读取  | 应用线程主动读取       | 应用线程在就绪后主动读取       | 操作完成后通知应用程序   |
| 线程模型  | 传统方式通常一个连接一个线程 | 少量线程管理多个连接         | 提交任务后异步等待完成通知 |
| 编程复杂度 | 较低             | 较高                 | 较高            |
| 典型场景  | 连接较少的简单网络应用    | 高并发网络服务器           | 异步 I/O 操作     |

**重点理解同步与异步、阻塞与非阻塞的区别：**

- 同步与异步：主要看应用程序是否需要自己等待并完成 I/O 操作，还是由系统或运行时在操作完成后通知。
    
- 阻塞与非阻塞：主要看调用线程在等待 I/O 条件或操作完成时，是否会被阻塞。
    

需要注意：NIO 中的 `Selector.select()` 本身可以阻塞等待事件，但这不代表 NIO 的通道读写就是阻塞的。

**这里的读写主要指网络 I/O 中的数据接收和发送**。如果放在 HTTP 服务端的场景下，可以理解为：

- 读（Read）：从网络连接中读取客户端发送过来的 HTTP 请求数据。
    
- 写（Write）：向网络连接中写入 HTTP 响应数据，返回给客户端。

# 3. NIO 是如何实现的？

NIO 主要通过三个核心组件实现：

- Channel（通道）
    
- Buffer（缓冲区）
    
- Selector（选择器）
    

其中，**Channel 负责数据传输，Buffer 负责存放数据，Selector 负责监听多个通道的就绪事件。**

# 3.0 Socket（套接字）

**Socket 是应用程序进行网络通信时使用的通信端点**，应用程序通过 Socket 建立网络连接，并发送、接收数据。

例如，在 HTTP 通信中：

1. 客户端通过 Socket 与服务器建立连接。
    
2. 客户端通过 Socket 发送 HTTP 请求。
    
3. 服务器通过 Socket 接收请求，并处理业务逻辑。
    
4. 服务器通过 Socket 发送 HTTP 响应。
    
5. 客户端通过 Socket 接收响应。
    

```text
客户端                         服务端
   |                              |
 Socket  <------ TCP连接 ------> Socket
   |                              |
发送 HTTP 请求 ---------------> 接收请求
   |                              |
接收 HTTP 响应 <--------------- 发送响应
```

### Socket 与 TCP、HTTP 的关系

- **TCP**：传输层协议，负责在通信双方之间提供可靠的数据传输。
    
- **Socket**：应用程序使用的通信接口，通过它进行网络数据的发送和接收。
    
- **HTTP**：应用层协议，规定客户端与服务器之间请求和响应的数据格式及交互规则。
    

**总结：Socket 是程序进行网络通信的入口，TCP 负责底层数据传输，HTTP 负责规定应用层的通信规则。**

## 3.1 Channel（通道）

Channel 是**数据传输的通道**，可以理解为应用程序与网络连接之间进行**数据读写的通道**。

传统 BIO 主要通过 InputStream 和 OutputStream 读写数据，而 NIO 使用 Channel 进行数据传输。

常见的 Channel：

|类型|作用|
|---|---|
|`FileChannel`|读写文件|
|`SocketChannel`|处理客户端 TCP 连接|
|`ServerSocketChannel`|监听和接收 TCP 客户端连接|
|`DatagramChannel`|处理 UDP 数据报|

例如：

```java
SocketChannel channel = SocketChannel.open();
```

创建一个客户端 SocketChannel。

Channel 可以工作在阻塞模式或非阻塞模式。

如果需要配合 Selector 实现 I/O 多路复用，通常需要将 Channel 设置为非阻塞模式：

```java
channel.configureBlocking(false);
```

## 3.2 Buffer（缓冲区）

Buffer 是 NIO 中用于存放数据的缓冲区。

**在 NIO 中，数据不能直接通过 Channel 读取到普通变量中，而是需要先读取到 Buffer 中。**

**使用 Buffer 的原因：作为一个“数据中转站”，用来暂存数据，实现批量的读取和写入；如果不用 Buffer，程序每次只能从网卡或磁盘中读取 1个字节，无法批量处理。**

例如：

```text
读取数据：

网络
  |
  v
Channel
  |
  v
Buffer
  |
  v
应用程序读取数据
```

发送数据时则相反：

```text
应用程序写入数据
       |
       v
     Buffer
       |
       v
     Channel
       |
       v
      网络
```

常见的 Buffer：

|类型|作用|
|---|---|
|`ByteBuffer`|存放字节数据|
|`CharBuffer`|存放字符数据|
|`IntBuffer`|存放 int 数据|
|`LongBuffer`|存放 long 数据|
|`FloatBuffer`|存放 float 数据|
|`DoubleBuffer`|存放 double 数据|

其中，网络编程中最常用的是 `ByteBuffer`。

### 3.2.1 Buffer 的三个重要属性

Buffer 内部有三个重要属性：

|属性|作用|
|---|---|
|capacity|缓冲区容量，创建后固定|
|position|当前读写位置|
|limit|当前允许读写的边界|

例如，创建一个容量为 10 的 ByteBuffer：

```java
ByteBuffer buffer = ByteBuffer.allocate(10);
```

初始状态：

```java
capacity = 10
position = 0
limit = 10
```

写入数据：

```java
buffer.put((byte) 1);
buffer.put((byte) 2);
buffer.put((byte) 3);
```

此时：

```java
capacity = 10
position = 3
limit = 10
```

如果需要从 Buffer 中读取刚才写入的数据，需要调用 `flip()`：

```java
buffer.flip();
```

此时：

```java
capacity = 10
position = 0
limit = 3
```

`flip()` 会将当前写入位置设置为读取边界，并将 position 重置为 0，使 Buffer 进入读取状态。

读取数据：

```java
while (buffer.hasRemaining()) {
    System.out.println(buffer.get());
}
```

读取完成后，可以调用：

```java
buffer.clear();
```

让 Buffer 重新进入写入状态。

注意：`clear()` 并不会真正清空缓冲区中的数据，只是重置 position 和 limit 等状态。

## 3.3 Selector（选择器）

Selector 是 NIO 实现 I/O 多路复用的核心组件。

**它可以同时监听多个 Channel 的就绪事件。**

例如，一个服务器需要处理 1000 个客户端连接：

如果使用 BIO，传统方式可能需要为每个连接分配一个线程。

如果使用 NIO，可以让一个线程通过 Selector 监听这些连接：

```text
客户端 A ──┐
客户端 B ──┤
客户端 C ──┤
客户端 D ──┼──> Selector
客户端 E ──┤       |
    ...    │       v
客户端 N ──┘    一个线程
                   |
                   v
              监听就绪事件
                   |
           +-------+-------+
           |               |
           v               v
        客户端 A         客户端 C
         可读             可读
           |               |
           v               v
        读取数据         读取数据
```

Selector 主要监听以下几种事件：

|事件|含义|
|---|---|
|`OP_ACCEPT`|服务端可以接收新的客户端连接|
|`OP_CONNECT`|客户端连接已经建立或可以完成连接|
|`OP_READ`|通道中有数据可以读取|
|`OP_WRITE`|通道可以进行写入|

注意：`OP_WRITE` 通常在通道具备写入空间时就可能处于就绪状态，因此实际开发中一般只在确实有待发送数据时注册写事件，避免空转。

## 3.4 NIO 的完整执行流程

NIO 通常通过 **Channel + Selector + Buffer** 实现非阻塞 I/O。

- **Channel（通道）**：负责与客户端进行网络数据的读取和写入。
    
- **Selector（选择器）**：负责监控多个 Channel，判断哪些连接已经准备好进行 I/O 操作。
    
- **Buffer（缓冲区）**：临时存放从 Channel 读取的数据，或者准备写入 Channel 的数据。
    

### 3.4.1 第一步：服务器启动并创建 Selector

**服务器启动时，需要创建 `ServerSocketChannel`，并绑定监听端口。**

`ServerSocketChannel` 用于监听客户端的连接请求。

随后，服务器还需要创建一个 `Selector`，并将 `ServerSocketChannel` 注册到 Selector 中，监听 `OP_ACCEPT` 事件。

`OP_ACCEPT` 表示服务器可以接收新的客户端连接。

```text
服务器启动
    |
    v
创建 ServerSocketChannel
    |
    v
绑定服务器端口
    |
    v
设置为非阻塞模式
    |
    v
创建 Selector
    |
    v
将 ServerSocketChannel 注册到 Selector
    |
    v
监听 OP_ACCEPT 事件
```

### 3.4.2 第二步：客户端发起连接

假设客户端 A、B、C 依次连接到服务器。

服务器通过 `ServerSocketChannel` 接收这些连接请求。

**每当有一个客户端成功连接，服务器就会获得一个对应的 `SocketChannel`。**

**ServerSocketChannel 和 SocketChannel 的区别：**

|类型|作用|
|---|---|
|ServerSocketChannel|监听端口，接收客户端连接|
|SocketChannel|与已经建立连接的客户端进行数据通信|

例如：

```text
客户端 A --------\
客户端 B ---------\
客户端 C ----------> ServerSocketChannel
                              |
                              v
                       接收客户端连接
                              |
               +--------------+--------------+
               |              |              |
               v              v              v
          SocketChannel A SocketChannel B SocketChannel C
               |              |              |
               v              v              v
            客户端 A        客户端 B        客户端 C
```

### 3.4.3 第三步：将客户端连接注册到 Selector

**服务器接收客户端连接后，会得到对应的 `SocketChannel`。**

接下来，服务器将这些 `SocketChannel` 设置为**非阻塞模式**，并**注册到 Selector 中**，监听 `OP_READ` 事件。

`OP_READ` 表示对应的连接已经有数据可以读取。

例如：

```text
                    Selector
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
  SocketChannel A SocketChannel B SocketChannel C
     监听可读事件     监听可读事件     监听可读事件
```

**这样，Selector 就可以同时监控多个客户端连接，而不需要为每个连接安排一个线程一直等待数据。**

### 3.4.4 第四步：Selector 监听就绪事件

**服务器通常会使用一个循环，不断调用 `selector.select()` 获取已经就绪的 I/O 事件。**

当没有连接就绪时，`select()` 通常会阻塞等待；当有连接就绪时，它会返回就绪事件的数量。

例如，现在有三个客户端连接：

- 客户端 A 已经发送数据，可以读取。
    
- 客户端 B 暂时没有发送数据。
    
- 客户端 C 已经发送数据，可以读取。
    

此时 Selector 监控到的连接状态如下：

```text
                  Selector
                     |
              监控多个 Channel
                     |
        +------------+------------+
        |            |            |
        v            v            v
     客户端 A      客户端 B      客户端 C
        |            |            |
        v            v            v
       可读         不可读        可读
        |            |            |
        +------------+------------+
                     |
                     v
              返回就绪事件
                     |
              +------+------+
              |             |
              v             v
          Channel A     Channel C
```

Selector 发现 A 和 C 已经有数据可以读取，于是将对应的就绪事件返回给工作线程。

**注意：Selector 负责监控和发现就绪事件，并不负责真正读取客户端发送的数据。**

### 3.4.5 第五步：工作线程读取数据

工作线程获取 Selector 返回的就绪事件后，根据事件找到对应的 `SocketChannel`。

然后创建或准备一个 `Buffer`，调用 `channel.read(buffer)` 将网络数据读取到缓冲区中。

例如：

```text
客户端 A 发送请求
       |
       v
Selector 发现 A 可读
       |
       v
工作线程获取 A 的就绪事件
       |
       v
找到 SocketChannel A
       |
       v
调用 read() 读取数据
       |

```

这里需要注意：

- `SocketChannel` 负责读取网络数据。
    
- `Buffer` 用于临时存放读取到的数据。
    
- 工作线程负责调用读取操作，并处理读取到的数据。
    

另外，**可读事件不代表整个 HTTP 请求已经接收完毕**。它只表示当前已经有数据可以读取，可能需要多次读取才能接收完整请求。

### 3.4.6 第六步：处理请求并返回响应

工作线程从 Buffer 中获取请求数据，按照 HTTP 协议解析请求，然后执行业务逻辑。

业务处理完成后，将响应数据写入 Buffer，再通过 `SocketChannel.write()` 将数据发送给客户端。

```text
客户端发送 HTTP 请求
          |
          v

          |
          v
      Buffer
          |
          v
     解析 HTTP 请求
          |
          v
      处理业务逻辑
          |
          v
     生成 HTTP 响应
          |
          v
      写入 Buffer
          |
          v
 SocketChannel.write()
          |
          v
    返回 HTTP 响应
          |
          v
       客户端
```

这里还需要注意：非阻塞写入不一定能一次性写完所有数据。

如果一次写入没有完成，服务器可以暂时保留剩余数据，并注册 `OP_WRITE` 事件，等通道再次可写时继续发送。

`OP_WRITE` 表示当前连接可以进行写入操作。

### 3.4.8 为什么 NIO 能提高并发处理能力？

BIO 和 NIO 最大的区别之一，在于线程如何等待连接中的数据。

**BIO：通常一个连接对应一个线程**

```text
客户端 A ------> 线程 A（等待 A 的数据）

客户端 B ------> 线程 B（等待 B 的数据）

客户端 C ------> 线程 C（等待 C 的数据）

客户端 D ------> 线程 D（等待 D 的数据）
```

**即使客户端暂时没有发送数据，对应线程也可能一直阻塞等待。**

**NIO：一个线程可以管理多个连接**

```text
客户端 A -------\
客户端 B --------\
客户端 C ---------> Selector
客户端 D --------/      |
                        v
                   一个工作线程
                        |
                        v
                   获取就绪事件
                        |
                  +-----+-----+
                  |           |
                  v           v
              处理客户端 A  处理客户端 C
                  |           |
                  v           v
               读取数据     读取数据
```

**NIO 通过 Selector 监控多个连接**，只有连接出现感兴趣的就绪事件时，工作线程才处理对应的 I/O 操作。

这样就不需要为每个客户端连接都安排一个线程一直等待，从而**减少线程资源消耗**，提高服务器处理大量连接的能力。

**注意：**

1. 一个线程在同一时刻仍然只能执行一段代码，处理 A 和 C 的操作通常是依次执行的，并不意味着一个线程能同时执行多个业务任务。
    
2. 如果业务处理涉及耗时的数据库查询或远程 RPC，通常会交给业务线程池处理，避免阻塞负责网络 I/O 的线程。
    
3. NIO 的非阻塞特性主要体现在 Channel 的 I/O 操作上。`Selector.select()` 本身通常会阻塞等待就绪事件，两者并不矛盾。
    

**总结：NIO 通过 Selector 让少量线程管理多个客户端连接，不需要为每个连接分配一个线程等待数据，从而减少线程资源消耗，提高服务器同时管理大量连接的能力。这里的并发主要指并发管理连接，不代表一个线程能够同时执行多个任务。**

# 4. 哪些框架使用了 NIO？
## 4.1 Netty

**Netty 是一个基于 Java NIO 的高性能网络通信框架，广泛应用于 RPC、消息通信和网络服务器开发。**

**它对 Java NIO 进行了封装，开发者不需要自己处理复杂的 Selector 循环、连接管理和数据缓冲区等底层细节。**

Netty 的主要特点：

- **高性能**：基于事件驱动模型处理网络 I/O。
    
- **高并发**：少量线程可以管理大量网络连接。
    
- **异步通信**：提供异步操作和 Future 等机制。
    
- **易于扩展**：通过 Handler 链处理网络数据。 

### 4.2 Netty 的核心组件

Netty 中比较重要的组件有：

|组件|作用|
|---|---|
|`EventLoopGroup`|管理一组 EventLoop|
|`EventLoop`|负责执行事件循环，监听和处理 I/O 事件|
|`Channel`|表示一个网络连接|
|`ChannelPipeline`|管理 ChannelHandler 组成的处理链|
|`ChannelHandler`|处理连接、数据读写等网络事件|

它们之间的关系：

```text
       EventLoopGroup
              |
       +------+------+
       |             |
       v             v
    EventLoop     EventLoop
       |             |
       v             v
   多个 Channel   多个 Channel
       |             |
       v             v
   Pipeline      Pipeline
       |             |
       v             v
    Handler       Handler
```

一个 EventLoop 通常由一个线程驱动，可以管理多个 Channel。

每个 Channel 都有自己的 ChannelPipeline，用于组织数据处理逻辑。

### 4.3 Netty 如何处理网络请求？

以 TCP 服务器为例，通常会使用两个 EventLoopGroup：

- **BossGroup**：负责接收客户端连接。
    
- **WorkerGroup**：负责处理已经建立连接的 I/O 事件。
    

执行流程：

```text
        客户端连接
             |
             v
          BossGroup
             |
             v
        接收客户端连接
             |
             v
          WorkerGroup
             |
             v
       处理网络读写事件
             |
             v
       ChannelPipeline
             |
             v
        ChannelHandler
             |
             v
          业务处理
```

其中：

1. BossGroup 接收新的客户端连接。
    
2. 将建立的连接分配给 WorkerGroup 中的某个 EventLoop。
    
3. EventLoop 负责监听该连接的读写事件。
    
4. 当有数据到达时，将数据交给 ChannelPipeline。
    
5. Pipeline 中的 Handler 按照配置的顺序处理数据。
    

例如，一个 Handler 可以负责解码，另一个 Handler 可以负责业务处理，还有一个 Handler 可以负责编码。

这样就将网络通信和具体业务逻辑进行了拆分。

### 4.4 Netty 使用的是 NIO 还是 epoll？

**Netty 不仅封装了网络通信的通用操作，还允许开发者选择不同的底层网络 I/O 实现。但是对于使用 Netty 开发业务的程序员来说，通常不需要自己实现底层的 NIO 或 epoll 机制，而是使用 Netty 提供的 API 完成网络通信。**

**可以把它分成两层理解：**

- **Netty 框架层：提供统一的编程接口，让开发者管理连接、接收数据、发送数据。**
    
- **底层 I/O 实现层：真正负责监控网络连接、处理读写事件，可以选择 Java NIO，也可以选择 Linux epoll。**

常见的有：

| 实现    | 说明                               |
| ----- | -------------------------------- |
| NIO   | 使用 Java NIO 的 Channel 和 Selector |
| Epoll | 在 Linux 上使用原生 epoll 机制           |

使用 NIO 时：

```java
NioEventLoopGroup group = new NioEventLoopGroup();
```

主要通过 Java NIO 的 Selector 实现 I/O 多路复用。

在 Linux 上，也可以使用 Netty 提供的原生 epoll 传输：

```java
EpollEventLoopGroup group = new EpollEventLoopGroup();
```

它通过 Linux 的 epoll 机制处理 I/O 事件，需要对应的原生依赖。

两者的区别主要在于底层 I/O 多路复用机制的实现不同。

注意：

- NIO 是 Java 提供的 I/O API。
    
- epoll 是 Linux 操作系统提供的 I/O 多路复用机制。
    
- Netty 可以根据运行环境选择不同的底层实现。
    

另外，Netty 的 NIO 和 epoll 实现都主要采用 Reactor 事件处理模型，并不能因为使用了异步 API 或 Future，就认为它一定采用了 Proactor 模型。

## 4.5 使用 Netty 时需要注意什么？

**虽然 Netty 可以高效地处理大量网络连接，但不能在负责 I/O 事件处理的 EventLoop 中执行耗时的阻塞操作。**

例如：
	
```java
@Override
public void channelRead(ChannelHandlerContext ctx, Object msg) {

    // 不推荐：直接执行耗时的数据库查询
    userService.queryUser();

}
```

如果数据库查询耗时较长，就可能导致当前 EventLoop 无法及时处理它所管理的其他连接。

因此，通常应该将耗时业务交给独立的业务线程池执行，处理完成后再将结果交回 Netty 的事件循环。

这样可以避免业务处理阻塞网络 I/O。

## 5.1 核心概念

|概念|作用|
|---|---|
|BIO|同步阻塞 I/O，传统方式通常一个连接对应一个线程|
|NIO|同步非阻塞 I/O，可以通过 Selector 实现 I/O 多路复用|
|AIO|异步非阻塞 I/O，操作完成后通知应用程序|
|Channel|负责数据读写|
|Buffer|存放读写数据|
|Selector|监听多个 Channel 的就绪事件|
|Netty|基于事件驱动模型的高性能网络通信框架|
|EventLoop|负责事件循环和 I/O 事件处理|
|Pipeline|管理网络事件处理链|
|Handler|负责具体的网络事件处理|

## 5.2 面试重点

1. **Java 如何实现网络 I/O 高并发？**  
    通过 NIO 的 I/O 多路复用机制，让少量线程监听和管理大量连接。
    
2. **BIO、NIO、AIO 有什么区别？**  
    重点区分同步与异步、阻塞与非阻塞，以及各自的执行方式。
    
3. **NIO 是如何实现的？**  
    掌握 Channel、Buffer、Selector 三个核心组件及其协作过程。

    因为不需要为每个连接分配一个独立线程持续等待 I/O。
    
5. **哪些框架使用了 NIO？**  
    Netty 是典型代表，掌握 EventLoopGroup、EventLoop、Channel 和 Pipeline 的作用。
    
6. **Netty 为什么不能在 EventLoop 中执行耗时操作？**  
    因为一个 EventLoop 可能管理多个连接，耗时任务会影响其他连接的事件处理。
