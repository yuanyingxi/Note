# 1. 什么是设计模式？

**设计模式是针对软件开发中常见问题总结出来的一套可复用的设计方案。**

它不是具体的代码，而是一种**设计思路**，帮助我们**组织类与对象之间的关系**，使代码更加容易维护、扩展和复用。

例如：

假设一个支付系统支持支付宝、微信和银行卡支付。如果直接使用大量 `if-else` 判断支付方式，随着支付方式增加，代码会越来越复杂。

使用设计模式，可以将不同的支付逻辑拆分成独立的类，让它们遵循统一的接口，从而降低代码之间的耦合。

### 设计模式的分类

经典设计模式通常分为三类：

|分类|作用|常见模式|
|---|---|---|
|创建型模式|解决对象如何创建的问题|单例模式、工厂模式、建造者模式|
|结构型模式|解决类和对象如何组合的问题|代理模式、适配器模式、装饰器模式|
|行为型模式|解决对象之间如何协作和分配职责的问题|策略模式、责任链模式、观察者模式|

本章重点介绍单例模式、代理模式、适配器模式、策略模式和责任链模式。

# 2. 单例模式（Singleton Pattern）
## 2.1 什么是单例模式？

**单例模式是一种创建型设计模式，保证一个类在应用程序中只有一个实例，并提供一个全局访问入口。**

例如，一个应用程序中的配置管理器、线程池管理器等，通常不需要创建多个相同的实例。

单例模式的核心要求：

- **私有构造方法**：禁止外部直接通过 `new` 创建对象。
    
- **静态实例**：使用 `static` 保存唯一实例。
    
- **公共访问方法**：通过静态方法获取实例。

## 2.2 如何使用 volatile 和 synchronized 实现单例模式？

常见实现方式是**双重检查锁定（Double-Checked Locking，DCL）**。

```java
public class Singleton {

    // volatile 防止指令重排序，并保证可见性
    private static volatile Singleton instance;

    // 私有构造方法，禁止外部创建对象
    private Singleton() {}

    public static Singleton getInstance() {

        // 第一次检查：实例不存在时才进入同步代码块
        if (instance == null) {

            synchronized (Singleton.class) {

                // 第二次检查：防止多个线程重复创建实例
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }

        return instance;
    }
}
```

## 2.3 为什么需要 synchronized？

假设有两个线程同时调用 `getInstance()`：

```
线程 A                    线程 B
  |                         |
  v                         v
instance == null         instance == null
  |                         |
  v                         v
进入 synchronized       等待获取锁
  |
  v
创建 Singleton
  |
  v
释放锁
                            |
                            v
                        获取锁
                            |
                            v
                      再次检查 instance
                            |
                            v
                       instance != null
                            |
                            v
                       不再创建对象
```

**`synchronized` 保证同一时刻只有一个线程能够进入同步代码块。**

而第二次检查 `instance == null` 是为了避免线程 A 已经创建对象后，线程 B 获取锁时又重复创建一个对象。

## 2.4 为什么还需要 volatile？

`volatile` 除了保证变量的**可见性**，还可以保证特定情况下的**有序性**，避免指令重排序带来的多线程问题。

### 2.4.1 什么是指令重排序？

指令重排序（Instruction Reordering）是指编译器或处理器在**不改变单线程程序执行结果**的前提下，**调整部分指令的执行顺序，以提高程序执行效率**。

例如：

```java
int a = 10;
int b = 20;
int c = a + b;
```

由于 `a` 和 `b` 之间没有依赖关系，前两条赋值指令可以调整执行顺序，最终计算结果仍然是 `30`。

重排序主要来源于：

- **编译器优化：** 编译器调整指令顺序，减少不必要的操作。
    
- **处理器优化：** CPU 通过指令流水线、乱序执行等机制提高执行效率。
    

注意：重排序通常不会影响单线程程序的正确结果，但在多线程环境中，可能导致其他线程观察到不符合预期的执行顺序。

### 2.4.2 为什么重排序会导致多线程问题？

以创建对象为例：

```java
instance = new User();
```

创建对象大致包含三个步骤：

1. 为对象分配内存。
    
2. 初始化对象。
    
3. 将对象引用赋值给 `instance`。
    

正常执行顺序：

```text
分配内存
   |
   v
初始化对象
   |
   v
赋值给 instance
```

但在没有适当同步约束的情况下，可能发生重排序：

```text
分配内存
   |
   v
赋值给 instance
   |
   v
初始化对象
```

此时可能出现 `instance` 已经不为 `null`，但对象还没有完成初始化的情况。

其他线程读取到非 null 的 `instance` 后，可能直接使用尚未完全初始化的对象，从而读取到字段的默认值。

### 2.4.3 为什么 volatile 可以避免重排序？

使用 `volatile` 修饰变量：

```java
private static volatile User instance;
```

Java 内存模型（JMM）通过 volatile 的读写语义限制相关指令重排序：

- **volatile 写：** 保证此前的普通写操作不会被重排序到 volatile 写操作之后。
    
- **volatile 读：** 保证此后的普通读操作不会被重排序到 volatile 读操作之前。
    

在双重检查锁（DCL）单例模式中，`volatile` 可以避免对象引用的赋值操作提前到对象初始化之前，从而防止其他线程获取到尚未完成初始化的对象。

注意：volatile 并不是禁止所有指令重排序，而是限制可能破坏其内存语义的重排序。

### 2.4.4 volatile 的两个核心作用

|作用|含义|
|---|---|
|可见性|一个线程修改 volatile 变量后，其他线程读取该变量时能够看到最新写入的值|
|有序性|限制特定情况下的指令重排序，保证多线程之间的执行顺序符合预期|

另外，`volatile` **不保证原子性**。

例如：

```java
volatile int count = 0;

count++;
```

`count++` 实际上包含读取、加一、写回三个步骤，多个线程同时执行时仍然可能出现数据竞争。

**一句话记忆：** `volatile` 主要解决共享变量的可见性和特定情况下的有序性问题，但不能保证复合操作的原子性。

## 2.5 为什么需要双重检查？

这里有两次 `instance == null` 判断：

- **第一次检查**：如果对象已经创建，就直接返回，避免每次获取实例都进入同步代码块。
    
- **第二次检查**：进入同步代码块后再次判断，防止多个线程先后获得锁时重复创建对象。
    

因此，双重检查锁定既保证了线程安全，又减少了后续获取实例时的同步开销。

# 3. 代理模式与适配器模式

两者都属于结构型设计模式，通常都会引入一个额外的类来间接使用另一个对象，但它们解决的问题不同。

## 3.1 代理模式（Proxy Pattern）
### 3.1.1 什么是代理模式？

代理模式是一种结构型设计模式。它通过引入一个代理对象，让代理对象代替真实对象对外提供服务。

**核心思想：代理类和真实类实现同一个接口，调用者通过统一接口调用代理对象，由代理对象负责调用真实对象的方法。**

### 3.1.2 代理模式的作用

**代理对象可以在调用真实对象的方法前后，增加一些与核心业务无关的通用操作**，例如：

- 日志记录
    
- 权限校验
    
- 事务管理
    
- 性能监控
    

这样就可以将通用功能与核心业务逻辑分离，避免在每个业务方法中重复编写这些代码。

### 3.1.3 基本结构

```text
             统一接口 UserService
                     |
             +-------+-------+
             |               |
       代理类 Proxy       真实类 Real
             |               |
       额外功能处理         核心业务逻辑
             |
             | 调用真实对象的方法
             v
         Real.login()
```

### 3.1.4 代码示例

```java
// 1. 统一接口
interface UserService {
    void login();
}

// 2. 真实对象：实现核心业务
class RealUserService implements UserService {
    @Override
    public void login() {
        System.out.println("执行登录业务");
    }
}

// 3. 代理对象：增加额外功能
class ProxyUserService implements UserService {

    private final UserService target;

    public ProxyUserService(UserService target) {
        this.target = target;
    }

    @Override
    public void login() {
        System.out.println("记录日志");

        // 调用真实对象的方法
        target.login();

        System.out.println("记录执行结果");
    }
}
```

调用：

```java
UserService service =
    new ProxyUserService(new RealUserService());

service.login();
```

执行顺序：

1. 调用者调用代理对象的 `login()`。
    
2. 代理对象执行额外操作，例如记录日志。
    
3. 代理对象调用真实对象的 `login()`。
    
4. 真实对象执行核心登录业务。
    
5. 真实对象执行完成后，代理对象继续执行后续操作。

### 3.1.5 总结

代理模式的核心就是：

- **统一接口：** 代理类和真实类实现同一个接口，对外提供统一的调用方式。
    
- **代理对象：** 负责额外的通用功能，例如日志、权限校验等。
    
- **真实对象：** 负责具体的核心业务逻辑。
    
- **解耦：** 将通用功能与核心业务分离，避免修改真实对象的业务代码。

注意：代理模式不一定必须通过接口实现，也可以通过继承真实类实现，例如 CGLIB 动态代理。

## 3.2 适配器模式（Adapter Pattern）

**适配器模式的核心是：让原本接口不兼容的类，通过适配器能够按照统一接口被调用。**

可以将它理解为现实生活中的电源转换插头。

例如，某个设备使用的插头和插座接口不匹配，就可以通过适配器进行转换，使两者能够正常连接。

### 3.2.1 基本结构

适配器模式通常包含三个角色：

|角色|作用|
|---|---|
|目标接口（Target）|客户端希望使用的接口|
|被适配者（Adaptee）|已有的接口或类，与目标接口不兼容|
|适配器（Adapter）|负责转换接口，使双方能够协作|

结构：

```text
     客户端
        |
        v
    目标接口
        |
        v
     适配器
        |
        v
   被适配者
        |
        v
    原有功能
```

### 3.2.2 代码示例

假设客户端需要一个统一的播放器接口：

```java
// 客户端需要的目标接口
interface MediaPlayer {
    void play(String file);
}
```

但是，已有的播放器使用了不同的方法：

```java
// 已有的第三方播放器
class OldPlayer {

    public void playMp3(String file) {
        System.out.println("播放音乐：" + file);
    }
}
```

由于 `OldPlayer` 没有实现 `MediaPlayer` 接口，因此不能直接作为 `MediaPlayer` 使用。

这时可以创建一个适配器：

```java
class PlayerAdapter implements MediaPlayer {

    private final OldPlayer oldPlayer;

    public PlayerAdapter(OldPlayer oldPlayer) {
        this.oldPlayer = oldPlayer;
    }

    @Override
    public void play(String file) {
        // 将目标接口的调用转换为已有接口的调用
        oldPlayer.playMp3(file);
    }
}
```

使用：

```java
MediaPlayer player = new PlayerAdapter(new OldPlayer());

player.play("music.mp3");
```

这样，客户端只需要调用统一的 `play()` 方法，适配器负责将其转换为原有的 `playMp3()` 方法。

#### 3.2.3 适配器模式的使用场景

- **兼容第三方接口**：已有第三方类的接口与当前系统不一致，需要进行转换。
    
- **兼容旧系统**：新系统需要使用旧系统的功能，但两者接口不兼容。
    
- **统一不同实现**：将不同来源、不同接口的功能包装成统一的接口。
    

例如，Java 中的 `InputStreamReader` 就体现了适配器思想，它可以将字节输入流 `InputStream` 适配为字符读取器 `Reader`。

## 3.3 代理模式与适配器模式的区别

| 对比维度    | 代理模式                  | 适配器模式                  |
| ------- | --------------------- | ---------------------- |
| 核心目的    | **控制**对真实对象的**访问**    | **转换接口**，使不兼容的接口能够协作   |
| 主要解决的问题 | 如何在访问对象时**增加控制或额外功能** | 如何让原本**不兼容**的类**一起工作** |
| 接口关系    | 代理对象通常与真实对象实现相同接口     | 适配器实现客户端需要的目标接口        |
| 是否调用原对象 | 通常会委托真实对象执行           | 通常会调用被适配者完成实际功能        |
| 典型场景    | 日志、权限、事务、远程调用         | 第三方接口兼容、旧系统改造          |

**记忆重点：**

- 代理模式：接口通常不变，重点是控制访问、增加功能。
    
- 适配器模式：接口发生转换，重点是解决接口不兼容问题。
    

# 4. 责任链模式（Chain of Responsibility Pattern）
## 4.1 什么是责任链模式？

**责任链模式就是把多个独立的处理逻辑串联起来，让请求按照设定的顺序依次经过这些处理节点，而请求入口不需要关心每个节点的具体实现**

**其核心是将请求的发送者和具体的处理者解耦，避免请求发起方直接依赖所有处理逻辑。**

例如，一个 HTTP 请求到达服务器后，可能需要依次进行：

1. 登录状态校验。
    
2. Token 有效性校验。
    
3. 用户权限校验。
    
4. 请求频率限制。
    

这些校验逻辑各自独立，可以封装为不同的处理节点。

## 4.2 责任链模式的执行流程

```text
       HTTP 请求
           |
           v
       登录校验
           |
      +----+----+
      |         |
    失败       成功
      |         |
      v         v
    拒绝      权限校验
                |
           +----+----+
           |         |
          失败       成功
           |         |
           v         v
          拒绝     频率限制
                      |
                 +----+----+
                 |         |
                失败       成功
                 |         |
                 v         v
                拒绝     执行业务
```

每个处理节点只需要关注自己的职责：

- 校验通过：交给下一个节点。
    
- 校验失败：可以直接终止处理，并返回相应结果。
    

这样，请求发起方只需要调用责任链的第一个节点，不需要关心后面具体有哪些处理者。

## 4.3 如何实现责任链模式？

通常需要定义一个处理者接口或抽象类，并让每个处理节点保存下一个节点的引用。

下面通过登录校验、权限校验和频率限制三个节点演示。

### 4.3.1 定义请求对象

```java
class Request {

    boolean login;
    boolean hasPermission;
    boolean withinLimit;

    public Request(boolean login,
                   boolean hasPermission,
                   boolean withinLimit) {
        this.login = login;
        this.hasPermission = hasPermission;
        this.withinLimit = withinLimit;
    }
}
```

### 4.3.2 定义抽象处理者

```java
abstract class Handler {

    protected Handler next;

    // 设置下一个处理节点
    public Handler setNext(Handler next) {
        this.next = next;
        return next;
    }

    // 处理请求
    public boolean handle(Request request) {

        // 当前节点校验失败，终止链路
        if (!check(request)) {
            return false;
        }

        // 当前节点校验通过，交给下一个节点
        return next == null || next.handle(request);
    }

    // 由具体处理者实现自己的校验逻辑
    protected abstract boolean check(Request request);
}
```

### 4.3.3 实现具体处理者

登录校验：

```java
class LoginHandler extends Handler {

    @Override
    protected boolean check(Request request) {
        System.out.println("执行登录校验");
        return request.login;
    }
}
```

权限校验：

```java
class PermissionHandler extends Handler {

    @Override
    protected boolean check(Request request) {
        System.out.println("执行权限校验");
        return request.hasPermission;
    }
}
```

频率限制：

```java
class RateLimitHandler extends Handler {

    @Override
    protected boolean check(Request request) {
        System.out.println("执行频率限制");
        return request.withinLimit;
    }
}
```

### 4.3.4 组装责任链并执行

```java
Handler login = new LoginHandler();
Handler permission = new PermissionHandler();
Handler rateLimit = new RateLimitHandler();

// 组装处理链
login.setNext(permission).setNext(rateLimit);

// 发起请求
Request request = new Request(true, true, true);

// 从第一个节点开始执行
boolean result = login.handle(request);
```

执行顺序：

```text
登录校验
    |
    v
权限校验
    |
    v
频率限制
    |
    v
返回 true
```

如果登录校验失败，后续的权限校验和频率限制就不会继续执行。

## 4.4 责任链模式的使用场景

- **请求拦截与校验**：登录校验、权限校验、参数校验、限流等。
    
- **审批流程**：员工请假需要依次经过直属经理、部门总监等审批。
    
- **过滤器链**：多个过滤器按照顺序对请求进行处理。
    
- **日志处理**：不同处理节点分别处理不同级别或类型的日志。
    

例如，Spring MVC 中的拦截器机制、Servlet Filter 链都体现了责任链的设计思想。

需要注意：责任链不一定只能由一个节点处理请求。有些实现中，每个节点处理完自己的部分后，仍然会继续传递请求。例如过滤器链通常需要多个节点依次执行。

# 5. 策略模式（Strategy Pattern）
## 5.1 什么是策略模式？

**策略模式是一种行为型设计模式，它将一系列可以相互替换的算法或业务行为分别封装起来，并通过统一接口进行调用（本质上就是利用面向对象中的多态来实现的）。**

简单来说，就是把不同的处理方式独立出来，在运行时根据实际情况选择其中一种。

例如，一个电商系统支持多种支付方式：

- 支付宝支付。
    
- 微信支付。
    
- 银行卡支付。
    

这些支付方式的具体实现不同，但对于上层业务来说，都属于支付操作。

如果直接使用大量 `if-else` 判断支付方式，后续新增支付方式时，就需要不断修改原有业务代码。

使用策略模式，可以将每种支付方式封装为独立的策略类。

### 5.2 策略模式的基本结构

策略模式通常包含三个角色：

|角色|作用|
|---|---|
|抽象策略（Strategy）|定义统一的行为接口|
|具体策略（Concrete Strategy）|实现不同的业务处理方式|
|上下文（Context）|持有策略对象，并调用策略执行具体业务|

结构：

```text
         上下文
           |
           v
       策略接口
           |
      +----+----+
      |         |
      v         v
  支付宝策略   微信策略
      |         |
      v         v
  支付宝支付   微信支付
```

## 5.3 如何实现策略模式？
### 5.3.1 定义策略接口

```java
public interface PaymentStrategy {
    void pay(double amount);
}
```

所有支付策略都实现这个统一接口。

### 5.3.2 实现具体策略

支付宝支付：

```java

public class AliPayStrategy implements PaymentStrategy {

    @Override

        System.out.println("支付宝支付：" + amount);
    }
```

微信支付：

### 5.3.3 定义上下文

```java
@Component
public class PaymentContext {

    // Spring 自动收集所有 PaymentStrategy 实现类
    // Key 是 Bean 名称，Value 是对应的策略对象
    @Autowired
    private Map<String, PaymentStrategy> strategyMap;

    public void execute(String type, double amount) {

        // 根据支付类型获取对应策略
        PaymentStrategy strategy = strategyMap.get(type + "Strategy");

        if (strategy == null) {
            throw new RuntimeException("不支持的支付方式");
        }

        // 执行具体支付逻辑
        strategy.pay(amount);
    }
}
```

### 5.3.4 使用策略

```java
@Service
public class OrderService {

    @Autowired
    private PaymentContext paymentContext;

    public void payOrder(String payType, double amount) {

        // 根据用户传入的支付方式，选择对应策略
        paymentContext.execute(payType, amount);
    }
}
```

```text
Spring 容器创建策略对象
          |
          v
自动收集所有策略对象到 Map
          |
          v
OrderService 调用 PaymentContext
          |
          v
根据支付类型从 Map 获取策略
          |
```

# 6. 策略模式与责任链模式的区别

两者都属于行为型设计模式，经常用于解决复杂的 `if-else` 或 `switch-case` 问题，但它们的执行方式不同。

## 6.1 核心区别

|对比维度|策略模式|责任链模式|
|---|---|---|
|核心目的|从多种策略中选择一种执行|将请求交给多个处理节点依次处理|
|执行方式|通常选择一个策略执行|请求沿着处理链传递|
|对象关系|多种可替换的策略|多个相互连接的处理者|
|主要解决的问题|不同场景下采用不同的处理算法|一个请求需要经过多个处理环节|
|典型场景|支付方式、优惠计算|登录校验、权限校验、审批流程|

## 6.2 用一个例子理解两者的区别

假设开发一个电商系统。

**策略模式：选择一种支付方式。**

用户可以选择支付宝或微信支付：

```text
       用户选择支付方式
               |
          +----+----+
          |         |
          v         v
       支付宝      微信
          |         |
          v         v
       执行支付    执行支付
```

这里需要根据用户的选择，从多种支付策略中选择一种执行。

**责任链模式：依次进行请求校验。**

用户提交支付请求后，需要检查登录状态、用户权限和请求频率：

```text
       支付请求
           |
           v
       登录校验
           |
           v
       权限校验
           |
           v
       频率限制
           |
           v
       执行支付
```

这里不是选择其中一个校验，而是需要按照流程依次经过多个处理节点。

因此，两者最重要的区别是：

- **策略模式：多个方案中选一个。**
    
- **责任链模式：多个处理节点按流程传递请求。**
    

# 7. 本章总结

| 设计模式  | 类型  | 核心思想             | 典型场景           |
| ----- | --- | ---------------- | -------------- |
| 单例模式  | 创建型 | 保证一个类只有一个实例      | 配置管理器、线程池管理器   |
| 代理模式  | 结构型 | 控制对象访问，增加额外处理    | 日志、事务、权限控制     |
| 适配器模式 | 结构型 | 转换接口，使不兼容的类能够协作  | 第三方接口兼容、旧系统改造  |
| 策略模式  | 行为型 | 多种可替换的策略中选择一种    | 支付方式、优惠计算      |
| 责任链模式 | 行为型 | 多个处理者连接成链，依次处理请求 | 请求校验、审批流程、过滤器链 |

**面试重点：**

1. 单例模式：掌握双重检查锁定，以及 `volatile` 和 `synchronized` 各自的作用。
    
2. 代理模式与适配器模式：重点理解控制对象访问和转换接口之间的区别。
    
3. 策略模式：重点理解如何通过统一接口封装不同的业务实现，减少复杂的条件判断。
    
4. 责任链模式：重点理解处理节点的组织方式，以及请求如何在节点之间传递。
    
5. 策略模式与责任链模式：记住一个是选择一种方案，另一个是将请求交给多个节点处理。
