# 1. 实习项目全貌：我的具体任务与实际开发流程

我在珠海金智维的实习时间只有一个月，因此这段经历更适合定位为：**在已有的 AI 数字员工平台后端项目中，参与接口功能完善、模型调用结果处理、任务数据读写和基础接口测试**。我不是从零搭建整个平台，也没有独立开发 RPA 执行器。我的工作主要是在现有 Spring Boot 项目中理解已有代码、补充或修改业务逻辑、通过 Postman 验证接口，再把完成的代码上传到公司内网代码平台。

## 1.1 项目背景：后端需要把自然语言指令整理成系统能处理的任务

平台结合大语言模型（LLM）和 RPA 等自动化能力。用户提交**自然语言指令**后，后端通过 **HTTP 请求调用模型服务**，取得**模型返回的意图和相关内容**，再**由 Java 业务代码**处理结果，并维护指令、任务步骤和执行日志等业务数据。

举例来说，用户提交一条“查询订单”的指令，后端需要做的不是简单地把文本转发给模型，而是：**接收请求、调用模型、读取响应、提取意图、处理无法识别或解析失败的情况**，并将处理结果按业务要求返回或保存。只有模型响应经过后端处理后，才能决定是否进入相应业务流程。

我的工作主要集中在**指令进入后端之后的接口处理和模型结果处理**，而不是 RPA 如何点击网页、如何操作第三方应用等执行器内部实现。

## 1.2 我的具体实习任务

| 实习任务        | 具体工作                                                                                                |
| ----------- | --------------------------------------------------------------------------------------------------- |
| 参与后端接口开发与完善 | 参与**指令提交、指令列表与分页查询、状态查询、任务步骤及相关记录查询**等接口的开发与完善；在指令处理流程中，根据模型返回的意图和操作信息生成自然语言步骤描述，并配合相关业务逻辑处理任务步骤记录。 |

## 1.3 一项功能是怎样从修改代码做到验证完成的

```text
在已有项目中接到一个接口或业务处理任务
        ↓
找到对应的 Controller，了解接口入参和返回值
        ↓
跟进 Service，找到实际的业务处理逻辑
        ↓
查看模型调用、意图处理和 Mapper 数据操作
        ↓
修改或补充需要的 Java 代码
        ↓
启动后端项目，确认服务正常运行
        ↓
使用 Postman 发送 HTTP 请求
        ↓
检查状态码、返回 JSON 和后端控制台信息
        ↓
需要时检查数据库中的指令/任务/失败记录
        ↓
调整问题并重新发送请求验证
        ↓
将修改完成的代码上传到公司内网代码平台
```

对于一个月的实习来说，这样的工作方式很合理：在已有工程中接手明确的小功能，理解现有代码后完成局部修改，再用接口请求验证，而不是独立设计一整套微服务架构或执行器。

### 实际操作时，各步分别做什么

1. **先定位接口。** 在 Controller 中找到对应的请求映射，弄清楚它接收什么参数、调用哪个 Service、最终返回什么结果。
2. **沿调用链看业务。** 进入 Service，查看它何时调用模型、如何处理模型响应、何时调用 Mapper 读写数据库。遇到模型相关问题时，再进入负责 HTTP 请求的封装代码。
3. **完成局部修改。** 例如补充一种意图的处理分支、调整返回内容、增加调用异常处理，或修正失败解析时的记录逻辑。修改范围围绕现有业务，不需要重写整个模块。
4. **启动项目并测试。** 后端正常启动后，在 Postman 中填写接口地址、请求方法和 JSON 请求体，发送请求并观察响应。
5. **对照结果排查。** 如果结果不符合预期，就看 Postman 响应、后端控制台输出，以及相关数据库记录，判断问题出在请求参数、业务分支、模型响应解析还是数据读写。
6. **上传代码。** 完成修改和基础测试后，将代码上传到公司内网的代码托管平台。你记得的平台类似 GitHub，因此可以把它理解为公司内部用于存放项目代码的服务；这里不额外假设你使用了 Git 命令、分支合并或代码评审流程。

## 1.4 两层 HTTP 请求：Postman 测后端，Java 代码调模型

这部分是我理解项目时最容易混淆的地方。一次测试可能涉及两条不同的 HTTP 请求链路。

```text
第一层：人工测试后端接口
Postman
   │ 发送指令 JSON
   ▼
Spring Boot Controller
   ▼
Service 业务逻辑

第二层：后端在业务处理中调用模型
Service / 模型调用封装
   │ Java 代码通过 HTTP 发送模型请求
   ▼
大模型服务
   │ 返回模型响应
   ▼
Java 代码接收并处理响应
   ▼
意图处理 / 异常处理 / 数据读写
   ▼
Controller 将后端处理结果返回给 Postman
```

**Postman 并不是替 Java 代码调用模型。** Postman 负责模拟前端或其他调用方访问我开发的后端接口；当后端业务执行到模型调用环节时，才由 Java 代码向模型服务发起另一个 HTTP 请求。Postman 展示的是后端最终返回的响应，它可能是处理后的意图结果，也可能是后端整理过的失败信息。

## 1.5 具体任务一：参与完善 10 余个后端接口

我的接口工作主要围绕**自然语言指令处理、指令记录查询和任务执行信息查询**展开。重点不是从零设计整套 API，而是在已有 Spring Boot 项目中理解接口入口和业务调用关系，补充或调整 Java 处理逻辑，再用 Postman 验证请求和响应。

下面把最有代表性的几类接口展开。**路由、参数名和 JSON 结构均为示例，不代表项目中的真实定义。** 复盘时应重点理解每类接口的用途、后端调用链，以及如何验证结果。

### 1.5.1 指令提交与意图处理接口

这是最值得重点理解的一类接口，因为它连接了用户输入、模型调用和后续的指令处理逻辑。

**示例接口定义**

| 项目   | 示例                     | 说明                      |
| ---- | ---------------------- | ----------------------- |
| 请求方法 | `POST`                 | 通常用于提交一条指令或发起一次处理       |
| 路由   | `/instructions/submit` | 请求路径                    |
| 请求内容 | 自然语言指令                 | 由调用方通过 JSON Body 传入     |
| 主要入口 | `Controller` 方法        | 接收并绑定请求参数，再调用 `Service` |

请求 Body 可以用下面的结构示意：

```json
{
  "instruction": "查询指定订单的状态"
}
```

`instruction` 只是示例字段名，实际项目可能使用不同字段，或者还要求其他参数。

**请求进入后端后，大致经过以下步骤：**

1. Controller 接收 HTTP 请求，将 JSON 请求体绑定到 Java 请求对象，并进行必要的基础校验。
    
2. Controller 调用 Service，由 Service 组织后续业务处理。
    
3. 业务逻辑调用模型服务，Java 代码通过 HTTP 取得模型响应。
    
4. 后端解析模型返回内容，提取意图等字段，并判断意图是否属于系统支持的类型。
    
5. 根据处理结果返回响应；如果项目设计要求保存指令记录或解析失败信息，则在相应分支执行数据库写入。
    

这里需要区分三个层次：**模型调用成功、响应内容能够解析、意图属于系统支持的类型**并不是同一件事。模型服务正常返回，并不保证返回内容一定符合后端预期；即使 JSON 可以解析，里面的意图也可能为空或不受支持。

例如，Postman 的响应可能表现为意图字段有值或为空。下面只是示意，不代表真实响应格式：

```json
{
  "intent": "query_order"
}
```

无法识别时，也可能出现 `null`、空字符串或其他项目约定的失败结果。不能仅凭这个示例断定项目一定返回上述字段和结构。

**Postman 主要验证什么？**

- 提交一条含义清楚、预期可识别的指令，检查请求是否被接收，响应中的意图结果是否合理。
    
- 提交一条系统无法识别或不在支持范围内的指令，观察意图为空或未识别时的处理结果。
    
- 检查请求格式错误、必填内容缺失等情况是否得到合理处理。
    
- 结合后端控制台日志，区分模型调用异常与模型响应解析失败；如果该业务分支会写入数据库，再检查相关记录是否符合预期。
    

这部分可以概括为：**我参与完善了指令处理相关后端逻辑，并用 Postman 验证自然语言指令进入后端后，模型响应及意图字段是否按预期处理。**

### 1.5.2 指令列表与分页查询接口

这类接口用于查看系统中已保存的指令记录，避免每次都只能通过提交接口观察单条指令的结果。

**示例接口定义**

|项目|示例|说明|
|---|---|---|
|请求方法|`GET`|查询已有数据，通常不修改记录|
|路由|`/instructions/page`|示例路径|
|请求参数|`pageNum`、`pageSize`，以及可选的筛选条件|通常通过 URL 查询参数传递|
|主要数据来源|指令记录表|通过 Service 调用 Mapper 查询 MySQL|

例如，可以用类似下面的请求进行测试：

```
GET /instructions/page?pageNum=1&pageSize=10
```

如果接口支持按状态筛选，可能还会有类似 `status` 的参数；是否存在该筛选项要以实际代码为准。

**后端处理过程：**

1. Controller 接收页码、每页条数和筛选条件。
    
2. Service 对分页参数和查询条件进行组织。
    
3. Mapper 根据条件查询数据库，并返回当前页记录及分页信息。
    
4. Controller 将查询结果封装成接口响应。
    

**Postman 验证方式：**

- 调整页码，确认返回的数据范围发生变化，而不是每次都返回同一页。
    
- 调整每页条数，观察当前页记录数量是否符合参数约定。
    
- 在存在筛选条件时，更换条件并比较返回记录。
    
- 查询没有匹配记录的条件，检查接口能否正常返回空列表或项目约定的空结果，而不是出现非预期异常。
    

理解这类接口时，要重点看参数如何传到 Service、分页查询如何交给 Mapper，以及响应中的记录列表和总数等信息从哪里来。具体响应字段需以项目实现为准。

### 1.5.3 指令或任务状态查询接口

**状态查询： 给我指令 ID `123`，告诉我它当前是成功、失败还是执行中。**

这类接口用于根据指令或任务标识查看当前处理状态。它和列表查询的区别是：列表查询返回多条记录，而状态查询通常针对一个具体对象。

**示例接口定义**

| 项目     | 示例                          | 说明                    |
| ------ | --------------------------- | --------------------- |
| 请求方法   | `GET`                       | 查询单条记录的状态             |
| 路由     | `/instructions/{id}/status` | `{id}` 表示待查询的标识，是示例写法 |
| 请求参数   | 指令 ID 或任务 ID                | 具体使用哪一种 ID 由实际接口决定    |
| 主要数据来源 | 指令记录或任务步骤数据                 | 由后端实际状态管理方式决定         |

例如，假设要查询 ID 为 `123` 的指令，可以用类似下面的请求：

```
GET /instructions/123/status
```

后端会读取路径中的标识，交给 Service 查询对应记录，再返回状态信息。状态字段可能是待处理、处理中、成功或失败等，但实际状态枚举和字段名必须以项目代码为准。

**Postman 验证方式：**

- 使用一个已存在的指令或任务标识发起查询。
    
- 将接口返回的状态与数据库中对应记录的状态进行比对。
    
- 使用不存在的标识，检查接口对“记录不存在”的处理方式。
    
- 如果状态会随处理流程更新，可以在处理前后分别查询，确认接口读到的是当前记录状态，而不是固定值或错误记录的状态。
    

这类接口的重点不只是“能返回一个状态字符串”，而是确认标识传递正确、Service 查到了正确的数据，以及响应内容与实际记录一致。

### 1.5.4 指令执行历史或相关记录查询接口

**历史查询： 给我指令 ID `123`，告诉我它有哪些执行步骤、每一步的结果或相关日志。**

这类接口用于查看某条指令关联的任务步骤、执行日志或历史记录，方便排查执行过程。它与状态查询不同：状态查询关注“现在是什么状态”，历史查询关注“有哪些相关记录”。

**示例接口定义**

|项目|示例|说明|
|---|---|---|
|请求方法|`GET`|查询已有的执行相关数据|
|路由|`/instructions/{id}/history`|示例路径，实际路由以项目为准|
|请求参数|指令 ID 或任务 ID|用于定位需要查看的记录|
|可能涉及的数据|指令记录、任务步骤、执行日志|具体查询哪些表取决于项目实现|

**后端处理过程：**

1. Controller 接收目标指令或任务的标识。
    
2. Service 组织查询逻辑，并调用对应 Mapper。
    
3. Mapper 查询与该标识相关的记录。
    
4. 后端将记录列表或项目规定的结果结构返回给调用方。
    

**Postman 验证方式：**

- 使用一个已有的指令或任务标识查询历史记录。
    
- 检查返回记录是否确实属于该指令或任务，避免关联条件错误导致返回其他数据。
    
- 对照数据库中的相关记录，核对返回条数和关键字段。
    
- 查询没有关联记录的对象，观察空结果处理是否符合接口约定。
    

如果项目确实将任务步骤和执行日志分开存储，就需要关注它们通过什么标识关联；但不要在没有看过实际代码的情况下，断定某个接口一定同时查询了这几张表。

### 1.5.5 这几类接口在代码中如何串起来？

从一次 HTTP 请求来看，典型调用关系可以概括为：

```
Postman
  ↓ HTTP 请求
Controller：接收参数、选择业务入口
  ↓ 调用 Java 方法
Service：组织业务处理
  ├─ 指令处理：调用模型、解析意图
  └─ 查询处理：组织查询条件、调用 Mapper
        ↓
Mapper / MyBatis-Plus：访问 MySQL
        ↓
Service 整理结果
  ↓
Controller 返回 JSON 响应
  ↓
Postman 检查状态码与响应内容
```

这张图是常见调用结构的概括。不是每个接口都会调用模型，也不是每个接口都会访问数据库：指令处理接口可能涉及模型服务和数据写入，列表、状态和历史查询接口则主要读取已有数据。

## 1.6 具体任务二：封装模型调用，获取 HTTP 响应

后端需要把用户指令发送给模型服务，再接收模型返回内容。我的任务是参与**模型调用逻辑的封装，并考虑超时、调用异常等情况**。

### 1.6.1 一次模型调用的具体步骤

在这个项目中，需要区分 **接口测试请求** 和 **后端调用模型的请求**。Postman 是测试工具，Java 后端才是实际执行模型调用的程序。

以测试自然语言指令处理接口为例，整个过程如下：

1. **使用 Postman 发送测试请求。** 开发者在 **Postman** 中填写**后端接口地址**、**请求方法**和 **JSON 请求体**，例如提交一条需要识别的自然语言指令。Postman 将请求发送给正在运行的 Spring Boot 后端。
    
2. **Controller 接收请求。** 后端接收到 HTTP 请求后，将**请求参数绑定到 Java 对象**，并调用 Service 处理业务逻辑。
    
3. **Java 后端组装模型请求。** Service 或对应的模型调用组件根据项目约定，组织需要发送给模型服务的**指令内容、请求头和其他必要参数**。
    
4. **Java 后端通过 HTTP 调用模型服务。** **后端**使用项目中的 **HTTP 客户端发送请求**，并等待**模型服务返回响应**。这是后端发起的另一次 HTTP 请求，与 Postman 发给后端的请求不同。
    
5. **接收并处理模型响应。** Java 代码取得模型服务返回的内容后，将其交给后续业务逻辑，尝试**解析意图及相关字段**。如果出现超时、连接失败、响应格式异常等情况，则根据项目已有的异常处理逻辑进行处理。
    
6. **后端向 Postman 返回结果。** 后端完成相应的业务处理后，将结果封装为 **HTTP 响应**返回给 **Postman**。开发者通过查看状态码、响应 JSON 和后端日志，判断接口是否按预期工作。
    

整个调用关系可以概括为：

```
开发者
  ↓ 在 Postman 中发送测试请求
Spring Boot 后端
  ↓ Controller 接收请求
  ↓ Service 处理业务
Java 模型调用组件
  ↓ 发送 HTTP 请求
模型服务
  ↓ 返回模型响应
Java 后端解析并处理结果
  ↓ 返回 HTTP 响应
Postman 展示结果
```

**需要记住的关键点：**

- Postman → 后端：用于测试后端接口。
    
- Java 后端 → 模型服务：用于在业务流程中实际调用模型。
    
- 模型服务成功返回，不代表返回内容一定能被正确解析，也不代表识别出的意图一定属于系统支持的类型。
    

以上是典型的调用流程。具体项目中由哪个类调用模型、使用什么 HTTP 客户端，以及异常如何处理，需要以实际代码为准。

### 1.6.2 为什么要处理超时和调用异常

模型服务是通过 HTTP 访问的外部服务，**网络和服务状态都可能影响请求**。若代码只考虑正常响应，一旦请求超时或调用失败，就可能抛出异常、返回不完整结果，甚至让接口无法按预期结束。因此需要在模型调用附近处理异常，并让业务层能够区分“没有成功取得模型响应”和“已经取得响应，但内容无法解析”。

这两种失败发生的阶段不同：

- **调用失败：** Java **没有正常取得模型响应**，例如**请求超时**或**连接异常**。
- **解析失败：** Java 已经**收到响应**，但响应内容**不符合**后端预期的**格式**，**无法正常提取意图**等字段。

## 1.7 具体任务三：通过 Postman 测试指令与意图处理结果

用 **Postman** 做过简单测试：**向后端接口传递指令**相关 **JSON**，**观察响应中意图字段**的表现。模型能够**识别**或**按约定返回结果**时，意图字段会**有值**；模型**无法识别**时，意图字段可能为**空**，后端再根据这个结果走相应的处理分支。

一次基础测试可以按下面的方式理解。

### 第一步：向后端提交指令

在 Postman 中选择接口要求的 HTTP 方法，填写**后端地址**，并在 **Body 中选择 JSON 格式**，输入接口需要的请求字段。例如，下面只是展示“请求里包含自然语言指令”的结构示意，字段名不代表项目真实字段：

```json
{
  "instruction": "查询指定订单的状态"
}
```

点击 Send 后，Postman 将请求发送给 Spring Boot 后端。Controller 接收请求并调用 Service，Service 再根据业务流程调用模型。

### 第二步：观察后端返回的 JSON

模型响应被 Java 代码接收并处理后，后端会把处理结果返回给 Postman。为了说明“意图有值”的含义，可以用下面的示意结果理解：

```json
{
  "intent": "query_order"
}
```

如果模型无法识别指令，后端可能返回意图为空的结果，例如：

```json
{
  "intent": null
}
```

这两段 JSON 仅用于说明测试现象。实际项目的字段名、响应层级，以及空值究竟是 `null`、空字符串还是缺少字段，应以接口真实约定为准。复盘时应把重点放在：**发送了什么指令、接口返回了什么、意图结果是否符合预期、后端如何处理无法识别的情况。**

### 第三步：检查后端的处理结果

不能只看 Postman 中有没有返回 JSON，还要结合后端逻辑判断：

- 意图有值时，代码是否成功提取该字段，并将其对应到系统支持的意图类型；
- 意图为空或无法识别时，代码是否进入未识别结果的处理分支；
- 响应格式错误时，是否进入解析失败处理，而不是继续按正常任务处理；
- 如果该次处理需要写入指令或失败记录，数据库中的记录是否与接口结果相符。

对于一个月的实习，使用 Postman 对正常指令和无法识别的指令做基本验证，是合理且有价值的测试方式。

## 1.8 具体任务四：将模型响应转换为规范的步骤描述

模型返回的响应可能包含意图、操作及相关参数等结构化信息。为了让这些信息更容易被后续业务使用或被开发者查看，可以根据预先定义的规则，将不同的意图和操作映射为相应的自然语言描述。

例如，假设模型返回的内容包含 `open_system` 意图和 `launch` 操作，脚本就可以根据已有映射规则，生成类似“打开指定系统”的步骤描述。具体的意图名称、操作字段和描述模板以项目实际定义为准。

**处理流程可以概括为：**

```
模型返回结构化响应
        ↓
解析意图、操作及相关参数
        ↓
根据预定义规则匹配对应描述
        ↓
拼接成规范的自然语言步骤
        ↓
交给后续业务处理
        ↓
如果项目将其用于任务步骤记录，
则由相应逻辑保存到数据库
```

这项工作的重点是根据既定规则处理模型响应，将结构化信息转换为统一的自然语言描述，而不是重新训练模型或自行定义所有业务意图。

需要注意，生成步骤描述与保存步骤历史是两个不同环节。脚本可能只负责生成文本，后续再由 Service 或其他业务逻辑保存相关记录。只有确认实际代码包含相应的数据写入逻辑，才能进一步将数据库持久化归为这项工作的内容。

目前还需要根据脚本的实际输出去向，确认这些描述究竟用于任务步骤记录、执行历史展示，还是其他业务处理。

## 1.9 指令记录、任务步骤和执行日志：我处理的业务数据

这三个概念分别对应不同粒度的业务信息：

| 数据类别 | 记录的内容 | 在接口流程中的作用 |
|---|---|---|
| 指令记录 | 一次用户指令的总体信息，例如原始指令、识别结果或整体状态等（具体字段以项目为准） | 用于定位和查询这次指令的处理情况 |
| 任务步骤 | 与指令相关的步骤信息及其处理状态（是否包含多步骤、具体字段以项目为准） | 记录任务处理过程中的步骤信息 |
| 执行日志 | 任务处理或执行过程中需要保留的记录；失败解析记录也应按项目设计归入相应记录机制 | 便于查询过程信息、排查异常或后续复核 |

我的工作重点是围绕这些已有业务数据完成接口所需的查询、保存或更新，而不是独立设计整套任务调度系统。实际操作中，可以把它理解为：接口接到请求后，Service 根据业务流程调用 Mapper；Mapper 通过 MyBatis-Plus 与 MySQL 交互；操作完成后，接口将结果返回给 Postman 或调用方。

还要区分数据库中的业务记录和应用控制台/日志文件中的运行日志：数据库记录通常用于业务查询和跟踪；运行日志则主要帮助开发者排查程序运行问题。

# 2. 一次 HTTP 请求如何经过 Spring Boot 后端
## 2.1 请求链路

一个常见的 Spring MVC 请求大致经过以下步骤：

1. Web 容器接收 HTTP 请求；
2. Spring MVC 的 `DispatcherServlet` 协调请求分发；
3. 根据请求路径和 HTTP 方法找到匹配的 Controller；
4. 将查询参数、路径参数或 JSON 请求体绑定到 Java 参数/对象；
5. Controller 调用 Service；
6. Service 执行业务判断，并按需要调用 Mapper、模型客户端或缓存；
7. 返回对象由 Spring 的响应处理机制序列化为 JSON；
8. 客户端收到 HTTP 状态码和响应体。

不必一开始记住 Spring MVC 的所有内部类。先能沿着代码说明：**请求从哪里进入、参数在哪里变成 Java 对象、业务在哪里执行、数据在哪里读写、返回值如何交给前端。**

## 2.2 Controller、Service、Mapper 分别负责什么

| 层                   | 主要职责                       | 不适合塞进去的内容                  |
| ------------------- | -------------------------- | -------------------------- |
| Controller          | 接收 HTTP 参数、基础校验、调用业务层、组织响应 | 大段业务流程、复杂 SQL、模型响应解析细节     |
| Service             | 组织业务规则、编排调用、控制必要的事务边界      | 与业务无关的 HTTP 协议细节、到处重复的 SQL |
| Mapper              | 对数据库执行查询和更新                | 大量业务决策、模型 API 调用           |
| Entity / DO         | 表示数据库记录                    | 直接承载完整 HTTP 请求/响应协议        |
| Request DTO         | 表示前端传入的数据结构                | 未校验便直接作为可信数据库数据            |
| Response DTO / View | 定义对外返回的数据                  | 不必要的内部字段、密钥、底层异常细节         |

分层的目的是让各部分职责清楚，方便修改和测试，而不是为了项目看起来复杂而机械地增加类。

## 2.3 最小示例：Controller 调用 Service

以下代码只展示分层方式，类名和接口路径不代表真实项目代码：

```java
@RestController
@RequestMapping("/instructions")
@RequiredArgsConstructor
public class InstructionController {

    private final InstructionService instructionService;

    @PostMapping
    public ApiResult<InstructionView> create(
            @Valid @RequestBody CreateInstructionRequest request) {
        return ApiResult.success(instructionService.create(request));
    }

    @GetMapping("/{id}")
    public ApiResult<InstructionView> getById(@PathVariable Long id) {
        return ApiResult.success(instructionService.getById(id));
    }
}
```

阅读时重点看：

- `@RestController`：声明 REST 风格的控制器；
- `@RequestMapping`：为一组接口指定路径前缀；
- `@PostMapping` / `@GetMapping`：分别映射 POST / GET 请求；
- `@RequestBody`：将 JSON 请求体绑定为 Java 对象；
- `@PathVariable`：获取 URL 路径中的参数；
- `@Valid`：触发 Bean Validation 校验，前提是 DTO 已声明校验规则且项目配置支持；
- 构造器注入：由 Spring 提供所需的 Service 实例。

实际项目可能使用不同的统一响应类、参数校验方式或接口路径，应该优先跟随现有代码风格。

### 2.3.1 `@RestController` 与 REST 风格接口

#### 什么是 REST？

**REST（Representational State Transfer，表述性状态转移）** 是一种软件架构风格，常用于设计 Web API。

REST 风格的核心思想是：**将系统中的业务对象抽象为资源，通过 URL 标识资源，并使用 HTTP 请求方法表达对资源的操作。**

例如，在一个用户管理系统中：

- `/users`：表示用户资源集合。
    
- `/users/123`：表示 ID 为 `123` 的用户资源。
    

REST 风格通常具有以下特点：

1. **资源导向**：URL 主要用于表示资源，而不是直接描述操作。
    
2. **使用 HTTP 方法表达操作**：通过 GET、POST、PUT、DELETE 等方法区分查询、新增、更新和删除。
    
3. **使用 HTTP 状态码表达请求结果**：例如 `200 OK`、`201 Created`、`404 Not Found`。
    
4. **通常使用 JSON 交换数据**：客户端与服务端可以通过 JSON 传递资源数据。
    

注意：REST 是一种架构风格，并不是 HTTP 协议本身。HTTP 提供了请求方法、状态码等机制，REST 风格的 API 则利用这些机制组织接口。

#### REST 风格与 HTTP 请求方法

HTTP 协议定义了多种请求方法，REST 风格的接口通常会根据操作语义选择合适的方法。

|HTTP 方法|常见用途|示例|
|---|---|---|
|`GET`|查询资源|`GET /users/123`：查询用户|
|`POST`|创建资源，或提交需要处理的数据|`POST /users`：创建用户|
|`PUT`|整体替换或更新资源|`PUT /users/123`：更新用户|
|`PATCH`|部分更新资源|`PATCH /users/123`：修改部分用户信息|
|`DELETE`|删除资源|`DELETE /users/123`：删除用户|

这里需要注意：

- HTTP 协议定义了这些请求方法，但并没有强制所有 API 都必须按照 REST 风格使用它们。
    
- REST 风格强调请求方法的语义应当与实际操作相符。
    
- `PUT` 通常用于整体替换资源；部分更新更适合使用 `PATCH`。具体接口也可能根据业务约定有所不同。
    

#### 普通接口与 REST 风格接口的区别

假设需要查询、创建、修改和删除用户。

**传统的操作导向设计：**

```
GET  /getUser?id=123
POST /addUser
POST /updateUser
POST /deleteUser?id=123
```

**REST 风格设计：**

```
GET    /users/123
POST   /users
PUT    /users/123
DELETE /users/123
```

两者都可以正常工作。区别在于：

- **操作导向设计**通常**将动作写在 URL 中**，例如 `getUser`、`addUser`。
    
- **REST 风格**设计通常用 **URL 表示资源**，用 **HTTP 方法表示操作**。
    

实际开发中，并不是所有接口都必须严格遵循 REST 风格。有些业务操作，例如 `/orders/123/cancel`，也可能采用动作导向的接口设计。

#### `@RestController` 的作用

`@RestController` 是 Spring MVC 提供的注解，用于声明 REST API 控制器。

它相当于：

```
@Controller
@ResponseBody
```

其中：

- `@Controller`：将类声明为 Spring MVC 控制器，告诉 Spring **这个类是处理 HTTP 请求的**，Spring 启动时会扫描它，把 `@GetMapping`、`@PostMapping` 等方法注册到路由表里。。
    
- `@ResponseBody`：将方法的返回值写入 HTTP 响应体，而不是将返回字符串当作视图名称进行页面跳转。

例如：

```
@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.getUserById(id);
    }

    @PostMapping
    public User createUser(@RequestBody User user) {
        return userService.createUser(user);
    }
}
```

这里：

- `@RestController`：声明控制器，方法返回的对象通常会被转换为 JSON 等响应数据。
    
- `@RequestMapping("/users")`：设置控制器的基础 URL 路径。
    
- `@GetMapping("/{id}")`：处理查询指定用户的 GET 请求。
    
- `@PostMapping`：处理创建用户的 POST 请求。
    
- `@PathVariable`：获取 URL 路径中的变量，例如 `/users/123` 中的 `123`。
    
- `@RequestBody`：将请求体中的 JSON 等数据反序列化为 Java 对象。

 **`@RequestBody`：管"进来"的数据：**

```text
客户端发：
  POST /user
  { "name": "alice", "age": 18 }   ← 请求体是 JSON
        │
        ▼
  @RequestBody User user             ← 把 JSON 转成 User 对象
```

**`@ResponseBody`：管"出去"的数据：**

```
服务端返回：
  User 对象  →  @ResponseBody  →  JSON
        │
        ▼
客户端收到：
  { "name": "alice", "age": 18 }
```

**注意：**`@RestController` **本身并不强制接口遵循 REST 设计规范。** 即使使用 `@RestController`，也可以编写 `/getUser` 这样的非 REST 风格接口。是否符合 REST 风格，主要取决于接口的整体设计。

#### 面试总结

如果面试官问“什么是 REST 风格？`@RestController` 有什么作用？”，可以这样回答：

REST 是一种面向资源的 Web API 架构风格，通常使用 URL 标识资源，使用 GET、POST、PUT、DELETE 等 HTTP 请求方法表达查询、创建、更新和删除等操作，并通过 HTTP 状态码表示请求结果。

`@RestController` 是 Spring MVC 的控制器注解，相当于 `@Controller` 和 `@ResponseBody` 的组合，主要用于**开发返回 JSON 等响应数据**的接口。但使用 `@RestController` 并不意味着接口一定符合 REST 风格，REST 风格取决于接口的设计方式。


# 3. 指令任务的数据应该怎样管理
## 3.1 先确认实际表结构，不要先假定一定有三张表

对于较简单的业务，一张指令主表就可能足够；如果一条指令会拆成多个可独立跟踪的步骤，才可能需要步骤表；如果系统需要保存较细的处理事件和排障记录，则可能需要日志表。

可以用下面的逻辑理解不同数据的职责：

#### A. 指令主表（示意）`instruction_record`

| 字段示例 | 含义 | 说明 |
|---|---|---|
| `id` | 主键 | 唯一标识任务记录 |
| `user_id` | 用户标识 | 仅当业务需要按用户隔离/查询时使用 |
| `raw_text` | 原始指令 | 是否完整保存需考虑长度和隐私要求 |
| `intent_type` | 识别出的业务意图 | 可能在模型处理后才有值 |
| `status` | 当前状态 | 例如待处理、处理中、成功、失败 |
| `result` | 处理结果摘要 | 根据结果大小和敏感程度决定保存方式 |
| `create_time` | 创建时间 | 用于排序和查询 |
| `update_time` | 更新时间 | 记录最近一次更新 |

表名与字段只是例子，不能直接当作项目的真实数据库结构。

#### B. 步骤表（仅当业务确实需要）

一条指令被拆成多个独立步骤，且每个步骤有自己的顺序、参数或状态时，可能使用类似 `instruction_step` 的表。常见概念字段有 `instruction_id`、`step_no`、`step_type`、`status` 和时间字段。

如果项目只有一次简单模型解析，并未实现多步骤执行，就没有必要为了“架构完整”强行增加步骤表。

#### C. 执行日志表（仅当系统需要持久化业务事件时）

如果需要长期查询每次状态变更、步骤结果或错误摘要，可以单独保存执行日志。日志表通常更偏向追加记录；是否保存完整模型输出需结合隐私、数据量和保留策略决定。

**注意区分应用运行日志与数据库业务日志**：应用运行日志主要服务于排障；数据库里的业务日志则可作为业务数据被查询。两者可能有关联，但不是同一种东西。

### 3.2 主键、索引和字段类型

- **主键**：唯一标识一行数据。使用自增 ID（单表唯一）还是分布式 ID（全局唯一），应以项目既定方案为准。
- **索引**：帮助数据库更快定位符合条件的数据，但会增加写入和存储成本。
- **状态字段**：可以使用枚举对应的字符串，也可以使用数字编码；关键是项目内要有清晰一致的映射规则。
- **时间字段**：要保持项目内的时区与格式约定一致。
- **文本字段**：根据业务长度选择合适类型，不应无条件把所有文本都设置成超大字段。
- **JSON 字段**：适合保存部分结构化数据，但若经常按其中某个值过滤，应重新评估字段设计和索引策略。

索引应由真实查询模式驱动。例如接口经常按用户筛选并按创建时间倒序查询，可以评估对应的联合索引；最终是否有效，应通过真实 SQL 和执行计划确认，而不是凭字段名猜测。

### 3.3 常见的增删改查与分页

一个指令管理模块常见的查询操作可能有：

| 业务操作 | HTTP 示例 | 用途 |
|---|---|---|
| 创建指令 | `POST /instructions` | 提交新指令 |
| 查询详情 | `GET /instructions/{id}` | 根据 ID 获取任务 |
| 分页查询 | `GET /instructions?pageNo=1&pageSize=10` | 分页查看任务列表 |
| 查询状态 | `GET /instructions/{id}/status` | 获取当前状态（也可合并在详情接口） |
| 查询日志 | `GET /instructions/{id}/logs` | 仅在项目提供此功能时适用 |

```text
CRUD（增删改查）
├── C（创建）POST
├── U（更新）PUT
├── D（删除）DELETE
└── R（读取）
     ├── 查单条  GET /xxx/{id}
     └── 查列表  GET /xxx?pageNo=1&pageSize=10   ← 分页在这里
```

这些路径只是 REST API 的示例，不是项目实际地址。

分页的意义是限制单次返回数量，避免一次读取过多记录。服务端至少应对 `pageNo` 和 `pageSize` 做合理范围校验，不能让调用方提交无边界的分页参数。

MyBatis-Plus 的示意用法：

```java
Page<InstructionRecord> page = new Page<>(pageNo, pageSize);
LambdaQueryWrapper<InstructionRecord> query =
        new LambdaQueryWrapper<InstructionRecord>()
                .eq(status != null, InstructionRecord::getStatus, status)
                .orderByDesc(InstructionRecord::getCreateTime)
                .orderByDesc(InstructionRecord::getId);

Page<InstructionRecord> result = instructionMapper.selectPage(page, query);
```

这段示例的前提是项目已正确配置 MyBatis-Plus 分页拦截器。排序字段和过滤条件需要按真实业务调整；如果排序字段可能重复，增加唯一字段作为次级排序，可以帮助保持页内顺序稳定。

## 3.4 Entity、DTO 和 View：为什么需要不同的对象？
### 3.4.1 先理解：什么是 Java 对象？

假设我们开发一个用户管理系统，一个用户有以下信息：

- 用户 ID
    
- 用户名
    
- 密码
    
- 手机号
    
- 创建时间
    

在 Java 中，我们可以定义一个 `User` 类，用来描述用户有哪些属性：

```java
public class User {
    private Long id;
    private String username;
    private String password;
    private String phone;
    private LocalDateTime createTime;
}
```

创建一个 `User` 对象，就可以用它保存某个用户的具体数据。

但是，**同一个用户在不同的业务环节，需要关注的信息可能不同。**

例如：

- 保存到数据库时，需要考虑数据库字段。
    
- 用户注册时，只允许客户端提交用户名、密码和手机号。
    
- 查询用户信息时，只希望返回用户 ID、用户名和手机号，不返回密码。
    
- 执行业务逻辑时，可能需要使用经过校验和处理的数据。
    

如果所有环节都直接使用同一个 `User` 对象，就容易出现职责混杂的问题。因此，开发中会根据用途定义不同的对象。

### 3.4.2 Entity / DO：与数据库交互的对象

**Entity / DO 主要用于表示与数据库表对应的数据。**

- Entity：通常表示实体对象。
    
- DO：Data Object，通常指数据对象。
    

不同项目的命名习惯可能不同，有些项目使用 `Entity`，有些使用 `DO`，也有项目使用 `User`、`UserPO` 等名称。

例如，数据库中有一张 `user` 表：

|id|username|password|phone|
|---|---|---|---|
|1|tom|加密后的密码|13800000000|

对应的 Java 类可以写成：

```java
public class UserEntity {
    private Long id;
    private String username;
    private String password;
    private String phone;
}
```

查询数据库后，可以将查询结果映射为 `UserEntity` 对象。

例如：

```java
UserEntity user = userMapper.selectById(1L);
```

这里的 `userMapper` 负责执行数据库访问操作，查询结果被映射成 Java 对象。

**记忆：Entity / DO 主要关注数据库中存储了什么数据。**

注意：Entity 不一定必须与数据库表的每个字段一一对应，具体取决于项目的数据映射设计。

### 3.4.3 Request DTO：接收客户端提交的数据

DTO 是 Data Transfer Object 的缩写，即**数据传输对象**。

Request DTO 专门用于接收客户端发送给后端的数据。

例如，用户注册时，客户端发送以下 JSON：

```json
{
  "username": "tom",
  "password": "123456",
  "phone": "13800000000"
}
```

后端可以定义一个注册请求 DTO：

```java
public class RegisterRequestDTO {
    private String username;
    private String password;
    private String phone;
}
```

Controller 接收请求：

```java
@PostMapping("/register")
public String register(
        @RequestBody RegisterRequestDTO request) {
    userService.register(request);
    return "注册成功";
}
```

`@RequestBody` 会让 Spring MVC 将请求体中的 JSON 数据转换为 `RegisterRequestDTO` 对象。

为什么不直接接收 `UserEntity`？

因为客户端只应该提交注册业务允许的字段。例如，用户 ID 通常由服务端生成，创建时间通常由服务端设置，客户端不应该随意指定这些值。

通过 `RegisterRequestDTO`，可以明确规定注册接口接受哪些字段，并配合校验注解检查输入是否合法。

**记忆：Request DTO 主要关注客户端可以提交什么数据。**

### 3.4.4 Response DTO / View：控制返回给客户端的数据

后端处理完请求后，通常需要将结果返回给客户端。

例如，查询用户资料时，数据库对象中可能包含：

```text
id
username
password
phone
createTime
```

但前端只需要展示：

```text
id
username
phone
```

这时可以定义一个响应 DTO：

```java
public class UserResponseDTO {
    private Long id;
    private String username;
    private String phone;
}
```

Controller 返回该对象：

```java
@GetMapping("/users/{id}")
public UserResponseDTO getUser(@PathVariable Long id) {
    return userService.getUserInfo(id);
}
```

Spring MVC 通常会通过消息转换器，将返回的 Java 对象序列化为 JSON：

```json
{
  "id": 1,
  "username": "tom",
  "phone": "13800000000"
}
```

这样，密码等不应暴露的字段就不会出现在这个响应对象中。

**Response DTO** 是用于返回数据的传输对象；**View** 通常强调面向展示的数据对象。在很多项目中，两者用途相近，但具体含义取决于项目约定。有些项目会把 `VO`（View Object）作为响应对象的命名，有些则直接使用 `ResponseDTO`。

注意：不返回密码字段只是基础措施，密码也不应该以明文形式存储在数据库中。

**记忆：Response DTO / View 主要关注客户端应该看到什么数据。**

### 3.4.5 内部业务对象：处理业务时使用的数据

有时，数据库对象和请求对象都不适合直接承担某项业务处理所需要的数据。

例如，用户注册时，后端可能需要：

1. 接收用户名、密码和手机号。
    
2. 校验手机号格式和验证码。
    
3. 对密码进行安全处理。
    
4. 生成用户 ID 和创建时间。
    
5. 保存用户记录。
    

在这些步骤中，后端处理的数据可能与客户端最初提交的数据不同。

如果某个业务流程需要独立的数据结构，可以定义内部业务对象，例如：

```java
public class RegisterCommand {
    private String username;
    private String encodedPassword;
    private String phone;
}
```

这里的 `RegisterCommand` 用于表达后端已经完成部分处理、准备执行注册操作的数据。

不过，**内部业务对象并不是每个项目都必须定义的对象。** 简单业务可以直接在 Service 中处理数据；只有在业务复杂度、复用需求或代码结构确实需要时，再考虑单独定义。

### 3.4.6 把整个过程串起来

以用户注册为例，典型的数据流可以理解为：

```text
客户端提交 JSON
        ↓
RegisterRequestDTO
接收用户名、密码、手机号
        ↓
Controller 调用 Service
        ↓
Service 校验和处理业务数据
        ↓
UserEntity
保存到数据库
        ↓
数据库
```

以查询用户资料为例：

```text
客户端发送查询请求
        ↓
Controller
        ↓
Service 调用 Mapper 查询数据库
        ↓
UserEntity
        ↓
转换为 UserResponseDTO
        ↓
Spring MVC 将对象转换为 JSON
        ↓
客户端展示用户资料
```

这两条流程只是常见设计方式的示例，实际项目不一定会把所有对象都单独定义出来。

### 3.4.7 总结对比

|对象|全称 / 含义|主要用途|关注的问题|
|---|---|---|---|
|Entity / DO|实体对象 / 数据对象|表示数据库相关数据|数据库里有什么？|
|Request DTO|请求数据传输对象|接收客户端提交的数据|客户端可以提交什么？|
|Response DTO|响应数据传输对象|组织接口返回的数据|客户端应该收到什么？|
|View / VO|视图对象|组织面向展示的数据|页面需要展示什么？|
|内部业务对象|根据业务定义的数据对象|承载业务处理中需要的数据|业务处理需要什么？|

### 3.4.8 面试重点

**为什么不直接使用 Entity 作为所有接口的请求和响应对象？**

主要有三个原因：

1. **安全性**：Entity 可能包含密码、内部状态等不应直接暴露给客户端的字段。
    
2. **职责分离**：数据库结构、接口输入输出和业务逻辑的变化原因不同，分开后可以减少相互影响。
    
3. **接口控制**：Request DTO 可以限制客户端提交的字段，Response DTO 可以明确规定接口返回的字段。
    

但是，也不应该为了形式而拆分所有对象。对于简单项目，如果数据结构完全一致且没有明确的隔离需求，可以采用更简洁的设计；对于涉及敏感字段、复杂业务或需要长期维护的接口，分离对象通常更有价值。

## 3.5 数据库事务
### 3.5.1 什么是数据库事务？

**数据库事务（Transaction）** 是一组数据库操作的执行单元，可以将多个操作作为一个整体提交或回滚。

例如，AI 数字员工平台接收到一条用户指令后，需要在数据库中创建指令记录，并创建对应的任务步骤。

假设需要执行以下操作：

1. 在 `instruction_record` 表中插入一条指令记录。
    
2. 在 `task_step` 表中插入多条任务步骤记录。

#### ① 指令记录（Instruction）

**代表"用户的一条指令"**，是**主记录**：

```text
Instruction（指令记录）
├── id：指令 ID
├── userId：谁发的
├── rawText：原始指令（"帮我把上个月的销售数据导出来"）
├── parsedTask：AI 解析后的结构化任务
├── status：状态（待执行/执行中/成功/失败）
├── createTime：创建时间
└── ...
```

**一条指令 = 一条主记录。**

#### ② 任务步骤（Task Step）

**代表"这条指令要执行的每个步骤"**，是**子记录**：

```text
TaskStep（任务步骤）
├── id：步骤 ID
├── instructionId：属于哪条指令（外键）
├── stepOrder：第几步
├── action：动作（打开 ERP、选择日期、点击导出）
├── status：状态（待执行/执行中/成功/失败）
├── result：执行结果
└── ...
```

**一条指令 = 多个步骤。**

如果第一步成功，但第二步失败，就可能出现指令记录已经存在、任务步骤却没有完整创建的情况。

如果这两步在同一个数据库事务中执行，那么可以根据业务要求，让它们要么全部提交，要么在发生需要回滚的异常时全部回滚。

例如：

```java
@Transactional(rollbackFor = Exception.class)
public void createInstruction(CreateInstructionDTO request) {
    // 1. 插入指令记录
    instructionMapper.insert(instruction);

    // 2. 插入任务步骤
    taskStepMapper.batchInsert(steps);
}
```

这里的代码只是示例，用于说明事务的使用方式，并不代表实习项目中实际存在这个方法。

### 3.5.2 事务的四个特性：ACID

数据库事务通常具有四个核心特性，简称 **ACID**：

- **A — Atomicity（原子性）**
    
- **C — Consistency（一致性）**
    
- **I — Isolation（隔离性）**
    
- **D — Durability（持久性）**
    

可以先记住四个问题：

| 特性  | 核心问题                      |
| --- | ------------------------- |
| 原子性 | 一组操作是全部成功，还是部分成功？         |
| 一致性 | 操作完成后，数据是否仍然满足规定的约束和业务规则？ |
| 隔离性 | 多个事务同时执行时，会不会相互干扰？        |
| 持久性 | 事务提交后，数据是否能够持久保存？         |

#### Atomicity：原子性

**定义：事务中的一组数据库操作作为一个整体，要么全部提交，要么全部回滚。**

原子性主要解决的问题是：如果一组相关操作执行到一半失败，如何避免只完成其中一部分？

例如，假设 AI 数字员工平台创建一条指令时，需要执行两个数据库操作：

1. 向 `instruction_record` 表插入指令记录。
    
2. 向 `task_step` 表插入对应的任务步骤。
    

假设第一步成功，第二步执行失败。

如果这两个操作处于同一个有效事务中，并且异常触发回滚，那么第一步插入的记录也会被撤销，避免出现不完整的数据。

```text
开始事务
   ↓
插入指令记录：成功
   ↓
插入任务步骤：失败
   ↓
事务回滚
   ↓
撤销本事务中尚未提交的数据库修改
```

如果没有将相关操作放在同一个事务中，第一步可能已经提交，即使第二步失败，第一步的数据仍然存在。

**Java 中的常见实现：**

```java
@Transactional(rollbackFor = Exception.class)
public void createInstruction() {
    instructionMapper.insert(instruction);
    taskStepMapper.insert(step);
}
```

这只是示例。只有当两个数据库操作实际参与同一个事务，并且异常符合回滚规则时，才能达到上述效果。

注意：原子性并不意味着整个业务流程中的所有操作都会自动撤销。例如，已经提交的事务不会因为后续调用大模型失败而自动回滚。

#### Consistency：一致性

**定义：事务执行前后，数据库都应满足规定的数据约束和业务规则。**

一致性关注的不是操作有没有执行完，而是操作完成后，数据是否处于合法、合理的状态。

例如：

- 用户 ID 必须唯一。
    
- 任务记录引用的用户必须存在。
    
- 任务状态只能是系统规定的合法状态。
    
- 某些业务要求任务成功时必须具有相应的执行结果。
    

假设系统规定，每条任务步骤都必须关联一个有效的指令记录。如果数据库存在相应的外键约束，那么数据库可以阻止插入引用不存在的指令 ID 的任务步骤。

但是，如果系统没有相应的数据库约束，或者业务规则没有被正确检查，就可能出现不符合预期的数据。

因此，保持一致性通常需要多方面配合：

1. **数据库约束**：例如主键、唯一约束、外键约束、非空约束。
    
2. **应用层校验**：例如检查输入格式、任务状态是否允许转换。
    
3. **事务机制**：保证相关数据库操作按照预期提交或回滚。
    
4. **合理的业务设计**：避免不同操作产生互相矛盾的数据。
    

这里有一个重要区别：

**事务不会自动判断业务数据是否正确。**

例如，将任务状态更新为 `SUCCESS`，即使这条 SQL 成功执行，也不代表业务一定正确。如果任务实际上没有完成，系统仍然可能产生错误状态。

所以，一致性依赖数据库约束、业务校验和正确的事务设计共同实现。事务是保障一致性的手段之一，而不是全部。

#### Isolation：隔离性

**定义：多个事务并发执行时，一个事务的中间状态不应被其他事务不合理地干扰或观察。**

实际系统中，可能有多个用户同时操作数据库，也可能有多个线程同时处理任务。

例如，假设某条任务的初始状态是 `PENDING`。

两个线程几乎同时读取到该状态：

- 线程 A 认为任务可以开始执行，将状态更新为 `RUNNING`。
    
- 线程 B 也认为任务可以开始执行，再次执行相同的操作。
    

如果系统没有适当的并发控制，就可能发生同一任务被重复处理的问题。

隔离性以及相关的并发控制机制，就是为了解决事务并发执行时可能出现的数据问题。

常见的并发问题包括：

| 问题    | 含义                                              |
| ----- | ----------------------------------------------- |
| 脏读    | 一个事务读取了另一个事务尚未提交的数据                             |
| 不可重复读 | 同一事务中，多次读取同一行时，其他事务提交的修改导致读取结果不同                |
| 幻读    | 同一事务中，按照相同条件再次查询时，其他事务提交的新增或删除操作导致符合条件的记录集合发生变化 |

数据库通常通过事务隔离级别和相应的并发控制机制，决定哪些现象可能出现。

以 MySQL InnoDB 为例，常见隔离级别有：

|隔离级别|简要说明|
|---|---|
|READ UNCOMMITTED（读未提交）|可能读取其他事务尚未提交的数据|
|READ COMMITTED（读已提交）|只能读取已经提交的数据|
|REPEATABLE READ（可重复读）|同一事务中的一致性读取具有可重复性；InnoDB 还通过具体的锁机制处理部分并发写入问题|
|SERIALIZABLE（可串行化）|提供更严格的隔离，限制并发操作的方式|

隔离级别越严格，通常越有利于避免某些并发异常，但也可能增加等待和并发控制开销。具体效果还取决于数据库实现和实际操作方式。

对于 Java 后端开发，需要先理解：**事务隔离性并不等于所有并发问题都会自动解决。**

例如，两个事务都读取到任务状态为 `PENDING`，然后分别尝试执行任务。即使使用了事务，也仍然需要根据业务选择合适的并发控制方式，例如条件更新、乐观锁或悲观锁。

#### Durability：持久性

**定义：事务成功提交后，其修改应当持久保存，即使之后发生普通的程序退出或系统重启，也不应轻易丢失。**

例如，系统成功创建了一条指令记录，并且数据库已经确认事务提交。

之后，即使 Java 应用程序关闭并重新启动，正常情况下也应该能够再次从数据库中查询到这条记录。

持久性主要由数据库的持久化机制保障，例如 InnoDB 的日志机制，以及数据库的存储和恢复能力。

需要注意：

- Java 方法正常返回，不一定意味着数据库事务已经成功提交；还需要考虑事务管理的实际边界。
    
- 事务提交成功后，数据通常能够在数据库故障恢复时得到保护，但具体保障程度也取决于数据库配置、存储可靠性和故障类型。
    
- 持久性不等于永远不会丢失数据。误删除、存储介质损坏、错误配置或备份失效等情况仍可能造成数据损失，因此生产系统还需要备份和恢复机制。
    

**记忆：持久性关注的是事务提交之后的数据保存，而不是 Java 对象是否仍然存在于内存中。**

### 3.5.3 ACID 四个特性的综合理解

继续使用创建指令的例子：

|特性|在创建指令时关注什么？|
|---|---|
|原子性|指令记录和初始任务步骤是否需要一起提交或回滚？|
|一致性|指令、任务步骤及其关联关系是否满足业务规则？|
|隔离性|多个线程同时处理同一条指令时，是否会发生不合理的并发操作？|
|持久性|指令事务提交后，数据库重启时是否仍能保留已提交的数据？|

这四个特性解决的是不同的问题：

- 原子性强调操作的完整性。
    
- 一致性强调数据的正确性。
    
- 隔离性强调并发事务之间的相互影响。
    
- 持久性强调提交结果的可靠保存。
    

在实际开发中，不能仅依靠事务注解就认为 ACID 的所有要求都已得到满足。还需要正确设计数据库约束、业务校验、事务边界和并发控制机制。

对于当前阶段的 Java 后端学习，建议先掌握四个特性的定义、典型问题和实际应用场景；后续再结合 MySQL 的隔离级别、MVCC 和锁机制深入理解隔离性。

### 3.5.3 Spring 中如何使用事务？

Spring 项目中最常见的方式是使用 `@Transactional`，通常放在 Service 层的业务方法上。

结合 AI 数字员工平台的业务流程，用户提交**自然语言指令**后，后端会**调用大语言模型**，将**指令解析为结构化任务步骤**，再**将任务下发给 RPA 或浏览器执行器**。执行器完成相应操作后，会将执行结果返回给后端，后端需要将结果保存到数据库。

例如，一条指令被拆分成多个任务步骤，其中某个步骤负责在第三方应用中查询信息。执行器完成查询后，后端需要处理以下操作：

1. **更新任务步骤。** 根据任务步骤 ID 找到对应记录，将该步骤的执行状态更新为成功或失败，并保存执行结果；如果执行失败，还可以记录相应的错误信息。
    
2. **写入执行日志。** 将本次执行的相关信息写入执行日志，例如任务步骤 ID、执行结果、执行时间和失败原因等，方便后续查询执行历史和排查问题。
    
3. **更新整体任务状态（视业务设计而定）。** 如果一条指令包含多个步骤，后端还需要根据各步骤的执行情况，判断整个任务是否完成。例如，所有必需步骤都执行成功后，才能将整体任务标记为成功；如果某个步骤失败，则根据业务规则决定将任务标记为失败、待重试或其他状态。
    

其中，**更新任务步骤和写入执行日志是两项相互关联的数据库操作**。如果业务要求这两项操作必须保持一致，就可以将它们放在同一个事务中。

#### 指令记录表

每条用户指令对应一条指令记录，用 `instruction_id` 区分不同指令。

|instruction_id|用户指令|status|
|---|---|---|
|1001|查询订单|SUCCESS|
|1002|登录系统并导出报表|RUNNING|
 
#### 任务步骤表

每条指令可以拆分成多个步骤，通过 `instruction_id` 关联所属指令，通过 `step_id` 区分每个步骤。

| step_id | instruction_id | step_no | step_name | status  |
| ------- | -------------- | ------- | --------- | ------- |
| 501     | 1001           | 1       | 登录应用      | SUCCESS |
| 502     | 1001           | 2       | 查询订单      | SUCCESS |
| 503     | 1002           | 1       | 登录系统      | SUCCESS |
| 504     | 1002           | 2       | 导出报表      | RUNNING |

注意：这里的 `step_id` 是步骤自身的唯一标识，而 `instruction_id` 表示这个步骤属于哪条指令。

#### 执行日志表

每条日志通过 `step_id` 关联对应的任务步骤。这样，不同指令的执行日志就可以保存在同一张表中。

| log_id | step_id | 执行结果    | 记录内容   |
| ------ | ------- | ------- | ------ |
| 9001   | 501     | SUCCESS | 登录应用成功 |
| 9002   | 502     | SUCCESS | 查询订单成功 |
| 9003   | 503     | SUCCESS | 登录系统成功 |
| 9004   | 504     | RUNNING | 开始导出报表 |

这里的 ID 都是示例值。真实项目中通常会使用数据库生成的主键等方式保证标识唯一。

**这三张表不是分别服务于某一个指令，而是共同存储整个系统中不同指令的业务数据。**

#### 事务示例代码

例如，执行器返回某个任务步骤的执行结果后，后端需要更新任务步骤状态，并将本次执行情况写入执行日志。这两项数据库操作可以放在同一个事务中，保证它们要么一起提交，要么在符合回滚规则的异常发生时一起回滚。

```java
@Service
public class TaskStepService {

    @Transactional(rollbackFor = Exception.class)
    public void updateStepResult(TaskStep step, ExecutionLog log) {
        // 更新任务步骤状态
        taskStepMapper.updateById(step);

        // 写入执行日志
        executionLogMapper.insert(log);
    }
}
```

这里的 `taskStepMapper` 和 `executionLogMapper` 分别用于**操作任务步骤表和执行日志表**，示例省略了依赖注入及其他业务代码。

如果更新任务步骤成功，但插入执行日志时发生异常，并且异常符合事务回滚规则且没有被吞掉，那么两项数据库操作都会回滚，避免出现步骤状态已更新、对应日志却未写入的情况。

需要注意，**事务只能回滚数据库操作，不能撤销已经完成的 RPA 或浏览器操作**。例如，第三方应用中的查询已经成功，但后端保存结果时发生异常，数据库事务回滚并不会自动撤销第三方应用中的操作，因此还需要结合任务状态管理和异常处理来应对。

#### 使用事务时的注意事项

- **使用位置：** `@Transactional` 通常放在 Service 层的业务方法上。
    
- **回滚规则：** 默认遇到 `RuntimeException` 或 `Error` 时回滚，受检异常默认不回滚；`rollbackFor = Exception.class` 可以将受检异常也纳入回滚规则。
    
- **异常处理：** 如果异常被捕获后没有继续抛出，事务通常不会自动回滚。
    
- **事务代理：** 同一个类内部直接调用带 `@Transactional` 的方法，可能导致事务不生效。
    
- **事务范围：** 相关数据库操作需要参与同一个事务，才能保证它们的原子性。

### 3.5.4 这个项目中哪些地方可能需要事务？

结合项目中的**指令记录表、任务步骤表和执行日志表**，可以从以下几个场景理解事务。

**场景一：保存模型解析结果**

用户提交**自然语言指令**后，后端调用大语言模型，将**指令解析为结构化任务步骤**，再保存到数据库。

一种可能的处理流程是：

```text
接收用户指令
    ↓
保存指令记录
    ↓
调用大语言模型并解析结果
    ↓
保存任务步骤 + 更新指令状态
    ↓
提交事务
```

其中，模型调用属于外部 HTTP 请求，不需要一直占用数据库事务。

如果业务要求任务步骤保存成功后，指令状态才能进入相应的后续阶段，那么可以将**保存任务步骤和更新指令状态**放在同一个事务中。这样，如果其中一项数据库操作失败，另一项也可以回滚。

如果模型解析失败，则需要根据项目的异常处理设计，保留失败信息，并将相关记录标记为待复核或其他合适状态。此时，之前已经提交的指令记录不会自动消失。

**场景二：任务执行结果回写**

平台将结构化步骤下发给 RPA 或浏览器执行器，执行器完成操作后，后端需要将**执行结果写回数据库**。

例如：

1. 更新**任务步骤**的执行状态和结果。
    
2. 插入对应的**执行日志**。
    
3. 根据多步骤任务的完成情况，**更新指令的整体状态**。
    

如果步骤结果和执行日志必须保持一致，可以将相关数据库操作放在同一个事务中。指令整体状态是否一并更新，则取决于它与当前步骤结果之间的一致性要求。

需要注意，**数据库事务只能控制数据库操作，不能撤销已经发生的外部执行行为。** 例如，浏览器已经完成了某项操作，但后续数据库写入失败，并不意味着浏览器操作也会自动撤销。因此，系统还需要结合状态记录、异常处理、重试和幂等性等机制处理这类问题。

**场景三：记录模型解析失败信息**

模型可能返回无法解析的内容，或者缺少必要字段。项目需要保留失败样本，并将相关任务标记为待复核，方便后续排查。

如果失败信息写入和相关状态更新属于同一个数据库一致性要求，就可以考虑将它们放在同一个事务中，避免只记录了失败信息却没有更新状态，或者反过来。

具体应该更新哪张表、保存哪些字段，要以项目的实际表结构为准。

### 3.5.5 事务与业务状态有什么区别？

事务和业务状态是两个不同的概念。

项目中的指令可能经历以下业务阶段：

```text
接收指令
   ↓
模型解析
   ↓
生成结构化任务步骤
   ↓
下发执行
   ↓
回写执行结果
```

每个阶段都可以对应相应的业务状态，例如等待处理、执行中、成功或失败，具体状态名称以项目实际定义为准。

**事务控制的是一组数据库操作如何提交或回滚；业务状态描述的是指令或任务当前处于哪个阶段。**

例如，**模型解析成功**后，系统可能已经**保存了指令记录**。随后 **RPA 执行失败**，系统可以通过**新的数据库事务记录**失败信息并更新任务状态，而不需要删除之前已经保存的指令。

同样，如果某次事务回滚，也不代表整个业务流程都回到了最初状态。之前提交的事务、已经完成的模型调用和外部执行操作，都不会因此自动撤销。

因此，涉及大语言模型和 RPA 执行器的业务流程，除了事务管理，还需要设计清晰的状态流转和异常处理逻辑。

### 3.5.6 事务需要掌握到什么程度？

结合 AI 数字员工平台，重点理解事务如何保证数据库操作的一致性，以及使用事务时需要注意什么。

#### 事务的作用与 ACID 特性

事务是将多个数据库操作作为一个整体执行的机制。事务成功时提交，发生需要回滚的异常时撤销事务内尚未提交的数据库修改。

ACID 是事务的四个基本特性：

- **原子性（Atomicity）：** 事务中的操作要么全部成功，要么全部回滚。
    
- **一致性（Consistency）：** 事务执行前后，数据库都应满足业务规则和数据约束。
    
- **隔离性（Isolation）：** 并发事务之间按照相应的隔离级别相互隔离，避免不符合要求的数据干扰。
    
- **持久性（Durability）：** 事务提交后，修改的数据会被持久保存。
    

例如，后端需要更新任务步骤状态，并写入执行日志。如果两项操作必须保持一致，就可以放在同一个事务中，避免只更新状态却没有成功保存日志。

#### Spring 中如何使用 `@Transactional`？

通常将 `@Transactional` 放在 Service 层的业务方法上，用于声明该方法需要事务管理。

```java
@Service
public class TaskService {

    @Transactional
    public void updateStepAndSaveLog() {
        // 1. 更新任务步骤状态
        // 2. 写入执行日志
    }
}
```

以上是示例代码，具体 DAO 调用和方法名称应以实际项目为准。

如果两项数据库操作都参与同一个事务，并且发生了符合回滚规则的异常，事务可以将两项操作一起回滚。

注意：事务只能管理参与该事务的数据库操作，不能自动撤销已经发生的浏览器操作、RPA 操作或大语言模型调用。

#### Spring 默认的回滚规则与 `rollbackFor`

Spring 声明式事务默认情况下：

- 遇到 `RuntimeException` 或 `Error`，通常会触发回滚。
    
- 遇到受检异常（Checked Exception），默认不会仅因为该异常而触发回滚。
    

如果希望受检异常也触发回滚，可以使用 `rollbackFor`：

```java
@Transactional(rollbackFor = Exception.class)
public void updateTask() throws Exception {
    // 数据库操作
}
```

`rollbackFor = Exception.class` 表示将 `Exception` 及其子类作为回滚规则适用的异常类型。

注意：如果异常被方法内部捕获后没有继续抛出，事务管理器通常就无法根据该异常自动触发回滚。需要根据业务选择重新抛出异常，或显式设置事务回滚状态。

#### 事务为什么可能失效？

常见原因包括：

- **同类内部调用绕过代理：** Spring 通常通过代理实现声明式事务。如果同一个类中的方法通过 `this.xxx()` 调用另一个事务方法，内部调用通常不会经过事务代理，因此被调用方法上的事务配置可能不会生效。
    
- **异常被捕获后没有处理回滚：** 异常被直接捕获并吞掉时（`catch`），事务管理器可能认为方法正常结束。
    
- **异常类型不符合默认回滚规则：** 例如，受检异常默认不会自动触发回滚，需要时可以配置 `rollbackFor`。
    
- **数据库操作没有参与当前事务：** 如果操作使用了不同的事务管理方式或数据源，不能直接假设它们会一起回滚。
    

面试时，优先记住同类内部调用、异常处理方式和默认回滚规则这几个常见问题。

#### 为什么要避免长事务？

事务开启后，数据库可能需要持续占用连接，并持有相关锁。如果在事务中执行耗时的外部操作，可能延长事务时间，增加连接占用和锁等待。

结合 AI 数字员工平台，例如：

1. 后端调用大语言模型解析用户指令。
    
2. 后端将解析结果保存到数据库。
    
3. 后端向 RPA 执行器下发任务。
    
4. RPA 执行完成后，后端保存执行结果。
    

**大语言模型调用**和 **RPA 执行**都可能**耗时较长**。因此，不宜为了保证数据库操作一致性，就把整个流程包在一个数据库事务中。

更合理的思路是：将事务用于需要保持一致性的数据库操作，例如保存**任务步骤**及其相关记录；外部调用结束后，再通过独立的数据库事务保存执行结果。

不过，这并不意味着外部操作与数据库状态天然保持一致。如果外部操作已经成功，但后端保存结果失败，就需要结合任务状态、重试或补偿机制进行处理。

通常不是把一条完整指令的整个执行流程放进一个数据库事务，而是**将每次需要保持一致性的数据库操作放进一个较小的事务中**。 但不一定严格按照每个步骤一个事务来划分，而是根据业务操作的一致性要求决定。

**结合 AI 数字员工平台，可以总结为：**

1. 指令解析阶段： **调用大语言模型解析指令**，解析完成后，通过数据库事务**保存任务步骤**等数据。
    
2. 步骤执行阶段： 后端**将步骤下发给 RPA 执行器**。调用外部执行器时，通常不持有数据库事务。
    
3. 执行结果保存阶段： **执行器返回结果**后，通过**一个数据库事务更新任务步骤状态，并写入相关执行日志**。
    
4. 整体任务更新阶段： 根据**所有步骤的执行情况**，更新**指令的整体状态**；如果需要与其他数据库操作保持一致，可以放在同一个事务中。
    

举个例子，一条指令有三个步骤：

|步骤|事务处理思路|
|---|---|
|步骤 1：登录应用|外部执行完成后，开启事务保存执行结果|
|步骤 2：查询订单|外部执行完成后，开启事务保存执行结果|
|步骤 3：导出报表|外部执行完成后，开启事务保存执行结果|

这里假设每个步骤的结果独立保存，所以可以分别使用事务。

注意： 事务不是用来保证整个指令从头到尾都成功，而是保证相关数据库操作的一致性。假设步骤 1、2 已经成功，步骤 3 失败，不能靠数据库事务自动撤销之前已经完成的 RPA 操作。

#### 当前项目需要掌握到什么程度？

优先掌握以下内容：

1. 理解事务和 ACID 四个特性。
    
2. 理解为什么相关的数据库操作需要放在同一个事务中。
    
3. 会使用 `@Transactional`，知道它通常应用于 Service 层。
    
4. 理解默认回滚规则，以及 `rollbackFor` 的用途。
    
5. 知道同类内部调用等常见事务失效原因。
    
6. 理解事务不能自动撤销外部模型调用和 RPA 操作。
    
7. 知道长事务可能增加连接占用和锁等待，应避免在事务中执行不必要的耗时操作。
    

**面试记忆版：**

**事务**保证的是**参与事务的数据库操作的一致性**。Spring 中通常使用 `@Transactional` 声明事务，默认对运行时异常和 `Error` 回滚；需要让受检异常触发回滚时，可以配置 `rollbackFor`。同时要注意代理调用、异常处理和事务持续时间等问题。对于 AI 数字员工平台，**数据库事务不能代替外部操作的重试、补偿和状态管理机制**。

# 4. 大模型调用：从 HTTP 请求到可用结果
## 4.1 模型客户端不只是“发一个请求”

如果项目确实调用大模型 API，通常需要处理以下环节：

1. 根据业务输入构造请求参数；
2. 设置请求 URL、请求头和 JSON 请求体；
3. 发送 HTTP 请求并等待响应；
4. 判断 HTTP 状态和响应内容是否存在；
5. 解析返回数据并检查必要字段；
6. 将结果交给业务层，或者将失败分类并记录。

HTTP 请求成功不等于模型返回内容一定正确；模型返回了 JSON，也不等于其业务含义一定合法。

如果实际代码使用 `RestTemplate`，需要知道它是 Spring 提供的同步 HTTP 客户端之一：调用线程通常会等待请求返回。阅读相关代码时，重点确认 URL、请求方法、请求头、请求体、响应类型，以及连接超时和读取超时在哪里配置。如果项目实际使用的是其他 HTTP 客户端，就按真实实现理解，不需要为统一笔记而强行改成 `RestTemplate`。

### 4.2 HTTP、JSON 与 DTO

HTTP 是服务之间传递请求和响应的协议；JSON 是常用的数据表示格式；DTO 是 Java 侧用来承载请求或响应结构的对象。这三个概念不同，但常组合在一起使用。

例如，业务可能期望模型返回：

```json
{
  "intent": "SEARCH_PRODUCT",
  "parameters": {
    "keyword": "wireless keyboard"
  }
}
```

可以为此定义一个简化对象：

```java
public class ModelOutput {
    private String intent;
    private Map<String, Object> parameters;

    public String getIntent() { return intent; }
    public void setIntent(String intent) { this.intent = intent; }
    public Map<String, Object> getParameters() { return parameters; }
    public void setParameters(Map<String, Object> parameters) {
        this.parameters = parameters;
    }
}
```

使用 Jackson 时，可以将合法 JSON 解析成对象：

```java
ModelOutput output = objectMapper.readValue(jsonText, ModelOutput.class);
```

能解析成对象，只表示 JSON 结构与目标类型基本匹配；仍需检查 `intent` 是否受支持、`parameters` 是否包含当前意图要求的字段，以及字段值是否符合业务规则。

## 4.3 输出规范化：解析成功不等于业务成功

在 AI 数字员工平台中，大语言模型负责将用户的自然语言指令转换成结构化任务信息，后端负责校验这些信息，并将符合要求的数据转换成系统内部使用的对象。

例如，用户输入：

> 登录系统并导出报表。

模型可能返回如下 JSON：

```json
{
  "intent": "export_report",
  "parameters": {
    "system": "财务系统",
    "report_type": "月度报表"
  }
}
```

这里的 `intent` 表示任务意图，`parameters` 表示执行任务所需的参数。以上字段仅为示例，实际字段应以项目定义的模型输出格式为准。

需要注意，**模型返回了 JSON，并不代表系统就可以直接执行**。模型输出仍然属于外部输入，可能存在格式错误、字段缺失、意图不受支持、参数不合法等问题。

因此，后端需要经过调用处理、格式解析、字段校验、意图校验、参数校验和对象转换等步骤，确认输出符合要求后，才能进入后续任务流程。

### 4.3.1 整体处理流程

```
  用户提交自然语言指令
          ↓
    调用大语言模型
          ↓
    获取模型原始响应
          ↓
解析 JSON 或读取结构化响应
          ↓
检查字段是否存在、类型是否正确
          ↓
检查 intent 是否属于系统支持的范围
          ↓
检查必填参数、参数格式及业务约束
          ↓
   转换为内部任务对象
          ↓
   保存指令及任务步骤
          ↓
进入后续任务调度与执行流程

    任意阶段校验失败
          ↓
   停止当前正常处理流程
          ↓
 返回受控错误、记录必要信息
          ↓
根据错误类型决定重试、人工复核或结束处理
```

这里的任务对象转换、数据库保存和任务调度属于不同的处理阶段。通常应先完成输出校验，再保存有效的任务信息（**无论模型返回什么，后端都要检查它是否符合系统规则**），避免无效的模型输出直接进入执行流程。

### 4.3.2 调用层：确认模型调用是否成功

调用层负责与大语言模型通信，并处理请求失败、超时和服务异常等问题。

常见情况包括：

- **连接失败：** 后端无法与模型服务建立连接。
    
- **请求超时：** 模型在规定时间内没有返回结果。
    
- **HTTP 5xx：** 模型服务出现内部错误。
    
- **响应被截断：** 模型响应不完整，无法继续解析。
    
- **响应为空：** 请求可能已经返回，但没有获得有效内容。
    

这些问题属于**模型调用或响应获取阶段**，还没有进入正常的业务校验流程。

例如，后端请求模型解析“登录系统并导出报表”，但**模型服务超时**。此时后端不能将其当成解析失败，也不能直接生成一条成功的任务记录。

合理的处理方式是：

1. 识别错误发生在**调用阶段**。
    
2. 记录错误类型、请求关联 ID、调用耗时等必要信息。
    
3. 根据错误类型和重试策略决定是否重新请求。
    
4. 超过重试限制后，结束本次处理或进入已有的异常处理流程。
    

重试需要设置次数和时间限制，并根据错误类型决定是否适合重试。对于超时等无法确定请求是否已经被服务端处理的情况，也要考虑重复请求的影响。

### 4.3.3 解析层：确认响应格式是否合法

**解析层主要关心：返回的内容能不能被当作合法的 JSON 解析？**

模型调用成功，只说明后端收到了响应，并不保证响应内容符合预期格式。

假设系统要求模型返回 JSON，但模型实际返回：

```text
这是解析结果：
intent = export_report
parameters = ...
```

如果后端只接受规定格式的 JSON，这个响应就无法按照预期结构解析。

常见问题包括：

- JSON 语法错误。
    
- 字符串、括号或逗号不完整。
    
- 响应被截断。
    
- 返回内容与约定格式不一致。
    
- 返回空内容或无法识别的响应结构。
    

后端可以使用 **Jackson** 等 JSON 处理工具解析响应。解析失败时，应停止后续正常处理流程，避免将不完整的数据转换成任务。

**Jackson 是 Java 里最常用的 JSON 处理库**，负责在 **Java 对象 ↔ JSON** 之间互相转换。

例如：

```java
try {
    JsonNode root = objectMapper.readTree(response);
} catch (JsonProcessingException e) {
    // 记录解析失败
    // 返回受控错误或进入已有的异常处理流程
}
```

以上代码仅展示异常处理思路，实际实现还需要检查空响应，并根据项目使用的响应格式调整处理方式。

如果使用模型服务提供的结构化输出功能或 JSON Schema，可以减少格式错误，但不能代替后端自身的校验。

### 4.3.4 字段层：检查字段是否存在、类型是否正确

**字段层主要关心：解析出来的数据，字段是否齐全、类型是否正确、必填内容是否有效？**

即使响应是合法 JSON，也不代表其中的字段符合系统要求。

例如：

```json
{
  "intent": "export_report",
  "parameters": "财务系统"
}
```

这段内容在 JSON 语法上完全合法，但如果系统约定 `parameters` 必须是对象，那么它就不符合字段结构要求。

字段校验通常包括：

1. **必需字段检查：** 例如必须存在 `intent` 和 `parameters`。
    
2. **类型检查：** 例如 `intent` 必须是字符串，`parameters` 必须是对象。
    
3. **空值检查：** 必填字段不能为 `null` 或空字符串。
    
4. **字段约束检查：** 例如字符串长度、集合大小、数值范围等。
    

Java 项目可以使用 **DTO（数据传输对象）描述模型输出的数据结构**，再配合 Jackson 和 Bean Validation 进行解析与校验。

例如：

```java
public class InstructionResult {

    @NotBlank
    private String intent;

    @NotNull
    @Valid  // ← 深入这个对象内部，也校验它的字段
    private TaskParameters parameters;

    // getter、setter
}
```

这里的 `TaskParameters` 代表项目定义的参数对象，需要根据实际支持的任务补充字段和约束。

需要注意，声明 `@NotBlank` 或 `@NotNull` 并不意味着校验会自动执行。还需要在相应的处理流程中触发 Bean Validation，并正确处理校验异常。

### 4.3.5 意图层：确认任务类型是否受支持

字段结构正确后，还需要**判断模型识别出的意图是否属于系统支持的业务范围**。

例如，系统当前只支持：

- `login`：登录应用。
    
- `query_order`：查询订单。
    
- `export_report`：导出报表。
    

如果模型返回：

```json
{
  "intent": "delete_all_data",
  "parameters": {}
}
```

**即使 JSON 和字段类型都正确，只要该意图不在系统允许的范围内，就不能直接进入执行流程。**

后端可以使用枚举、白名单或明确的分支判断实现意图校验。例如：

```java
switch (intent) {
    case "login":
        // 进入登录任务处理流程
        break;
    case "query_order":
        // 进入订单查询任务处理流程
        break;
    case "export_report":
        // 进入报表导出任务处理流程
        break;
    default:
        throw new IllegalArgumentException("不支持的任务意图");
}
```

以上仅为示例。实际项目可以使用枚举或其他明确的映射方式，不必为了体现设计模式而强行引入复杂的策略模式。

核心原则是：**模型可以提出任务意图，但只有后端定义并允许的意图才能进入对应业务流程。**

即使意图本身受支持，也不代表该用户一定有权限执行对应操作。权限校验应由后端依据可信的用户身份和业务规则独立完成，不能依赖模型的判断。

### 4.3.6 参数层：检查必填参数与业务约束

**意图合法之后，还需要检查完成任务所需的参数是否完整、格式是否正确，以及是否符合业务规则。**

例如，用户要求导出报表，系统可能需要报表类型、查询时间范围和目标系统等参数。

以下是一个示例：

```json
{
  "intent": "export_report",
  "parameters": {
    "system": "财务系统",
    "report_type": "月度报表",
    "start_date": "2026-09-01",
    "end_date": "2026-09-30"
  }
}
```

后端可以进一步检查：

- `system` 是否属于系统支持的目标应用。
    
- `report_type` 是否属于允许的报表类型。
    
- `start_date` 和 `end_date` 是否符合日期格式。
    
- 开始日期是否早于或等于结束日期。
    
- 查询范围是否超出业务允许的限制。
    
- 当前用户是否有权限访问对应数据。
    

参数校验通常分为两类。

**第一类：基础格式校验**

例如非空、数据类型、日期格式、字符串长度和数值范围。这类校验可以使用 Bean Validation 或普通条件判断实现。

**第二类：业务规则校验**

例如目标应用是否支持对应操作、查询范围是否允许、当前用户是否有权限导出报表。这类校验通常需要结合业务规则、数据库信息或权限系统判断。

需要注意，模型输出的参数不能直接用于执行 SQL、拼接命令或控制浏览器。后端应将参数映射到明确的业务操作，**并进行必要的权限校验和输入处理**。即**后端负责“能不能干、怎么安全地干”，绝不能让模型直接指挥执行**。

如果必填参数缺失，可以根据业务设计选择拒绝处理、要求用户补充信息，或者进入人工复核流程，而不是默认补出一个可能错误的参数。

### 4.3.7 输出规范化：转换为内部认可的数据对象

完成前面的校验后，后端还需要将模型返回的数据转换成系统内部使用的对象。

这里的规范化不是简单地把 JSON 转成 Java 对象，而是确保数据具有明确的结构、类型和业务含义。

例如，模型可能返回：

```json
{
  "intent": "export_report",
  "parameters": {
    "report_type": "月度报表"
  }
}
```

后端校验通过后，可以将其**转换成内部任务对象**，其中包含已经确认的意图、经过校验的参数，以及后续业务处理需要的其他信息。

在这一过程中，后端可以：

1. 将字符串意图转换成内部枚举。
    
2. 将日期字符串转换成日期类型。
    
3. 统一参数的表示方式。
    
4. 将模型输出映射到内部 DTO 或任务命令对象。
    
5. 补充由后端生成的指令 ID、任务 ID 等系统字段。
    

**需要特别注意，任务 ID、用户身份、权限信息和执行状态等关键字段，应由后端根据实际业务生成或确定，而不是直接信任模型提供的值。**

完成规范化后，数据才具备进入后续业务流程的条件。之后，后端可以保存指令记录、创建任务步骤，并按项目的调度机制执行任务。

如果需要保证指令记录与任务步骤等数据库操作的一致性，可以在保存阶段使用事务。输出规范化本身不等于任务已经执行，也不意味着数据库事务已经提交。

### 4.3.8 异常处理：不同错误采用不同策略

**不同阶段的错误不应该全部统一处理为“模型解析失败”，因为错误原因不同，合理的处理方式也不同。**

| 失败层次 | 例子                  | 合理处理方向                    |
| ---- | ------------------- | ------------------------- |
| 调用层  | 连接失败、超时、HTTP 5xx    | 记录错误类别和必要上下文，根据错误类型决定是否重试 |
| 解析层  | 响应不是合法 JSON         | 停止正常处理，记录解析错误，必要时进入复核流程   |
| 字段层  | 缺少 `intent`、参数类型不正确 | **返回结构错误**，不创建正常任务步骤      |
| 意图层  | 模型输出不支持的意图          | 拒绝进入未知业务分支                |
| 参数层  | 缺少必填参数、日期范围不合法      | 返回明确错误，要求补充参数或拒绝处理        |
| 权限层  | 用户无权执行目标操作          | **拒绝操作**，按安全要求记录相关信息      |

对于不同的错误，可以分别采取以下策略：

- **适合重试的临时错误：** 例如部分网络异常或服务暂时不可用，可以采用有限次数的重试和退避策略。
    
- **不适合直接重试的业务错误：** 例如不支持的意图、缺少必填参数或权限不足，应优先返回明确错误，而不是重复调用模型或执行器。
    
- **需要人工处理的异常：** 对于多次解析失败或无法可靠识别的指令，可以根据业务设计保存必要的失败信息，并标记为待复核。
    

日志应记录足以定位问题的信息，例如关联 ID、错误类别、处理阶段和必要的错误摘要。对于包含敏感信息的原始指令、模型响应或业务参数，应遵循数据最小化和访问控制要求，避免无必要地完整写入日志。

此外，数据库中用于用户查询的业务执行记录，与应用程序自身用于排查异常的运行日志，可以采用不同的存储和管理方式，不必强行合并。

### 4.3.9 当前项目需要掌握到什么程度？

结合 AI 数字员工平台，优先掌握以下内容：

1. 理解模型调用成功、JSON 解析成功和业务校验成功之间的区别。
    
2. 知道如何使用 Jackson 解析 JSON，并处理格式错误。
    
3. 理解 DTO、Bean Validation 和字段类型校验的用途。
    
4. 知道意图需要使用枚举、白名单或明确的分支逻辑进行校验。
    
5. 理解必填参数、格式约束、业务规则和权限校验的区别。
    
6. 理解规范化后的数据才能进入后续任务流程，模型输出不能直接作为可信的执行指令。
    
7. 知道不同错误应采用不同处理策略，并根据错误类型决定重试、拒绝处理或人工复核。
    
8. 理解结构化输出可以降低格式错误，但不能代替后端校验。
    

**面试记忆版：**

在 AI 数字员工平台中，**后端不能直接信任大语言模型的输出**。通常先**获取模型响应**，再进行 **JSON 解析**、**字段校验**、**意图校验**和**参数校验**，最后**转换为内部任务对象**。只有通过校验的数据才能进入后续业务流程。对于调用失败、格式错误、意图不支持和参数不合法等情况，应分类处理，避免无效指令进入任务执行环节。

# 5. 任务状态、异常记录与接口响应
## 5.1 为什么需要任务状态

对于可能经历多个处理阶段的指令，只看一行数据是否存在，并不能说明任务现在处于什么阶段。简单状态可以帮助前端展示进度，也方便排查失败。

一个最小状态模型可以是：

```text
PENDING（待处理）
       ↓
PROCESSING（处理中）
    ↙         ↘
SUCCESS      FAILED
（成功）      （失败）
```

具体项目可能使用其他状态名称；如果实际业务没有异步处理，也可能不需要单独的 `PROCESSING` 状态。`REVIEW_REQUIRED` 等人工复核状态只在系统确实存在相应业务流程时才应加入。

## 5.2 更新状态时的基本原则

1. 状态值应有清晰定义，不要在各处随意写入任意字符串；
2. 成功与失败的更新路径尽量清楚；
3. 发生异常时，不要留下与真实处理结果明显矛盾的状态；
4. 状态变更和结果保存之间需要考虑一致性；
5. 失败详情应尽可能记录成可诊断的错误类别或摘要，而不是无条件保存全部敏感内容。

如果项目只需要几个简单状态，枚举配合 Service 中的清晰逻辑就可以；不必一开始就实现复杂状态机框架。

## 5.3 统一响应与全局异常处理

很多 Spring Boot 项目会使用**统一响应对象**，让前端能够以一致的结构处理正常返回和业务错误，例如：

```json
{
  "code": "SUCCESS",
  "message": "ok",
  "data": {}
}
```

这是示意结构，真实项目可能使用数字业务码或其他字段名。

全局异常处理常见写法是使用 `@RestControllerAdvice` 配合 `@ExceptionHandler`，把可预期的异常转换成约定的 HTTP 状态码和响应体，减少 Controller 中重复的 `try-catch`。

**Controller 只写业务，不写 try-catch**：

```java
@PostMapping("/register")
public Result<Void> register(@RequestBody RegisterRequest request) {
    authService.register(request);   // 出异常就抛，不用管
    return Result.success();
}
@PostMapping("/login")
public Result<String> login(@RequestBody LoginRequest request) {
    return Result.success(authService.login(request));  // 干干净净
}
```

**异常统一在一个类里处理**：

```java
@RestControllerAdvice   // ← 全局异常处理器
public class GlobalExceptionHandler {
    // 处理业务异常
    @ExceptionHandler(BizException.class)   // ← 指定处理哪种异常
    public Result<Void> handleBizException(BizException e) {
        return Result.error(400, e.getMessage());
    }
    // 处理参数校验异常
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldError().getDefaultMessage();
        return Result.error(400, msg);
    }
    // 处理其他所有异常
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.error(500, "系统错误");
    }
}
```


统一响应不等于所有请求都应该返回 HTTP 200。参数错误、未认证、无权限、资源不存在和服务端异常应按项目接口约定区分。

# 6. Redis：仅掌握实际业务用到的部分
## 6.1 Redis 在这条链路中可能做什么

Redis 是内存数据结构存储系统，常用于保存热点或可复用的数据。结合这类项目，它可能被用于缓存提示词模板、提示词压缩结果或其他计算中间结果；但这只是可能的用途，必须看真实代码确认。

首先要回答三个问题：**缓存什么？什么情况下能复用？什么时候过期？** 不要只因为项目连接了 Redis，就认为它一定缓存了模型结果或承担了任务状态管理。

## 6.2 普通 key-value 与 Hash 的区别

普通 key-value：

```text
key                  value
prompt:template:v1 →  "...prompt text..."
```

Hash 则是在一个 Redis key 内保存多个 field-value：

```text
key = user:123
    name   → "Alice"
    online → "1"
```

因此，`user:123` 是 Redis 的外层 key，`name` 和 `online` 是 Hash 内部的 field，不是独立的 Redis key。

## 6.3 TTL 是什么

TTL 是 key 的剩余生存时间。常见命令包括：

```text
SET prompt:template:v1 "..."
EXPIRE prompt:template:v1 3600
TTL prompt:template:v1
GET prompt:template:v1
```

在常见用法中，对 Hash 外层 key 执行 `EXPIRE user:123 60`，过期的是整个 Hash，而不是仅过期某一个 field。不要把 TTL 和 Redis 内存不足时使用的淘汰策略混为一谈：前者是过期时间，后者是内存压力下选择移除哪些 key 的机制。

## 6.4 缓存 key 应与结果的适用条件一致

假设实际业务缓存的是“提示词压缩结果”，一个示意 key 可以是：

```text
prompt:compressed:{bizType}:{inputHash}:{templateVersion}
```

设计原则：

- 不同业务或模板版本之间避免 key 冲突；
- 输入内容不同，通常不能错误地共享压缩结果；
- 如果结果还依赖模型版本、参数或用户上下文，相关条件也可能影响缓存有效性；
- 避免将长文本或敏感原文直接拼入 key；
- 设置合理 TTL，并在需要时通过版本号或失效机制处理更新。

这只是设计思路，不代表真实项目一定使用这套 key。重点在于：**相同 key 必须对应可以安全复用的结果。**

## 6.5 缓存未命中或不可用时怎么办

如果缓存只是可重建的加速层，系统可能在缓存未命中时重新计算或读取数据库；如果 Redis 不可用，也可能按业务要求降级。是否可以绕过缓存不能一概而论：如果缓存实际承载权限、会话或防重信息，直接绕过可能改变系统安全语义。

对主链路来说，先理解缓存命中、未命中、写入和过期的基本行为即可。缓存穿透、击穿、雪崩、持久化、淘汰策略和高可用架构属于扩展知识，除非实习任务确实涉及，否则不应占据复习主体。

# 7. Java 基础：只保留读懂业务代码最常用的部分

这份 Overview 不替代完整的 Java 面试笔记。为了读懂前面的 Controller、Service、DTO 和 Mapper，优先掌握以下内容即可。

## 7.1 类、对象、接口与依赖注入

- **类**定义属性和行为；**对象**是类的实例；
- **接口**定义一组行为契约，不同实现可以提供不同逻辑；
- **封装**让对象通过明确的方法暴露需要的操作；
- Spring 的 **IoC/DI** 让容器负责创建和组织 Bean，不用再自己 `new` 对象，通过注解让容器来 `new` 对象，并将依赖提供给需要它们的对象。

例如 `InstructionController` 依赖 `InstructionService`，不必在 Controller 内部手动 `new InstructionService()`；通常由 Spring 管理其生命周期和依赖。

## 7.2 集合、泛型与常用类型

| 类型 | 常见用途 | 阅读代码时关注什么 |
|---|---|---|
| `List<T>` | 有序保存多个对象 | 元素类型、空列表、遍历和映射 |
| `Map<K, V>` | 按 key 查找 value | key 的含义、value 类型是否明确 |
| `Set<T>` | 保存不重复元素 | 去重依据以及 `equals()` / `hashCode()` |
| `String` | 保存文本 | 不可变；频繁拼接时可考虑 `StringBuilder` |
| 枚举 `enum` | 表示有限状态或类型 | 合法值是否集中定义 |

泛型如 `List<InstructionView>` 帮助编译器检查集合里应该放什么类型。暂时不需要深入学习 `HashMap` 红黑树树化阈值等实现细节，除非任务或独立学习计划需要。

## 7.3 `==` 与 `equals()`

- 对基本类型，`==` 比较数值等实际值；
- 对引用类型，`==` 比较两个引用值是否相同；
- `equals()` 在许多类中用于比较对象内容，例如 `String`；
- 如果某个类重写了 `equals()`，通常也需要正确重写 `hashCode()`，尤其当对象被用作 `HashMap` 的 key 或放入 `HashSet` 时。

比较字符串内容时通常使用 `equals()`，不要依赖字符串对象是否来自同一引用。

## 7.4 异常处理

Java 中常见的 `RuntimeException` 包括 `NullPointerException` 和 `IllegalArgumentException`。异常处理的重点不是把异常全部捕获，而是明确由哪一层负责处理：

- 能在当前层合理修复或转换的，进行处理；
- 需要上层决定如何返回的，带着必要上下文继续抛出；
- 确实需要记录的异常，记录足够排查的信息；
- 不要捕获异常后什么都不做，导致任务失败却没有任何可见线索。

## 7.5 线程与并发的最低要求

如果当前接口只是普通同步 CRUD，不需要先深入研究 Java 并发包的所有工具。先理解：Spring Web 服务可能同时处理多个请求，因此共享的单例 Service 不应将当前请求的临时数据存入可变实例字段。若项目确实使用线程池或异步任务，再进一步学习任务提交、线程池配置、异常传播与状态更新。

# 8. Spring 与 MyBatis-Plus：沿代码阅读即可掌握
## 8.1 Spring Boot / Spring MVC 常用知识

| 概念或注解                             | 主要作用                           |
| --------------------------------- | ------------------------------ |
| `@SpringBootApplication`          | Spring Boot 应用入口及配置组合注解        |
| `@RestController`                 | 声明 REST 控制器                    |
| `@RequestMapping`                 | 定义请求映射路径和条件                    |
| `@GetMapping` / `@PostMapping`    | 映射 GET / POST 请求               |
| `@RequestBody`                    | 把请求体绑定为对象                      |
| `@PathVariable` / `@RequestParam` | 获取路径参数 / 查询参数                  |
| `@Service`                        | 将业务类注册为 Spring Bean            |
| `@Mapper`                         | 标记 MyBatis Mapper（实际也可能采用扫描配置） |
| `@Transactional`                  | 在满足代理与配置条件时声明事务边界              |
| `@RestControllerAdvice`           | 集中处理 Web 层异常或相关响应逻辑            |

**`@PathVariable`**：

```java
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
    //                          ↑ 取路径里的 123
}
```

 `@RequestParam`：
 
 ```java
@GetMapping("/user/{userId}/order/{orderId}")
public Order getOrder(
    @PathVariable Long userId,    // 取 {userId}
    @PathVariable Long orderId    // 取 {orderId}
) { ... }
 ```

## 8.2 IOC 与构造器注入

IoC 表示对象的创建和依赖管理由容器负责；DI 表示容器把依赖提供给对象。使用构造器注入时，依赖关系通常更明确，也比较容易在测试中替换依赖。

`@Transactional` 需要理解到的核心是：它为符合条件的调用提供事务行为，但实际生效受 Spring 代理、调用方式、异常类型和事务配置影响。当前任务若没有修改事务逻辑，先能辨认事务边界并理解异常如何影响提交/回滚即可。

## 8.3 MyBatis / MyBatis-Plus 的作用

MyBatis 把 Java 方法与 SQL 执行连接起来，并将查询结果映射为 Java 对象。MyBatis-Plus 在此基础上提供 `BaseMapper`、条件构造器和分页等常用能力，从而减少重复 CRUD 代码。

例如：

```java
@Mapper
public interface InstructionMapper extends BaseMapper<InstructionRecord> {
}
```

在相应配置生效时，继承 `BaseMapper` 后就可以使用常见的新增、查询、更新和删除方法。具体方法、实体映射及 SQL 行为应以项目版本和实际配置为准。

## 8.4 `#{}` 与 `${}`

MyBatis SQL 中：

- `#{value}` 通常通过预编译参数绑定传递值，能够降低常见 SQL 注入风险；
- `${value}` 是文本替换，若直接拼接不可信输入，可能引入 SQL 注入风险。

动态列名或排序字段等不能简单作为普通参数绑定的场景，应使用服务端白名单映射合法字段，而不是任意接受用户传入的 SQL 片段。

# 9. 工程化、测试和联调
## 9.1 Maven 与 Git

- **Maven**：管理 Java 项目的依赖、编译、测试和打包；`pom.xml` 是主要项目配置文件。
- **Git**：记录代码变更，支持分支协作和版本回退；提交信息应尽量说明本次修改解决了什么问题。
- **配置文件**：开发、测试环境可能使用不同的数据库、缓存、模型 URL 或密钥配置。不要把密码和 API Key 硬编码进代码或提交到仓库。

需要做的不是掌握所有工具的高级功能，而是能够启动项目、定位依赖和配置、拉取/提交代码，并在修改前后检查差异。

## 9.2 单元测试与接口联调

- **单元测试**：测试一个较小的逻辑单元，例如模型输出映射、状态判断或参数校验；
- **集成测试**：验证多个真实组件能否协作，例如接口、数据库和配置是否正确连接；
- **接口联调**：用前端、Postman 或项目指定工具发送请求，检查状态码、响应体和数据库结果是否符合预期。

对于模型输出规范化逻辑，可以先使用固定 JSON 构造测试，不必每次都请求真实模型服务。至少覆盖正常输入、缺字段、未知意图和格式错误等基本路径。

## 9.3 日志与排错

日志应该帮助回答：是哪一次请求或哪个任务出了问题、执行到哪一步、用了多长时间、失败类型是什么。若项目有任务 ID 或请求 ID，排错时应优先用它们串起相关日志。

不要把 API Key、密码、完整敏感提示词或不必要的用户隐私直接写进日志。日志也不应只写一句含糊的“失败”，而应在安全范围内提供足以定位问题的上下文。

Docker、部署流水线、复杂监控与生产环境运维，如果没有在实际实习任务中接触，可以作为了解项，不需要默认成为这段实习的主要工作内容。

# 10. 沿着一个请求进行排错

当创建指令接口不符合预期，可以按链路从外到内排查，而不是同时修改很多模块：

1. **HTTP 层**：URL、请求方法、参数和状态码是否正确？
2. **Controller 层**：请求是否进入目标方法？JSON 绑定或参数校验有没有失败？
3. **Service 层**：实际走了哪个业务分支？状态是否按预期变化？
4. **模型客户端**：请求是否发送？响应状态、耗时和响应内容是否符合预期？
5. **输出解析**：失败属于 JSON 格式、字段类型、未知意图还是业务参数问题？
6. **数据库**：SQL 是否执行？查询结果是否正确？事务是否提交？
7. **Redis（如果涉及）**：缓存是命中、未命中还是访问失败？key 对应的内容是否适用？
8. **日志与测试**：能否用任务 ID 找到相关日志？是否有复现该问题的样例？

建议先复现问题、记录预期和实际结果，再逐层缩小范围。修改后用同一组请求回归测试，避免修复一个分支却影响其他路径。
