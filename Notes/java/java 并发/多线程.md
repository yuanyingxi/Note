# 1. 什么是 Java 多线程？
## 1.1 基本概念

**线程（Thread）是 CPU 调度执行任务的基本单位之一。** 一个 Java 程序可以创建多个线程，让它们分别执行不同的任务。

例如，一个应用程序可以同时执行以下任务：

- 线程 A：处理用户请求。
    
- 线程 B：读取文件。
    
- 线程 C：执行后台任务。
    

多线程可以提高程序的并发处理能力，但不代表所有任务都会因此执行得更快。

## 1.2 线程之间的内存关系

同一个 Java **进程**中的**多个线程通常共享进程的资源**，但每个线程也有**自己的执行状态**。

| 资源              | 线程之间的关系     |
| --------------- | ----------- |
| **堆**内存中的**对象** | 可以被多个线程共享   |
| 类的**静态变量**      | 可以被多个线程访问   |
| **局部变量**        | 通常属于各自线程的栈帧 |
| 程序计数器、**线程栈**   | 每个线程独立维护    |

例如：

```java
class Counter {
    static int count = 0;

    public static void main(String[] args) {
        // 多个线程都可以访问 Counter.count
    }
}
```

`count` 是静态变量，多个线程可以访问它。如果多个线程同时修改它，就可能出现线程安全问题。

# 2. 使用多线程需要注意什么？

主要有三个问题：

1. **线程安全**：多个线程同时操作共享数据，可能产生错误结果。
    
2. **线程间通信**：线程需要交换数据或等待其他线程完成任务。
    
3. **线程管理成本**：创建和销毁线程会消耗系统资源，通常需要合理使用线程池。
    

# 3. Java 内存模型 JMM
## 3.1 什么是 JMM？

JMM（Java Memory Model，Java 内存模型）规定了**多线程环境下**，共享变量的读写操作应当满足哪些可见性和顺序规则**。

JMM 是一种抽象的内存模型，不应将它的“主内存”和“工作内存”直接等同于物理内存、JVM 堆或 CPU 缓存。

**理解 JMM，主要关注三个问题：**

- **原子性**
    
- **可见性**
    
- **有序性**
    

## 3.2 原子性

**原子性**指一个操作或需要整体保护的一组操作，不会被其他线程的并发操作破坏其整体效果。

例如：

```java
count++;
```

虽然只有一行代码，但通常包含读取、加一、写回三个步骤。

假设 `count` 初始值为 0，两个线程同时执行：

1. 线程 A 读取 `count = 0`。
    
2. 线程 B 读取 `count = 0`。
    
3. 线程 A 写入 `1`。
    
4. 线程 B 也写入 `1`。
    

最终结果是 1，而不是预期的 2。这就是丢失更新。

常见解决方案：

- 使用 `synchronized` 或 `Lock` 保护整个操作。
    
- 使用 `AtomicInteger` 等原子类执行相应的原子操作。
    

## 3.3 可见性

**可见性**指一个线程对共享变量的修改，能够按照 Java 内存模型规定的同步关系被其他线程观察到。

例如：

```java
private static boolean stopped = false;

public void run() {
    while (!stopped) {
        // 执行任务
    }
}
```

如果一个线程把 `stopped` 改成 `true`，另一个线程不一定能及时观察到这次修改。

可以使用 `volatile`：

```java
private static volatile boolean stopped = false;
```

`volatile` 能为该变量提供相应的可见性和有序性保证。

注意：`volatile` 不能保证 `count++` 这样的复合操作具有原子性。

## 3.4 有序性

**有序性**指多线程环境下，操作之间应当满足规定的**先后关系**。

为了提高性能，编译器和处理器可能**对指令进行重排序**，只要不破坏规定的程序语义。

但在多线程环境中，如果没有适当的同步措施，其他线程观察到的结果可能不符合预期。

Java 通过 JMM 的规则来保证必要的**顺序关系**。

## 3.5 happens-before 规则：多线程之间的可见性保证
### 3.5.1 什么是 happens-before？

在多线程程序中，一个线程修改了数据，另一个线程不一定能够直接按照预期观察到这个修改。

Java 内存模型（JMM）使用 **happens-before 规则**，规定**不同操作**之间是否具有**必要的先后关系**，以及这种关系能否保证一个线程的操作结果对另一个线程可见。

简单来说：

**如果操作 A happens-before 操作 B，那么 Java 保证 A 的执行结果对 B 可见，并且 A 与 B 之间必须满足规定的顺序关系。**

注意：这不意味着 A 和 B 一定由两个线程执行，也不意味着底层指令必须严格按照代码书写顺序执行。

### 3.5.2 为什么需要 happens-before？

例如，线程 A 修改了一个普通变量，线程 B 随后读取它：

```java
int number = 0;

// 线程 A
number = 100;

// 线程 B
System.out.println(number);
```

如果没有建立合适的线程间同步关系，线程 B 就不能保证读到 `100`，也可能读到旧值 `0`。

Java 提供了一些规则，用来建立线程之间的可见性和顺序保证。满足这些规则后，程序才可以依赖相应的结果。

### 3.5.3 常见的 happens-before 规则

#### 规则一：volatile 变量规则

**作用：一个线程修改了 `volatile` 变量，另一个线程随后读到了这次修改，就不仅能看到这个变量的新值，还能看到修改它之前已经完成的其他操作。**

例如：

```java
int number = 0;
volatile boolean ready = false;

// 线程 A
number = 100;
ready = true;

// 线程 B
if (ready) {
    System.out.println(number);
}
```

当线程 B 读取到线程 A 写入的 `ready = true` 时，就能够保证看到此前写入的 `number = 100`。

原因是：

1. 线程 A 先执行 `number = 100`。
    
2. 线程 A 再执行 `ready = true`。
    
3. 线程 B 读取到 `ready = true` 后，**能够看到线程 A 在此之前完成的写操作**。
    

这里的关键是 `volatile` 建立了必要的线程间可见性保证。**仅仅把** `ready` **声明为 `volatile`，并不能让所有共享变量的任意操作都自动变得线程安全。**

#### 规则二：synchronized 锁规则

对同一把锁的解锁操作，happens-before 后续对这把锁的加锁操作。

例如：

```java
int number = 0;
Object lock = new Object();

// 线程 A
synchronized (lock) {
    number = 100;
}

// 线程 B
synchronized (lock) {
    System.out.println(number);
}
```

如果线程 A 先退出同步代码块，释放 `lock`，线程 B 随后成功获取同一把锁，那么线程 B 能够看到线程 A 在释放锁之前的修改。

注意：这里要求使用的是**同一把锁**，**并且线程 B 获取锁的操作发生在线程 A 释放锁之后**。

#### 规则三：线程启动规则

在调用 `Thread.start()` 之前执行的操作，happens-before 被启动线程中的操作。

例如：

```java
int number = 100;

Thread thread = new Thread(() -> {
    System.out.println(number);
});

thread.start();
```

**线程启动前**已经执行的 `number = 100`，对**新启动的线程是可见的**，因此这里能够保证读取到 `100`。

#### 规则四：线程结束规则

一个线程中的操作，happens-before 另一个线程成功检测到该线程已经结束的操作，例如 `join()` 成功返回之后的操作。

例如：

```java
int number = 0;

Thread thread = new Thread(() -> {
    number = 100;
});

thread.start();
thread.join();

System.out.println(number);
```

执行过程：

1. 新线程将 `number` 修改为 `100`。
    
2. 主线程调用 `join()` 等待新线程结束。
    
3. `join()` 返回后，主线程能够看到新线程在结束前所做的修改，因此输出 `100`。
    

这里 `join()` 不只是让主线程等待，它也建立了必要的可见性保证。

#### 规则五：传递性规则

如果 A happens-before B，B happens-before C，那么 A happens-before C。

例如：

```text
操作 A
   ↓ happens-before
操作 B
   ↓ happens-before
操作 C
```

即使 A 和 C 之间没有直接建立一条规则，只要存在这样的关系链，就可以推导出 A happens-before C。

### 3.5.4 总结

**happens-before 不是一个需要调用的方法，而是 Java 内存模型中的一组规则，用来判断操作之间是否具备必要的可见性和顺序保证。**

|规则|记忆重点|
|---|---|
|`volatile` 规则|对同一变量的写入，对后续读取具有可见性保证|
|锁规则|释放同一把锁后，后续获取该锁的线程能看到此前的修改|
|线程启动规则|`start()` 之前的操作，对新启动线程中的操作可见|
|线程结束规则|线程结束后的成功 `join()`，保证此前操作对等待线程可见|
|传递性|A 先于 B，B 先于 C，可以推导出 A 先于 C|

**最重要的是：** happens-before 帮助我们判断多线程代码是否具有可靠的**可见性和顺序保证**。学习 `volatile`、`synchronized`、`Thread.start()` 和 `Thread.join()` 时，都可以用这套规则来理解它们为什么有效。

## 3.6 Thread 的常用方法

| 方法                     | 作用            | 说明                                                  |
| ---------------------- | ------------- | --------------------------------------------------- |
| `start()`              | 启动线程          | 创建新的执行流程，线程会自动调用 `run()`                            |
| `run()`                | 定义线程执行的任务     | 直接调用 `run()` 不会启动新线程，只是普通的方法调用                      |
| `sleep(ms)`            | 让当前线程休眠指定时间   | **不会释放已经持有的锁**；休眠结束后，线程只是重新具备运行条件，不保证立即执行           |
| `join()`               | 等待指定线程执行结束    | 例如 `thread.join()` 会让**当前线程**等待 `thread` 运行结束后再继续执行 |
| `interrupt()`          | 向线程发送中断请求     | 不一定直接终止线程；线程需要根据中断状态或异常进行处理                         |
| `isInterrupted()`      | 检查线程是否被中断     | 只检查中断状态，不会清除该状态                                     |
| `Thread.interrupted()` | 检查当前线程是否被中断   | 会清除当前线程的中断状态                                        |
| `currentThread()`      | 获取当前正在执行的线程   | 常用于查看当前线程的信息                                        |
| `isAlive()`            | 检查线程是否仍处于存活状态 | 线程启动后、执行结束前通常返回 `true`                              |

**示例：`join()` 的作用**

```java
int[] number = {0};

Thread thread = new Thread(() -> {
    number[0] = 100;
});

thread.start();
thread.join();

System.out.println(number[0]); // 输出 100
```

这里使用数组是因为 Java 的 Lambda 表达式中，**引用的局部变量必须是 `final` 或 effectively final**，不能直接在 Lambda 中重新给局部变量 `number` 赋值；但可以修改数组中的元素。

执行过程：

1. `thread.start()`：启动子线程。
    
2. 子线程将数组中的值修改为 `100`。
    
3. `thread.join()`：主线程等待子线程执行结束。
    
4. 主线程继续执行，输出 `100`。
    

**注意：** `join()` 不仅**保证主线程等待子线程结束**，还能保证子线程结束前的操作对等待结束后继续执行的主线程可见。

# 4. Java 线程与操作系统线程的关系

Java 线程与操作系统线程的映射关系，取决于使用的是**平台线程（Platform Thread）还是虚拟线程（Virtual Thread）**。

## 4.1 平台线程（Platform Thread）

传统 Java 线程通常采用 **1:1 映射模型**，即一个 Java 平台线程对应一个操作系统线程。

### 4.1.1 执行方式

```
Java 平台线程
      |
      | 1:1 映射
      v
操作系统线程
      |
      v
    CPU 执行
```

Java 平台线程由 JVM 管理，但其底层执行依赖操作系统线程。线程的 CPU 调度主要由操作系统负责。

### 4.1.2 主要特点

- **操作系统负责调度**：决定哪个线程获得 **CPU 执行时间**。
    
- **资源开销较大**：每个线程通常需要**独立的栈空间**及**相关系统资源**。
    
- **线程数量受到限制**：创建和维护大量操作系统线程**会消耗较多内存和系统资源**。
    
- **存在上下文切换开销**：操作系统在**线程之间切换**时，需要保存和恢复相关执行状态。
    

例如，服务器同时处理大量请求时，如果每个请求都使用一个平台线程，那么大量线程可能会增加资源消耗。当线程因为数据库查询、网络请求等操作而阻塞时，对应的操作系统线程通常也无法用于执行其他 Java 线程的任务。

## 4.2 虚拟线程（Virtual Thread）

Java 21 正式发布了虚拟线程。虚拟线程由 JVM 管理和调度，采用 **M 映射模型（M:N 线程映射模型）**，即**多个虚拟线程可以由较少的平台线程承载和调度**。

其中，负责承载虚拟线程的平台线程称为**载体线程（Carrier Thread）**。载体线程本身仍对应一个操作系统线程。

### 4.2.1 执行方式

```text
虚拟线程
 VT1    VT2    VT3    VT4
   \      |      |    /
      JVM 调度器
           |
      +----+----+
      |         |
      v         v
  平台线程1  平台线程2
      |         |
      v         v
  操作系统线程
```

虚拟线程不需要始终独占一个平台线程。JVM 可以根据执行情况，将不同的虚拟线程调度到载体线程上运行。

因此，虚拟线程的数量可以远多于平台线程的数量。

### 4.2.2 为什么适合高并发 I/O 场景？

假设服务器需要同时处理大量 HTTP 请求，每个请求都需要查询数据库。

```text
请求 A：执行代码 → 等待数据库 → 继续执行
请求 B：执行代码 → 等待数据库 → 继续执行
请求 C：执行代码 → 等待数据库 → 继续执行
```

**平台线程**执行**阻塞式 I/O 操**作时，即使一直在等待数据、没有执行任何代码，它对应的操作系统线程通常仍然被**占用**，不能拿去执行另一个任务。。

使用**虚拟线程**时，当虚拟线程执行某些受支持的**阻塞操作**时，**JVM** 通常可以将其暂时**挂起**，并**释放载体平台线程**，让**载体线程去执行其他虚拟线程**。等操作具备继续执行的条件后，虚拟线程再被调度执行。

这样，即使同时存在大量等待 I/O 的任务，也不必为每个任务都分配一个独立的操作系统线程，从而提高系统的并发承载能力。

**总的来说，I/O 密集型任务的大量时间花在等待上。虚拟线程可以在支持卸载的阻塞操作期间释放载体平台线程，让有限的平台线程执行更多其他任务，从而提高并发承载能力。**

### 4.2.3 主要特点

- **创建和管理成本较低**：通常比平台线程**轻量**，适合创建大量线程。
    
- **适合 I/O 密集型任务**：例如**大量 HTTP 请求**、**数据库访问**和**远程接口调用**。
    
- **不会自动加快 CPU 密集型任务**：例如复杂数学计算、图像处理等任务，仍然主要受 CPU 核心数和计算能力限制。
    
- **仍然受到系统资源限制**：虚拟线程也需要内存，数据库连接数、远程接口容量和 CPU 等仍会限制实际处理能力。
    

注意：虚拟线程可以提高并发承载能力，但不意味着数据库或其他外部服务的处理速度会随之提高。

## 4.3 平台线程与虚拟线程的区别

| 对比维度      | 平台线程             | 虚拟线程                      |
| --------- | ---------------- | ------------------------- |
| 映射关系      | 通常为 1:1          | 通常为 M                     |
| 主要调度者     | **操作系统负责调度底层线程** | **JVM 调度虚拟线程，操作系统调度底层线程** |
| 资源开销      | 相对较大             | 通常较小                      |
| 适合场景      | 各类任务             | **大量并发**、经常**阻塞等待**的任务    |
| CPU 密集型任务 | 可以执行，受 CPU 能力限制  | 可以执行，但通常不会因此获得额外的计算能力     |
| 并发能力      | 受到操作系统线程数量等因素限制  | 可以支持**远多于载体线程数量的并发任**务    |

## 4.4 总结

- **平台线程**：一个 Java 平台线程通常对应一个操作系统线程，底层线程主要由操作系统调度。
    
- **虚拟线程**：多个虚拟线程可以复用较少的平台线程，由 JVM 负责调度。
    
- **虚拟线程的核心优势**：减少大量并发任务对操作系统线程的占用，尤其适合 I/O 密集型场景。
    
- **虚拟线程的局限**：不会自动加快 CPU 密集型计算，也不会消除数据库连接数、内存和外部服务容量等限制。
    

因此，不能简单地认为 Java 线程永远等于操作系统线程，必须结合平台线程和虚拟线程的映射方式来理解。

# 5. 如何保证多线程安全？

多线程安全通常关注三个方面：

| 方面      | 含义                | 常见解决方式                         |
| ------- | ----------------- | ------------------------------ |
| **原子性** | 避免并发操作产生不完整或丢失的更新 | 原子类、锁                          |
| **可见性** | 确保其他线程能观察到共享变量的修改 | `volatile`、锁                   |
| **有序性** | 确保必要的操作顺序得到保证     | `volatile`、锁、happens-before 规则 |

这些方式各有适用范围，需要根据具体的共享数据和操作选择，不能认为使用 `volatile` 就能解决所有线程安全问题。

# 6. 线程的创建方式

Java 中常见的线程创建和任务提交方式有以下几种。

## 6.0 Java 并发编程的基础类与接口

在 Java 并发编程中，经常会遇到 `Thread`、`Runnable`、`Callable`、`Future`、`FutureTask`、`ExecutorService` 等类和接口。

它们的职责不同，可以先分为四类：

|类型|代表|主要作用|
|---|---|---|
|线程|`Thread`|启动和执行线程|
|任务|`Runnable`、`Callable<V>`|定义需要执行的任务|
|任务结果|`Future<V>`、`FutureTask<V>`|获取异步任务的执行结果，查询状态或取消任务|
|任务执行与管理|`Executor`、`ExecutorService`|提交任务，由执行器负责安排任务执行|

### 6.0.1 Thread：线程类

`Thread` 是 Java 中表示线程的类，可以**创建线程并启动执行**。

常用方法：

|方法|作用|
|---|---|
|`start()`|启动线程，由新线程执行 `run()` 中的任务逻辑|
|`run()`|定义线程要执行的代码；直接调用它不会启动新线程|
|`sleep(long millis)`|让当前线程暂停一段时间|
|`join()`|等待指定线程执行结束|
|`interrupt()`|发出中断请求，通知线程应当停止等待或处理中断|
|`currentThread()`|获取当前正在执行的线程|
|`isAlive()`|判断线程是否已经启动且尚未结束|

例如：

```java
Thread thread = new Thread(() -> {
    System.out.println("执行任务");
});

thread.start(); // 启动新线程
```

注意：`start()` 和 `run()` 不一样。调用 `start()` 才会启动一个新线程；直接调用 `run()` 只是普通的方法调用。

### 6.0.2 Runnable：无返回值的任务接口

`Runnable` 是一个函数式接口，用于定义需要执行的任务。

```java
@FunctionalInterface
public interface Runnable {
    void run();
}
```

它只定义任务逻辑，不负责启动线程，也不能通过 `run()` 直接返回任务结果。

例如：

```java
Runnable task = () -> {
    System.out.println("执行任务");
};

Thread thread = new Thread(task);
thread.start();

// 等价于使用 lambda
Thread thread = new Thread(() -> {
	System.out.println("执行任务");
});

thread.start();
```

这里：

- `Runnable`：描述要做什么。
    
- `Thread`：负责启动线程执行任务。
    

由于 `Runnable` 没有返回值，任务执行过程中产生的结果通常需要通过其他方式传递，例如返回值封装、共享对象或其他并发工具。

### 6.0.3 Callable\<V>：有返回值的任务接口

`Callable<V>` 与 `Runnable` 类似，也是用于定义任务的接口，但它可以**返回结果**，也可以**抛出异常**。

```java
@FunctionalInterface
public interface Callable<V> {
    V call() throws Exception;
}
```

例如：

```java
Callable<Integer> task = () -> {
    return 100;
};
```

这里的 `Integer` 表示任务返回结果的类型。

与 `Runnable` 的区别：

|对比|Runnable|Callable<V>|
|---|---|---|
|执行方法|`run()`|`call()`|
|返回结果|无|可以返回 `V` 类型结果|
|声明抛出异常|不能在接口方法中声明受检异常|可以声明 `throws Exception`|
|能否直接传给 `Thread` 构造器|可以|不可以，需要包装或通过执行器提交|

**`Callable` 本身不能直接传给 `new Thread()`，因为 `Thread` 的相关构造器接收的是 `Runnable`，而不是 `Callable`。**

### 6.0.4 Future\<V>：获取异步任务的执行结果

**`Future<V>` 是一个接口**，用来表示一个已经提交、但可能尚未执行完成的任务。它可以让我们获取**异步任务**的**执行结果，以及查询任务状态、尝试取消任务**的接口。

可以把它理解为：**你把任务交给线程池执行后，线程池给你一个 `Future`，之后你就可以通过它了解任务的执行情况。**

例如，提交一个计算任务，计算完成后返回 `100`：

```java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();

        // 1. 提交任务，任务执行后返回 100
        Future<Integer> future =
                executor.submit(() -> 100);

        // 2. 获取任务的执行结果
        Integer result = future.get();

        // 3. 输出结果
        System.out.println(result); // 100

        executor.shutdown();
    }
}
```

**执行过程：**

1. `executor.submit(() -> 100)`：**向线程池提交一个任务**，这个任务执行后会返回整数 `100`。
    
2. `Future<Integer> future`：**接收线程池返回的 `Future` 对象**。`Integer` 表示这个任务的结果类型是整数。
    
3. `future.get()`：获取任务的执行结果。**如果任务还没执行完成，当前线程就会等待，直到任务完成或发生异常（就是死等）**。
    
4. `System.out.println(result)`：输出获取到的结果 `100`。
    

这里需要区分：**`future` 不是计算结果本身，而是一个可以用来获取结果、查询任务状态的对象**。真正的结果是调用 `future.get()` 后得到的 `100`。

#### 为什么需要 Future？

假设任务需要执行一段耗时操作，我们不一定要在提交任务时立即等待结果，可以先做其他事情，之后再调用 `get()` 获取结果。

`Future` 的常用方法：

| 方法                   | 作用                                |
| -------------------- | --------------------------------- |
| `get()`              | 获取结果；任务未完成时会等待                    |
| `get(timeout, unit)` | 最多等待指定时间，超时会抛出 `TimeoutException` |
| `isDone()`           | 判断任务是否已经结束                        |
| `cancel(true)`       | 尝试取消任务，并尝试中断正在执行任务的线程             |
| `isCancelled()`      | 判断任务是否已被取消                        |

注意：`cancel(true)` 不保证任务立即停止。如果任务没有响应中断，或者已经完成，就不能依靠这个方法强制终止任务。

#### Callable 与 Future 的区别

`Callable` 和 `Future` 的职责不同：

| 对比       | `Callable<V>`      | `Future<V>`                     |
| -------- | ------------------ | ------------------------------- |
| 本质       | 接口，用于**定义任务**      | 接口，用于**管理异步任务的结果**              |
| 主要作用     | 规定任务要执行什么，以及返回什么结果 | 获取结果、查询状态、尝试取消任务                |
| 核心方法     | `call()`           | `get()`、`isDone()`、`cancel()` 等 |
| 是否直接执行任务 | 定义任务，但本身不负责调度执行    | 不负责执行任务                         |
| 形象理解     | 要执行的工作             | 获取这项工作的结果凭证                     |

例如：

```java
Callable<Integer> task = () -> 100;

Future<Integer> future = executor.submit(task);

Integer result = future.get();
```

**`Runnable` 和 `Callable` 都可以提交给线程池执行；主要区别是 `Callable` 可以通过返回值传递计算结果并通过 `future.get()` 获取，而 `Runnable` 不行。

执行过程：

```text
Callable<Integer>
定义任务：返回 100
        |
        v
executor.submit(task)
将任务提交给线程池执行
        |
        v
Future<Integer>
代表异步任务的结果
        |
        v
future.get()
获取结果 100
```

这里：

- `task`：定义要执行的任务。
    
- `submit(task)`：将任务提交给线程池执行，并返回一个 `Future` 对象。
    
- `future`：用于查询任务状态和获取结果。
    
- `future.get()`：获取任务实际返回的 `100`。
    

**核心记忆：`Callable` 关注任务本身，`Future` 关注任务执行的结果和状态。**

### 6.0.5 FutureTask\<V>：包装任务并提供执行与结果管理能力

`FutureTask<V>` 是一个**具体类**，可以**包装 `Callable<V>` 或 `Runnable` 任务**，并**结合任务执行与结果管理的功能**。

它**实现**了 `RunnableFuture<V>` 接口，而 `RunnableFuture<V>` 同时继承了 `Runnable` 和 `Future<V>`。

因此，**`FutureTask` 具备以下能力**：

- **执行任务**：实现了 `Runnable`，可以传入 `Thread` 的构造方法，也可以交给线程池执行。
    
- **获取结果**：实现了 `Future<V>`，可以通过 `get()` 获取任务的执行结果。
    
- **查询状态**：可以通过 `isDone()`、`isCancelled()` 查询任务状态。
    
- **尝试取消任务**：可以通过 `cancel()` 尝试取消任务。
    

#### 基本使用

```java
import java.util.concurrent.Callable;
import java.util.concurrent.FutureTask;

public class Main {
    public static void main(String[] args) throws Exception {
        // 1. 定义有返回值的任务
        Callable<Integer> task = () -> 100;

        // 2. 使用 FutureTask 包装任务
        FutureTask<Integer> futureTask = new FutureTask<>(task);

        // 3. 将 FutureTask 传入 Thread
        Thread thread = new Thread(futureTask);

        // 4. 启动线程执行任务
        thread.start();

        // 5. 获取任务结果
        Integer result = futureTask.get();
        System.out.println(result); // 100
    }
}
```

#### 执行过程

```text
Callable<Integer>
定义任务：返回 100
        |
        v
FutureTask<Integer>
包装任务
        |
        +----------------------+
        |                      |
        v                      v
Runnable 能力             Future<Integer> 能力
可以交给 Thread 执行       获取结果、查询状态、尝试取消
        |                      |
        v                      v
thread.start()            futureTask.get()
        |                      |
        v                      v
执行 call()               获取结果 100
```

#### 为什么需要 FutureTask？

**`Callable` 可以定义有返回值的任务，但不能直接传给 `Thread`；`Future` 可以管理异步任务的结果，但它本身只是接口，不能直接创建对象。**

`FutureTask` 将这两类能力结合起来，**使一个任务既可以交给线程执行，又可以在任务执行后获取结果**。

注意：创建 `FutureTask` 时，任务不会自动开始执行，需要通过 `Thread.start()`、线程池等方式启动或提交。调用 `get()` 时，如果任务尚未完成，当前线程会等待结果。

**核心记忆：`FutureTask` 可以把 `Callable` 包装成可执行的任务，同时提供 `Future` 的结果管理能力，因此既能传给 `Thread`，也能获取任务结果和查询任务状态。**

### 6.0.6 Executor 与 ExecutorService：任务执行器

前面介绍的 `Thread` 需要我们创建线程并调用 `start()` 执行任务。实际开发中，也可以把任务交给**执行器（Executor）**，由执行器负责安排任务的执行。

#### Executor：执行任务的接口

`Executor` 是一个接口，核心方法是：

```java
void execute(Runnable command);
```

它只规定了一个基本功能：**接收一个 `Runnable` 任务并执行**。

调用者只需要提交任务，不必关心具体如何创建和管理线程。

#### ExecutorService：提供更多管理功能的接口

`ExecutorService` 继承了 `Executor`，除了可以执行任务，还提供了**提交任务**、**获取任务结果**以及**管理执行器生命周期**等功能。

常用方法：

|方法|作用|
|---|---|
|`execute(Runnable)`|提交任务，不返回 `Future`|
|`submit(Runnable)`|提交任务，返回 `Future<?>`|
|`submit(Callable<V>)`|提交有返回值的任务，返回 `Future<V>`|
|`shutdown()`|停止接收新任务，让已提交的任务继续执行|
|`shutdownNow()`|尝试停止正在执行的任务，并返回尚未开始执行的任务|
|`awaitTermination(...)`|等待执行器终止，最多等待指定时间|

其中，`execute()` 和 `submit()` 的主要区别是：`execute()` 不返回任务结果凭证，而 `submit()` 会返回 `Future`，方便后续查询任务状态或获取结果。

#### 使用示例

```java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        // 1. 创建一个固定大小为 10 的线程池
        ExecutorService executor =
                Executors.newFixedThreadPool(10);

        // 2. 提交任务，并获取 Future
        Future<Integer> future =
                executor.submit(() -> 100);

        // 3. 获取任务结果
        Integer result = future.get();
        System.out.println(result); // 100

        // 4. 关闭执行器
        executor.shutdown();
    }
}
```

执行过程：

```text
创建 ExecutorService
        |
        v
submit() 提交 Callable 任务
        |
        v
执行器安排任务执行
        |
        v
返回 Future<Integer>
        |
        v
future.get() 获取结果
        |
        v
得到 100
```

注意：

- `submit()` 返回 `Future` 后，任务不一定已经执行完成。
    
- `get()` 在任务未完成时会等待结果。
    
- `shutdown()` 不会直接中断已提交的任务，而是停止接收新任务，并等待已提交任务执行完毕。
    
- `Executors.newFixedThreadPool(10)` 默认使用无界任务队列，实际开发中需要考虑任务积压和资源限制。
    

**核心记忆：`Executor` 负责定义任务执行的基本入口，`ExecutorService` 在此基础上提供更完整的任务提交、结果获取和生命周期管理功能。**

### 6.0.7 Java 并发类与接口之间的关系

前面这些类和接口可以按照职责分为三部分：**定义任务、执行任务、管理结果**。

#### 定义任务

- `Runnable`：定义无返回值的任务，通过 `run()` 执行。
    
- `Callable<V>`：定义可以返回 `V` 类型结果的任务，通过 `call()` 执行。
    

它们都只负责描述任务逻辑，本身不负责启动线程。

#### 执行任务

- `Thread`：可以接收 `Runnable`，通过 `start()` 启动新线程执行任务。
    
- `Executor`：定义执行 `Runnable` 任务的基本接口。
    
- `ExecutorService`：扩展 `Executor`，支持 `execute()` 和 `submit()` 等操作。
    
- `FutureTask<V>`：实现了 `RunnableFuture<V>`，因此既可以作为 `Runnable` 被执行，也可以作为 `Future<V>` 管理结果。
    

#### 获取和管理结果

- `Future<V>`：定义获取结果、查询状态和尝试取消任务等操作。
    
- `FutureTask<V>`：`Future<V>` 的一种具体实现，同时具备可执行任务的能力。
    

#### 整体关系图

```
                定义任务
              /        \
        Runnable       Callable<V>
            |               |
            |               v
            |         FutureTask<V>
            |               |
            +-------+-------+
                    |
                    v
                 执行任务
                /        \
             Thread    ExecutorService
             start()    execute()/submit()
                            |
                            v
                      Future<V>
                      获取和管理结果
```

这张图展示的是常见的使用关系，并不是所有类之间的继承关系。

需要特别注意：

- `Thread` 可以执行 `Runnable`，因此也可以执行实现了 `Runnable` 的 `FutureTask`。
    
- `ExecutorService.submit(Callable)` 可以提交有返回值的任务，并返回 `Future`。
    
- `ExecutorService.submit(Runnable)` 也会返回 `Future`，但普通 `Runnable` 没有返回值，因此正常完成时 `get()` 返回 `null`。
    
- `FutureTask` 同时具备任务执行和结果管理能力，但不是所有 `Future` 都是 `FutureTask`。
    

**核心记忆：`Runnable` 和 `Callable` 定义任务，`Thread` 和执行器负责执行任务，`Future` 管理异步结果，`FutureTask` 将可执行任务与结果管理结合起来。**

## 6.1 继承 Thread 类

```java
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("执行任务");
    }
}

// 创建并启动线程
MyThread thread = new MyThread();
thread.start();
```

特点：

- 实现简单。
    
- 因为已经继承了 `Thread`，不能再继承其他类。

## 6.2 实现 Runnable 接口

```java
class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println("执行任务");
    }
}

Thread thread = new Thread(new MyTask());
thread.start();
```

特点：

- 将任务逻辑与线程对象分离。
    
- 任务类仍然可以继承其他类。
    
- 多个线程可以使用同一个 `Runnable` 对象，但如果共享可变数据，仍需考虑线程安全。
    

## 6.3 实现 Callable 接口

`Callable` 与 `Runnable` 类似，但 `call()` 方法可以**返回结果**，也可以抛出异常。

通常可以配合 `FutureTask` 使用：

```java
import java.util.concurrent.Callable;
import java.util.concurrent.FutureTask;

Callable<Integer> task = () -> 100;

FutureTask<Integer> futureTask = new FutureTask<>(task);

Thread thread = new Thread(futureTask);
thread.start();

Integer result = futureTask.get();
System.out.println(result); // 100
```

这里：

- `Callable<Integer>`：定义一个返回整数结果的任务。
    
- `FutureTask`：包装任务，并保存执行结果。
    
- `get()`：获取任务结果。如果任务尚未完成，调用线程可能需要等待。
    

## 6.4 使用线程池

实际开发中，通常会使用线程池管理任务，而不是每次都手动创建线程。

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

ExecutorService executor = Executors.newFixedThreadPool(10);

executor.submit(() -> {
    System.out.println("执行任务");
});

executor.shutdown();
```

这里创建了一个固定大小为 10 的线程池，并提交了一个任务。

线程池的主要作用：

- 重用线程，减少频繁创建和销毁线程的开销。
    
- 控制并发执行的线程数量。
    
- 配合任务队列管理待执行任务。
    

注意：线程池的大小和队列容量仍需要合理配置。配置不当也可能造成任务积压或资源耗尽。

# 7. start() 和 run() 的区别
## 7.1 start()

`start()` 会启动一个新线程，由新线程执行 `run()` 中的任务。

```java
Thread thread = new Thread(() -> {
    System.out.println("执行任务");
});

thread.start();
```

## 7.2 run()

直接调用 `run()` 只是普通的方法调用，不会启动新线程。

```java
thread.run();
```

此时，任务会在当前调用线程中执行。

## 7.3 注意事项

同一个 `Thread` 对象只能成功调用一次 `start()`。线程结束后，不能通过再次调用该对象的 `start()` 来重新启动它。

# 8. 如何停止线程？

Java 通常采用**协作式取消**：向线程发出停止请求，由线程在适当的位置检查请求并自行退出。

### 8.1 使用标志位

```java
private volatile boolean running = true;

public void run() {
    while (running) {
        // 执行任务
    }
}

public void stopTask() {
    running = false;
}
```

**`volatile` 保证可见性：一个线程修改了变量后，其他线程后续读取该变量时，能够看到符合 Java 内存模型规则的最新值。**

适合能够**定期检查标志位的任务**。但如果线程正在长时间阻塞，仅修改标志位不一定能立即让它退出。

## 8.2 使用 interrupt()

`interrupt()` 用于向线程发出中断请求。

```java
Thread worker = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // 执行任务
    }
});

worker.start();
worker.interrupt();
```

线程通过检查中断状态，决定是否退出任务。

## 8.3 使用 Future.cancel(true)

对于**线程池中的任务**，可以使用 `Future.cancel(true)` 尝试取消任务，并在适用情况下向执行任务的线程发出中断请求。

但任务能否及时停止，仍取决于任务是否正确响应中断。

## 8.4 注意事项

- `interrupt()` 不是强制杀死线程。
    
- `Thread.stop()` 已废弃，不应使用，因为它可能使共享数据处于不一致状态。
    
- 如果线程在 `sleep()`、`wait()` 或 `join()` 等可中断等待中收到中断，通常会抛出 `InterruptedException`，并清除中断标志。
    
- 捕获 `InterruptedException` 后，如果当前方法不能继续完成任务，通常应结束任务或向上抛出异常；如果需要在当前层处理并保留中断请求，可以恢复中断标志。
    

# 9. `interrupt()` 为什么可能抛出 `InterruptedException`？

Java 的线程中断是一种**协作式中断机制**，不是强制终止线程。

调用 `thread.interrupt()` 是向目标线程发出**中断请求**。目标线程可以通过检查中断状态，或者响应支持中断的阻塞方法，决定如何处理这个请求。

## 9.0 什么是中断状态？

**中断状态是 Java 用来记录线程是否收到了中断请求的一个状态标记。** 可以把它简单理解为一个 `true / false` 标记：

- `false`：当前没有处于中断状态。
    
- `true`：当前处于中断状态，表示线程**收到了中断请求**，但**不代表线程已经停止**。
    

例如：

```java
// 线程 A
while (!Thread.currentThread().isInterrupted()) {
    // 执行任务
}

// 线程 B
thread.interrupt();
```

当线程 B 调用 `interrupt()` 后，如果线程 A 没有正在执行会响应中断的阻塞操作，其中断状态通常会被设置为 `true`。

线程 A 在后续检查中断状态时，发现状态为 `true`，就可以主动退出循环。

因此，**中断状态只是一个标记，不会自动终止线程。线程是否退出，取决于线程如何响应中断请求。**

### 9.0.1 什么是清除中断状态？

清除中断状态，就是将中断状态从 `true` 变回 `false`。

```java
Thread.currentThread().interrupt();

System.out.println(Thread.currentThread().isInterrupted()); // true

Thread.interrupted(); // 检查当前线程状态，并清除状态

System.out.println(Thread.currentThread().isInterrupted()); // false
```

这里需要注意：

- **`isInterrupted()`**：检查指定线程的中断状态，**不清除状态**。
    
- **`Thread.interrupted()`**：检查当前线程的中断状态，**如果状态为** `true`，则清除状态并返回 `true`。
    

清除中断状态不代表之前没有发生过中断，也不代表线程重新启动了，只是当前的中断状态被清除了。

### 9.0.2 为什么有时中断状态会被清除？

当线程正在执行 `sleep()`、`wait()`、`join()` 等**支持中断的阻塞方法**时，如果收到中断请求，这些方法会**提前结束**等待并抛出 `InterruptedException`。

**这类方法因中断而抛出** `InterruptedException` **时，会清除线程的中断状态。**

例如：

```java
try {
    Thread.sleep(10000);
} catch (InterruptedException e) {
    System.out.println(Thread.currentThread().isInterrupted()); // 通常为 false
}
```

如果捕获异常后，希望上层代码仍然能够感知这次中断，可以恢复中断状态：

```java
try {
    Thread.sleep(10000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // 恢复中断状态
    return;
}
```

这里重新调用 `interrupt()`，是为了将中断状态重新设置为 `true`，让上层代码或后续逻辑能够感知中断请求。

## 9.1 不同情况下的中断行为

调用 `interrupt()` 后，具体行为取决于目标线程当前正在做什么。

|线程当前的状态|中断后的常见行为|
|---|---|
|正常执行代码|设置中断状态，不会强制停止线程；线程需要主动检查或响应中断|
|执行 `sleep()`、`wait()`、`join()`|提前结束等待并抛出 `InterruptedException`，同时清除中断状态|
|执行 `LockSupport.park()`|可以使等待提前返回，通常不抛出 `InterruptedException`，也不会因此清除中断状态|
|等待进入 `synchronized`|不能靠中断直接取消获取监视器锁的等待|
|使用 `ReentrantLock.lock()` 等待|普通 `lock()` 不支持通过中断取消等待；可以使用 `lockInterruptibly()` 响应中断|

注意：线程即使收到了中断请求，也不一定会立即退出。例如，线程正在执行不响应中断的阻塞操作时，单纯调用 `interrupt()` 不一定能让它立即结束。

## 9.2 `isInterrupted()` 和 `Thread.interrupted()` 的区别

| 方法                       | 作用          | 是否清除中断状态              |
| ------------------------ | ----------- | --------------------- |
| `thread.isInterrupted()` | 检查指定线程的中断状态 | 否                     |
| `Thread.interrupted()`   | 检查当前线程的中断状态 | 是，如果状态为 `true`，检查后会清除 |

示例：

```java
Thread.currentThread().interrupt();

// 检查状态，但不清除
System.out.println(Thread.currentThread().isInterrupted()); // true

// 检查当前线程状态，并清除
System.out.println(Thread.interrupted()); // true

// 状态已经被清除
System.out.println(Thread.currentThread().isInterrupted()); // false
```

## 9.3 总结

|概念|含义|
|---|---|
|`interrupt()`|向目标线程发出中断请求|
|中断状态|记录线程当前是否处于中断状态|
|清除中断状态|将中断状态从 `true` 变回 `false`|
|`InterruptedException`|支持中断的阻塞方法响应中断时可能抛出的异常|

**核心理解：** `interrupt()` 是发出中断请求，中断状态是记录请求的标记，`InterruptedException` 是部分阻塞方法响应中断的方式。三者都不等于强制终止线程。**
    

# 10. Java 线程的六种状态

Java 在 `Thread.State` 中定义了六种线程状态。

| 状态              | 含义                             |
| --------------- | ------------------------------ |
| `NEW`           | 线程对象已创建，但尚未启动                  |
| `RUNNABLE`      | 处于可运行状态，可能正在运行，也可能等待 CPU 调度    |
| `BLOCKED`       | 等待获取或重新获取 `synchronized` 的监视器锁 |
| `WAITING`       | 无限期等待其他线程执行某种操作                |
| `TIMED_WAITING` | 在指定时间内等待                       |
| `TERMINATED`    | 线程已经执行结束                       |

注意：

- Java 的 `RUNNABLE` 同时涵盖了**操作系统层面的就绪和运行情况**。
    
- `BLOCKED` 特指等待进入或重新进入 `synchronized` 监视器的状态。
    
- 等待 `ReentrantLock` 时，线程可能处于 `WAITING` 或 `TIMED_WAITING`，具体取决于等待方式。
    
- `getState()` 返回的是某一时刻的状态，不能单独用于精确控制线程执行顺序。
    

# 11. `sleep()` 和 `wait()` 的区别
## 11.1 基础概念：`wait()` 和对象监视器锁
### 11.1.1 什么是对象监视器锁？

Java 中，**每个对象**都可以作为 `synchronized` 的锁对象。线程进入以该对象为锁的同步代码块之前，需要先获得对应的**对象监视器锁（Monitor Lock）**。

例如：

```java
Object lock = new Object();

synchronized (lock) {
    // 执行同步代码
}
```

这里的 `lock` 是锁对象。

- 线程获得 `lock` 的监视器锁后，才能进入同步代码块。
    
- 如果其他线程也想进入以 `lock` 为锁的同步代码块，就需要等待。
    
- 同一时刻，只有一个线程能够持有同一个对象的监视器锁。
    

注意：这里说的是同一个锁对象。如果两个同步代码块使用不同的对象作为锁，它们之间就不一定存在锁竞争。

### 11.1.2 什么是 `Object.wait()`？

`wait()` 是 `Object` 类提供的方法，用于让当前线程等待某个条件成立。

它通常与 `synchronized` 配合使用：

```
synchronized (lock) {
    lock.wait();
}
```

调用 `lock.wait()` 时，需要满足两个条件：

1. 当前线程已经持有 `lock` 对应的监视器锁。
    
2. 当前线程调用的是这个锁对象的 `wait()` 方法。
    

调用后，线程会进入等待状态，并**释放** `**lock**` **对应的监视器锁**，让其他线程有机会获取这把锁并修改相关条件。

当其他线程调用 `lock.notify()` 或 `lock.notifyAll()` 后，等待线程可以被唤醒，但它必须重新竞争并获得 `lock` 的监视器锁，才能从 `wait()` 返回并继续执行。

因此，`notify()` 不代表等待线程会立即执行。

### 11.1.3 `wait()` 为什么需要配合锁使用？

假设一个线程需要等待任务完成，另一个线程负责完成任务。

```
Object lock = new Object();
boolean finished = false;

// 线程 A：等待任务完成
synchronized (lock) {
    while (!finished) {
        lock.wait();
    }

    // 任务已经完成，继续执行
}

// 线程 B：完成任务并通知
synchronized (lock) {
    finished = true;
    lock.notifyAll();
}
```

执行过程：

1. 线程 A 获取 `lock`，发现 `finished == false`。
    
2. 线程 A 调用 `wait()`，进入等待状态并释放 `lock`。
    
3. 线程 B 获取 `lock`，将 `finished` 修改为 `true`，然后调用 `notifyAll()`。
    
4. 线程 A 被唤醒后，重新竞争 `lock`。
    
5. 线程 A 重新获得锁后，再次检查 `finished`，发现条件成立，于是继续执行。
    

这里使用 `while` 而不是 `if`，是因为线程被唤醒后需要重新检查条件：它可能经历虚假唤醒，也可能被唤醒时条件已经不再成立。

**核心理解：** `wait()` 不是简单地暂停一段时间，而是让线程等待条件，并在等待期间释放指定对象的监视器锁。

## 11.2 `Thread.sleep()` 是什么？

`Thread.sleep()` 是 `Thread` 类提供的静态方法，用于让当前线程暂停执行指定时间。

```
Thread.sleep(1000); // 暂停约 1 秒
```

调用后：

- 当前线程进入计时等待状态（`TIMED_WAITING`）。
    
- 时间到达后，线程可以恢复为可运行状态，但不保证立即获得 CPU 执行。
    
- `sleep()` 不会释放当前线程已经持有的任何监视器锁。
    

例如：

```
synchronized (lock) {
    Thread.sleep(1000);
}
```

线程休眠期间仍然持有 `lock`，其他线程不能进入需要同一把锁的同步代码块。

## 11.3 `sleep()` 和 `wait()` 的区别

|对比项|`Thread.sleep()`|`Object.wait()`|
|---|---|---|
|所属类|`Thread`|`Object`|
|主要用途|暂停当前线程一段时间|等待其他线程通知或相关条件成立|
|调用前是否需要持有锁|不需要|必须持有调用对象的监视器锁|
|是否释放锁|不释放任何已持有的监视器锁|释放调用对象对应的监视器锁|
|如何恢复执行|等待时间结束，或被中断|被通知、发生虚假唤醒或被中断等；有超时时也可能因超时返回|
|常见线程状态|`TIMED_WAITING`|无超时通常为 `WAITING`；有超时通常为 `TIMED_WAITING`|
|是否可能抛出 `InterruptedException`|是|是|

注意：`wait()` 只释放调用对象的监视器锁，不会自动释放当前线程持有的其他锁。

## 11.4 `wait()` 的使用注意事项

### （1）必须持有对应的监视器锁

```
Object lock = new Object();

lock.wait(); // 错误：当前线程没有持有 lock 的监视器锁
```

上述代码会抛出 `IllegalMonitorStateException`。

正确做法是：

```
synchronized (lock) {
    lock.wait();
}
```

### （2）`notify()` 不会直接释放锁

```
synchronized (lock) {
    lock.notifyAll();
    // 此时当前线程仍然持有 lock
}
```

被唤醒的线程必须等通知线程退出同步代码块、释放锁后，才有机会重新获取锁并继续执行。

### （3）为什么通常使用 `while` 检查条件？

```
synchronized (lock) {
    while (!finished) {
        lock.wait();
    }
}
```

线程被唤醒不代表等待条件一定成立，因此需要重新检查条件。使用 `while` 也可以应对虚假唤醒。

## 11.5 总结

- `sleep()`：让当前线程暂停一段时间，**不释放已经持有的监视器锁**。
    
- `wait()`：让当前线程等待，并**释放调用对象对应的监视器锁**。
    
- `wait()` 必须在持有对应监视器锁时调用，通常与 `synchronized` 配合使用。
    
- `notify()` 和 `notifyAll()` 用于通知等待线程，但不会直接释放锁，也不保证线程立即执行。

## 12. sleep() 会释放 CPU 吗？

调用 `Thread.sleep()` 后，线程会暂停执行并进入 `TIMED_WAITING` 状态，不再继续占用 CPU 执行该线程的任务。

但要区分两件事：

- **释放 CPU 执行机会**：线程休眠后，操作系统可以把 CPU 分配给其他可运行线程。
    
- **释放锁**：`sleep()` 不会自动释放线程已经持有的锁。
    

另外，休眠时间到达只意味着线程可以再次参与调度，不代表它一定会立即运行。

## 13. BLOCKED 和 WAITING 的区别

两者都表示线程暂时无法继续执行，但等待原因不同。

### BLOCKED

线程正在等待获取 `synchronized` 使用的监视器锁。

例如，线程 A 已持有 `lock`，线程 B 也想进入 `synchronized (lock)`，那么线程 B 可能进入 `BLOCKED` 状态。

### WAITING

线程正在无限期等待某种事件，例如：

- 调用 `Object.wait()` 等待通知。
    
- 调用 `Thread.join()` 等待另一个线程结束。
    
- 调用 `LockSupport.park()` 等待许可或其他唤醒条件。
    

**记忆重点：** `BLOCKED` 主要是等待进入 `synchronized` 监视器；`WAITING` 则可能是在等待通知、线程结束或其他协作条件。

## 14. wait() 状态下的线程如何恢复执行？

调用 `wait()` 后，线程可以通过以下情况结束等待：

- 其他线程调用同一个对象的 `notify()` 或 `notifyAll()`。
    
- 线程收到中断请求，等待操作抛出 `InterruptedException`。
    
- 带超时的 `wait()` 到达等待时间。
    
- 发生虚假唤醒。
    

但**结束等待不代表立即继续执行**。线程还需要重新获取原先释放的监视器锁。

例如：

```
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }

    // ready 为 true 后继续执行
}
```

这里使用 `while` 检查条件，而不是 `if`，是因为线程被唤醒后，条件可能仍然不满足，也可能发生虚假唤醒。

## 15. notify() 和 notifyAll() 的区别

两者都用于通知等待在同一个对象监视器上的线程。

|方法|作用|
|---|---|
|`notify()`|通知一个等待线程|
|`notifyAll()`|通知所有等待线程|

注意：

1. 调用它们时必须持有对应对象的监视器锁。
    
2. 调用通知方法不会立即释放锁。
    
3. 被通知的线程还需要重新竞争锁。
    
4. `notify()` 不保证选择最先等待的线程。
    
5. 被唤醒的线程仍然必须重新检查条件，因此通常应将 `wait()` 放在 `while` 循环中。
    

如果多个线程等待不同条件，而无法确定 `notify()` 选择的线程是否能够继续工作，使用 `notifyAll()` 通常更稳妥。

## 16. 线程间通信的方式

### 16.1 共享变量

多个线程通过共享变量传递状态或数据。

例如，使用 `volatile` 变量发布一个简单的状态变化：

```
private volatile boolean ready = false;
```

一个线程修改 `ready`，其他线程可以按照 `volatile` 的可见性规则观察到修改。

但 `volatile` 不能保证复合操作的原子性，也不能替代所有线程同步机制。

### 16.2 wait()、notify() 和 notifyAll()

通过对象监视器锁配合等待与通知，实现线程协作。

常见于生产者和消费者之间的协调。

### 16.3 Lock 和 Condition

`Condition` 配合 `Lock` 提供等待与通知功能。

|方法|作用|
|---|---|
|`await()`|等待条件满足|
|`signal()`|通知一个等待线程|
|`signalAll()`|通知所有等待线程|

调用 `await()` 前需要持有对应的锁；等待时会释放该锁，恢复执行前需要重新获取它。

### 16.4 BlockingQueue

`BlockingQueue` 是线程安全的阻塞队列。

例如：

- `put()`：队列满时，插入操作可以等待。
    
- `take()`：队列为空时，获取操作可以等待。
    

它适合生产者和消费者模式，能将线程间的数据传递与部分等待协调交给队列处理。

### 16.5 常见并发工具类

|工具类|主要作用|
|---|---|
|`CountDownLatch`|让一个或多个线程等待其他任务完成|
|`CyclicBarrier`|让一组线程相互等待，直到所有参与者到达屏障|
|`Semaphore`|限制同时访问某类资源的线程数量|

这些工具解决的问题不同，不应互相混淆。

## 17. Go 协程和 Java 线程的区别

Go 使用 goroutine，Java 主要提供平台线程和虚拟线程。

|对比项|Java 平台线程|Java 虚拟线程|Go goroutine|
|---|---|---|---|
|调度方式|主要由操作系统调度|由 JVM 调度到载体线程|由 Go 运行时调度|
|与操作系统线程的关系|通常一对一|大量虚拟线程可映射到较少的平台线程|大量 goroutine 可映射到较少的操作系统线程|
|资源开销|相对较高|通常较低|通常较低|
|适用场景|通用并发任务|大量阻塞等待的任务|大量并发任务|

注意：

- 虚拟线程与 goroutine 的调度思路有相似之处，但两者的实现并不完全相同。
    
- 虚拟线程和 goroutine 都不是无限制的资源。
    
- 轻量级并发模型不能自动提升 CPU 密集型任务的执行速度。
