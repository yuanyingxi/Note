# 1 事务的四种隔离级别

多个事务并发执行时，如果缺乏适当的隔离，可能出现脏读、不可重复读和幻读等问题。MySQL 提供四种标准事务隔离级别。

## 1.1 READ UNCOMMITTED：读未提交

一个事务尚未提交的修改，也可能被其他事务读取。

- 可能发生：脏读、不可重复读、幻读。
- 隔离程度最低。
- 理解重点：其他事务可以读到尚未提交的数据；如果修改事务之后回滚，读取方此前读到的内容就可能是无效数据。

## 1.2 READ COMMITTED：读已提交

一个事务只能读取其他事务已经提交的修改，不能读取其未提交的数据。

- 不会发生脏读。
- 仍可能发生不可重复读和幻读。
- 在 InnoDB 中，普通一致性读通常通过 MVCC 和 Read View 实现。**每次普通 `SELECT` 开始一致性读时，通常都会创建新的 Read View**，因此同一事务两次查询之间，如果其他事务提交了修改，后一次查询就可能看到新数据。

### 3. REPEATABLE READ：可重复读

在 InnoDB 中，同一个事务的普通快照读通常复用同一个 Read View，因此其他事务后来提交的修改，不会改变该快照读所能看到的数据版本。

- 不会发生脏读。
- 普通快照读通常不会因其他事务后来提交修改而改变查询结果。
- InnoDB 默认隔离级别是 `REPEATABLE READ`。
- 但要注意：**普通快照读的可重复性，不等于事务中所有类型的读操作都使用同一个快照。** `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等当前读相关操作，不能直接套用普通快照读的规则。

### 4. SERIALIZABLE：串行化

隔离程度最严格的隔离级别。对于发生冲突的并发读写操作，数据库会通过锁等机制使事务互相等待，让冲突操作表现得像按顺序执行。

- 可以避免脏读、不可重复读和幻读。
- 并发冲突时等待和锁竞争可能更多，吞吐量可能下降。
- 并不意味着整个数据库任何时刻只能运行一个事务；互不冲突的操作仍可能并发执行。

### 四种隔离级别对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 关键理解 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 可能读取未提交的数据 |
| READ COMMITTED | 不会 | 可能 | 可能 | 普通一致性读通常每次创建新的 Read View |
| REPEATABLE READ | 不会 | 普通快照读通常不会 | SQL 标准允许；InnoDB 还会结合 MVCC 与锁机制处理 | 普通快照读通常复用同一个 Read View |
| SERIALIZABLE | 不会 | 不会 | 不会 | 通过锁定和冲突等待实现更严格隔离 |

> 注意：表格中的“幻读”需要结合具体读操作理解。InnoDB 的普通快照读与范围锁定读采用的机制不同，不能只根据 SQL 标准的概括就推断所有 InnoDB 查询行为。

## 二、不同隔离级别下查询结果有什么区别？

假设账户表中有一条记录，余额最初是 100 万。事务 A 负责多次查询余额，事务 B 将余额修改为 200 万。

### 1. 读未提交

事务 B 把余额改成 200 万，但还没有提交；事务 A 就可能读取到 200 万。

如果事务 B 随后回滚，事务 A 之前读到的 200 万并不是最终有效的数据。这就是脏读。

### 2. 读已提交

事务 B 修改余额但尚未提交时，事务 A 仍只能读到已提交的 100 万。

等事务 B 提交之后，事务 A 后续开始的新一次普通 `SELECT` 就可以读到 200 万。因此，同一个事务的前后两次查询可能不同。

### 3. 可重复读

假设事务 A 已经通过第一次普通快照读建立了 Read View，之后事务 B 才把余额改成 200 万并提交。

- 事务 A 后续的普通快照读通常仍然看到 100 万。
- 事务 A 结束后，新事务建立新的快照，就可以看到 200 万。

关键点：**单独执行 `BEGIN` 并不意味着 InnoDB 一定立刻建立普通快照读使用的 Read View。** 在普通 RR 事务中，Read View 通常在第一次一致性读时建立；也可以使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 在事务开启时建立一致性快照。

### 4. 串行化

在显式多语句事务中，InnoDB 的 `SERIALIZABLE` 隔离级别会让普通 `SELECT` 采用类似锁定读的方式。当事务 A 的读操作与事务 B 的写操作发生冲突时，后者可能需要等待事务 A 结束。

因此，事务 A 在等待期间继续读取时不会看到事务 B 尚未执行的修改；待 A 结束、B 完成修改并提交后，后续事务才能读到新值。

## 三、MySQL 默认隔离级别与 autocommit

### 1. 默认隔离级别

MySQL InnoDB 默认隔离级别是：

```sql
REPEATABLE READ
```

可以查看当前会话的隔离级别：

```sql
SELECT @@transaction_isolation;
```

实际环境可能被修改，因此需要时应查看当前配置，而不是只记住默认值。

### 2. autocommit（自动提交）

MySQL 默认开启 `autocommit`。在没有显式开启事务的情况下，每条 SQL 通常作为一个独立事务执行并自动提交。

这意味着：连续执行多条普通 `SELECT`，并不一定是在同一个事务里，也不一定共享同一个 Read View。

如果需要让多条数据库操作处于同一个事务中，通常需要显式开启事务，并在完成后提交或回滚：

```sql
START TRANSACTION;

-- 多条数据库操作

COMMIT;
-- 如果需要撤销尚未提交的事务修改，可以使用 ROLLBACK
```

## 四、RR 下，事务 A 提交的数据，事务 B 能看见吗？

**不能只根据事务开启的先后顺序判断，要看 B 是否建立了快照，以及执行的是快照读还是当前读。**

### 情况一：B 已经建立 Read View，之后执行普通 SELECT

如果事务 A 在 B 的 Read View 建立之后才提交修改，那么 B 后续的普通快照读通常仍按旧 Read View 判断可见性，因此看不到 A 后来提交的版本。

### 情况二：B 只执行了 BEGIN，还没有进行第一次快照读

如果 A 在 B 第一次普通一致性读之前已经提交，那么 B 在建立 Read View 时就可能看到 A 已提交的数据。

### 情况三：B 执行当前读

例如：

```sql
SELECT * FROM users WHERE id = 1 FOR UPDATE;
```

这类锁定读读取当前记录并按规则加锁，不是简单地复用普通 SELECT 的旧快照。如果目标记录被其他事务持有冲突锁，当前读可能需要等待。

### 易错点

- RR 不代表事务一开始就必然固定了所有读取的快照。
- 普通 `SELECT` 通常是快照读。
- `SELECT ... FOR UPDATE` 是当前读相关操作。
- 事务自己做出的修改，对自己是可见的。
- 判断可见性时，必须说明具体使用的是哪一种读操作。

## 五、可重复读下的幻读案例

### 1. 什么是幻读？

事务在相同条件下重复查询，发现符合条件的记录集合发生了变化，就可能出现幻读。它不只是记录数量变化，也可能是符合条件的记录被另一批记录替换。

### 2. 执行过程

假设表 `t_stu` 中暂时没有 `id = 5` 的记录。

**事务 A：第一次普通快照读**

```sql
BEGIN;

SELECT * FROM t_stu WHERE id = 5;
-- 返回空结果
```

这次普通一致性读建立了 Read View。

**事务 B：插入并提交**

```sql
BEGIN;

INSERT INTO t_stu VALUES (5, '小美', 18);

COMMIT;
```

事务 B 已经提交了 `id = 5` 的记录。

**事务 A：执行 UPDATE，再查询**

```sql
UPDATE t_stu
SET name = '小林coding'
WHERE id = 5;

SELECT * FROM t_stu WHERE id = 5;
```

在原文这个案例中，`UPDATE` 使用当前读相关的机制，能够处理事务 B 已提交的当前记录。事务 A 修改该记录后，自己所做的修改对自己可见，因此后续普通 `SELECT` 能看到这条记录。

### 3. 为什么会出现前后不一致？

这不是 Read View 自动更新了，而是两类读操作的语义不同：

1. 第一次普通 `SELECT` 是快照读，旧快照中没有 `id = 5`。
2. `UPDATE` 属于当前读相关操作，针对当前记录执行更新。
3. 事务 A 自己修改后的版本对 A 可见。
4. 后续普通 `SELECT` 因而能看到 A 自己修改过的记录。

**如果事务 A 只重复执行相同条件的普通快照读，而不进行 UPDATE 等当前读相关操作，通常仍然看不到事务 B 后来插入的记录。**

这个案例说明：分析 RR 下的现象时，不能只看隔离级别，还要看读操作类型以及事务是否修改了记录。

## 六、MySQL InnoDB 在 RR 下如何处理幻读？

首先区分两种业务需求。

### 1. 只需要重复查询同一份快照

如果事务只是重复进行普通一致性读，InnoDB 通过 MVCC 和同一个 Read View，使这些快照查询通常保持一致，不会因为其他事务后来插入记录就改变快照结果。

### 2. 查询后还要修改，并且要阻止范围内出现新记录

如果业务要求先查询某个范围内的记录，再根据查询结果执行修改，而且需要防止其他事务在该范围插入新记录，就不能只依赖普通快照读。

可以在显式事务中使用锁定读，例如：

```sql
BEGIN;

SELECT id, balance
FROM accounts
WHERE balance >= 1000000
  AND balance < 2000000
FOR UPDATE;

-- 根据查询结果执行后续操作

COMMIT;
```

InnoDB 会根据索引和实际扫描范围，使用相应的记录锁、间隙锁或 Next-Key Lock。锁通常会持有到事务结束。

### 3. 三种锁的基本概念

- **记录锁（Record Lock）**：锁定索引中的某条记录。
- **间隙锁（Gap Lock）**：锁定索引记录之间的间隙，主要用于阻止其他事务向相应间隙插入记录。
- **Next-Key Lock（临键锁）**：通常可以理解为记录锁与其前方间隙锁的组合，用于锁定索引记录及相关间隙。

实际加锁范围取决于查询条件、索引结构和执行计划：

- 并非每次 `SELECT ... FOR UPDATE` 都一定加 Next-Key Lock。
- 对存在记录的唯一索引等值查询，可能只需要记录锁。
- 缺少合适索引时，扫描和加锁范围可能扩大。
- 锁定读会增加并发事务之间的等待，因此应根据业务需要使用。

## 七、串行化隔离级别是通过什么实现的？

对于 InnoDB，在 `SERIALIZABLE` 隔离级别下，如果使用显式多语句事务，普通 `SELECT` 会隐式变成类似 `SELECT ... FOR SHARE` 的锁定读。

这类读操作会使用共享记录锁或 Next-Key Lock 等机制，与其他事务的冲突写操作形成互斥。

### 示例理解

- 事务 A 读取一段记录，并持有相应的锁。
- 事务 B 想修改被锁住的记录，或者向被锁定的间隙插入数据。
- 如果操作与 A 持有的锁冲突，B 就需要等待。
- A 提交或回滚、释放锁之后，B 才能继续执行。

因此，串行化通过锁和冲突等待，使并发事务的效果更接近按顺序执行，避免脏读、不可重复读和幻读。

### 两个补充点

1. **串行化不等于全库只能同时执行一个事务。** 不发生锁冲突的操作仍然可以并发。
2. 如果开启 `autocommit`，而某条 `SELECT` 本身就是一个独立的只读事务，InnoDB 可以使用非锁定一致性读完成它。判断 SERIALIZABLE 的行为时，需要结合是否处于显式多语句事务等具体条件。

### 面试回答模板

**问：MySQL 的 SERIALIZABLE 隔离级别是怎么实现的？**

答：InnoDB 在 SERIALIZABLE 隔离级别下，会对显式多语句事务中的普通查询采用类似 `SELECT ... FOR SHARE` 的锁定读方式，通过共享记录锁或 Next-Key Lock 与冲突的写操作互斥。其他事务如果要修改被锁定的记录，或向被锁定的间隙插入数据，就需要等待当前事务结束。这样可以避免脏读、不可重复读和幻读，但会增加锁竞争和事务等待。
