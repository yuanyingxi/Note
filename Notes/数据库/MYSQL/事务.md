# 1 事务的特性是什么？如何实现的？
## 1.1 什么是事务？

事务（Transaction）是数据库操作的一个逻辑单元，可以将多条 SQL 语句作为一个整体执行。

例如，A 向 B 转账 200 元，需要执行两个操作：

1. A 的账户余额减少 200 元。
    
2. B 的账户余额增加 200 元。
    

这两个操作必须作为一个整体执行，不能出现 A 扣款成功、B 却没有收到钱的情况。

```
START TRANSACTION;

UPDATE account
SET balance = balance - 200
WHERE id = 'A';

UPDATE account
SET balance = balance + 200
WHERE id = 'B';

COMMIT;
```

如果事务执行失败，需要撤销本次事务的修改，可以使用：

```
ROLLBACK;
```

- `COMMIT`：提交事务，使事务的修改正式生效。
    
- `ROLLBACK`：回滚事务，撤销事务中尚未提交的修改。
    

注意：SQL 执行报错不一定意味着整个事务都会自动回滚，应用程序需要正确处理异常，并根据具体情况提交或回滚事务。

## 1.2 ACID 四大特性

ACID 是事务的四个核心特性。

| 特性              | 中文名称 | 含义                     | InnoDB 主要实现机制      |
| --------------- | ---- | ---------------------- | ------------------ |
| A - Atomicity   | 原子性  | 事务中的操作要么全部生效，要么全部撤销    | Undo Log           |
| C - Consistency | 一致性  | 事务执行前后，数据满足约束和业务规则     | 由数据库机制、约束及业务逻辑共同保证 |
| I - Isolation   | 隔离性  | 控制并发事务之间的相互影响          | MVCC、锁机制           |
| D - Durability  | 持久性  | 事务提交成功后，修改能够在系统故障恢复后保留 | Redo Log 等持久化机制    |

### 1.2.1 原子性（Atomicity）

**含义：事务中的操作要么全部完成，要么全部撤销。**

例如，转账过程中 A 已经扣款，但 B 尚未入账。如果事务回滚，需要撤销 A 的扣款。

**实现机制：Undo Log（回滚日志）**

Undo Log 记录用于撤销修改的信息，使数据库能够将数据恢复到修改之前的状态。

### 1.2.2 一致性（Consistency）

**含义：事务执行前后，数据都应该满足预先定义的约束和业务规则。**

例如，A 向 B 转账 200 元，在没有其他资金变动的情况下，转账前后两个人的账户余额总和应当保持不变。

一致性不是由某个单独的日志实现的，而是由原子性、隔离性、持久性、数据库约束以及正确的业务逻辑等共同保证的。

### 1.2.3 隔离性（Isolation）

**含义：多个事务并发执行时，控制它们之间的相互影响。**

例如，事务 A 修改账户余额但尚未提交，事务 B 此时读取余额，能否看到事务 A 的修改，取决于事务隔离级别及具体的读取方式。

**实现机制：MVCC + 锁机制**

- MVCC：通过多个数据版本和可见性规则，控制事务读取哪个版本的数据。
    
- 锁机制：协调存在冲突的并发操作，避免多个事务不恰当地同时修改数据。
    

### 1.2.4 持久性（Durability）

**含义：事务一旦成功提交，其修改就应当在系统发生故障后得到保留。**

例如，转账事务已经提交，但相关数据页还没有全部写入磁盘。即使此时数据库发生崩溃，也应当能够恢复已经提交的修改。

**实现机制：Redo Log（重做日志）**

Redo Log 记录用于恢复数据修改的信息。数据库发生崩溃后，可以通过重做日志恢复已经提交、但尚未全部写入数据文件的修改。

## 1.3 Undo Log 和 Redo Log 的区别

|对比项|Undo Log|Redo Log|
|---|---|---|
|中文名称|回滚日志|重做日志|
|主要作用|撤销修改、支持回滚|崩溃恢复|
|主要关联特性|原子性|持久性|
|核心思想|恢复修改前的状态|重做需要恢复的修改|

补充：Undo Log 还会参与 MVCC 的历史版本构建，因此它不仅用于事务回滚，也是 InnoDB 多版本并发控制的重要基础。

## 1.4 面试回答模板

MySQL InnoDB 事务具有 ACID 四大特性。原子性主要通过 Undo Log 实现，持久性主要依靠 Redo Log，隔离性主要通过 MVCC 和锁机制实现，而一致性则由这些机制、数据库约束和正确的业务逻辑共同保证。

**记忆口诀：原子性 Undo，一致性共同保证，隔离性 MVCC 加锁，持久性 Redo。**

# 2. MySQL 可能出现什么并发问题？

多个客户端可以同时访问数据库，因此多个事务可能同时读取或修改同一份数据。如果并发控制不足，就可能出现脏读、不可重复读和幻读等问题。

## 2.1 脏读（Dirty Read）

**定义：一个事务读取到了另一个事务尚未提交的数据。**

例如，账户原本有 100 元。

|时间|事务 A|事务 B|
|---|---|---|
|T1|开始事务||
|T2|将余额修改为 50 元，但未提交||
|T3||读取余额，得到 50 元|
|T4|回滚，余额恢复为 100 元||
|T5||此前读取的 50 元实际上并未正式生效|

问题：事务 B 读到了事务 A 尚未提交的修改，但事务 A 最终又回滚了。

**判断关键词：读取了其他事务尚未提交的数据。**

## 2.2 不可重复读（Non-repeatable Read）

**定义：同一个事务中，两次读取同一条记录，得到的结果不一致。**

例如：

|时间|事务 A|事务 B|
|---|---|---|
|T1|查询余额，结果为 100 元||
|T2||将余额修改为 200 元并提交|
|T3|再次查询余额，结果为 200 元||

事务 A 在同一个事务期间，对同一条记录进行了两次读取，但读取结果不同。

**判断关键词：同一条记录的值发生变化。**

## 2.3 幻读（Phantom Read）

**定义：同一个事务中，使用相同的条件重复查询，符合条件的记录集合发生了变化。**

例如，事务 A 执行：

```
SELECT *
FROM account
WHERE balance >= 100;
```

第一次查询得到 3 条记录。

随后，事务 B 插入一条满足 `balance >= 100` 的记录并提交。

事务 A 再次执行相同查询时，可能发现结果中多了一条记录。

这就像原来的查询结果中突然出现了一条新记录，因此称为幻读。

**判断关键词：相同查询条件对应的记录集合发生变化。**

## 2.4 三种并发问题的区别

| 问题    | 核心现象              | 记忆关键词 |
| ----- | ----------------- | ----- |
| 脏读    | 读取了其他事务尚未提交的数据    | 未提交   |
| 不可重复读 | 同一条记录前后读取的值不同     | 记录值   |
| 幻读    | 相同条件前后查询得到的记录集合不同 | 记录集合  |

注意：

- 不可重复读关注同一条记录的值是否发生变化。
    
- 幻读关注某个查询条件对应的记录集合是否发生变化。
    
- 在实际场景中，具体现象还需要结合隔离级别和读取方式判断。
    

## 2.5 如何区分这三种问题？

记忆方法：

- **脏读：读到了不该读取的未提交数据。**
    
- **不可重复读：同一条记录，两次读取的值不一样。**
    
- **幻读：同一个查询条件，两次查询的记录集合不一样。**
    

# 3. 哪些场景不适合脏读？举个例子

脏读的主要问题是：事务可能基于尚未正式生效的数据进行后续业务处理。

如果数据随后被回滚，先前的判断就可能失去依据。

|业务场景|可能出现的问题|为什么要避免脏读|
|---|---|---|
|银行转账|读取了尚未提交的账户余额|用户可能看到临时余额，并据此作出错误判断|
|库存管理|读取了尚未提交的库存数量|系统可能基于临时库存作出错误决策|
|订单系统|读取了尚未提交的订单状态|页面或后续业务可能处理错误的订单状态|

### 面试回答模板

银行系统、库存管理系统和订单系统都不适合出现脏读。

例如，某个事务正在修改账户余额，但还没有提交，另一个事务就读取了修改后的余额。如果前一个事务最终回滚，读取方得到的就是未正式生效的数据，可能导致后续业务判断错误。

因此，如果目标是避免脏读，至少需要采用读已提交（Read Committed）隔离级别。

注意：读已提交只能解决脏读问题，并不能完全解决不可重复读和幻读。

# 4. MySQL 是怎么解决并发问题的？

MySQL InnoDB 主要通过以下三种机制协调并发事务：

1. 锁机制
    
2. 事务隔离级别
    
3. MVCC（多版本并发控制）
    

三者相互配合，共同控制并发事务之间的相互影响。

## 4.1 锁机制（Lock）

**作用：协调存在冲突的并发操作，控制事务访问共享数据的方式。**

例如，两个事务同时修改同一个账户的余额：

- 事务 A 正在修改账户记录。
    
- 事务 B 也想修改这条记录。
    
- 如果两者的操作存在冲突，事务 B 可能需要等待事务 A 释放相应的锁。
    

锁可以防止多个事务不恰当地同时修改同一份数据。

但并不是所有操作都需要排队。InnoDB 的普通快照读通常可以通过 MVCC 读取符合可见性规则的历史版本，而不必等待其他事务持有的排他锁。

**核心记忆：锁主要负责协调存在冲突的访问和修改操作。**

## 4.2 事务隔离级别（Isolation Level）

**作用：规定并发事务之间的数据可见性和隔离程度。**

MySQL 常见的四种事务隔离级别：

|隔离级别|英文名称|脏读|不可重复读|幻读|
|---|---|---|---|---|
|读未提交|Read Uncommitted|可能|可能|可能|
|读已提交|Read Committed|避免|可能|可能|
|可重复读|Repeatable Read|避免|避免|与读取方式和 InnoDB 实现有关|
|串行化|Serializable|避免|避免|避免|

说明：

- 上表用于概括常见隔离级别的行为。
    
- SQL 标准对可重复读级别仍允许幻读。
    
- InnoDB 的可重复读通过 MVCC 和锁机制处理幻读相关场景：普通一致性读使用事务快照；锁定读或当前读可能涉及间隙锁、临键锁等机制。
    
- 因此，不能简单认为可重复读隔离级别下，所有读取方式都使用同一个快照，也不能仅根据隔离级别名称判断所有并发行为。
    

隔离级别越严格，通常越能限制事务间的相互影响，但也可能增加锁竞争和事务等待。

**核心记忆：隔离级别决定数据库如何限制并发事务之间的相互影响。**

## 4.3 MVCC（Multi-Version Concurrency Control）

MVCC 的全称是 Multi-Version Concurrency Control，即多版本并发控制。

**核心思想：通过保存和管理数据的多个版本，让事务根据相应的可见性规则读取合适的数据版本。**

例如，某条账户记录最初的余额为 100 元。

事务 A 将余额修改为 200 元，但尚未提交。

在使用合适隔离级别的普通快照读场景中，事务 B 可以读取符合自身可见性规则的历史版本，例如仍然看到 100 元，而不必直接读取事务 A 尚未提交的修改。

这能够减少普通读取与写入操作之间不必要的阻塞。

### 4.3.1 MVCC 的主要作用

- 为事务读取数据提供版本可见性控制。
    
- 让某些普通读取不必等待其他事务完成写入。
    
- 配合 Undo Log 保存和访问历史版本。
    
- 降低部分读写冲突，提高并发访问能力。
    

### 4.3.2 MVCC 并不意味着所有读取都不需要锁

需要区分两种常见读取方式：

**普通快照读：**

```
SELECT *
FROM account
WHERE id = 'A';
```

在适用的事务隔离级别下，普通 `SELECT` 通常按照一致性读的规则读取数据版本。

**当前读（锁定读）：**

```
SELECT *
FROM account
WHERE id = 'A'
FOR UPDATE;
```

当前读需要读取相应的当前记录，并可能加锁，以便协调后续修改操作。

因此，MVCC 并不能代替所有锁机制。

**核心记忆：MVCC 主要通过数据多版本和可见性规则支持并发读取，锁机制则负责协调存在冲突的访问和修改。**

## 4.4 三种机制之间的关系

|机制|主要解决的问题|核心作用|
|---|---|---|
|锁机制|并发操作之间的冲突|控制冲突操作的执行|
|事务隔离级别|事务间相互影响的程度|规定并发事务的隔离规则|
|MVCC|并发读取和数据版本可见性|让事务读取符合规则的数据版本|

三者并不是各自独立地解决某一个固定问题，而是相互配合的。

例如：

- 隔离级别决定事务读取数据时遵循什么可见性规则。
    
- MVCC 为普通一致性读提供多版本支持。
    
- 锁机制协调存在冲突的写入，以及需要锁定的读取操作。
    

## 4.5 快照读和当前读

- **快照读（Snapshot Read）**：普通 `SELECT` 通常属于快照读，通过 MVCC 和 Read View 读取符合可见性规则的数据版本，不一定是最新数据。
    
- **当前读（Current Read）**：读取当前可读取的记录版本，并通过锁机制协调并发操作。`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等通常涉及当前读。
    

| 类型  | 典型操作                                      | 核心特点               |
| --- | ----------------------------------------- | ------------------ |
| 快照读 | 普通 `SELECT`                               | 按 Read View 读取可见版本 |
| 当前读 | `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` | 处理当前记录，必要时加锁       |

## 4.6 面试回答模板

MySQL InnoDB 主要通过锁机制、事务隔离级别和 MVCC 来控制并发问题。

首先，**事务隔离级别**决定**并发事务之间的隔离程度**；其次，**MVCC** 通过**多版本和可见性规则支持**并发读取，减少读写操作之间不必要的阻塞；最后，锁机制协调存在冲突的操作，避免不恰当的并发修改。这些机制相互配合，共同维护事务的隔离性和数据的一致性。

# 5 事务的四种隔离级别

多个事务并发执行时，如果缺乏适当的隔离，可能出现脏读、不可重复读和幻读等问题。MySQL 提供四种标准事务隔离级别。

## 5.1 READ UNCOMMITTED：读未提交

一个事务尚未提交的修改，也可能被其他事务读取。

- 可能发生：脏读、不可重复读、幻读。
- 隔离程度最低。
- 理解重点：其他事务可以读到尚未提交的数据；如果修改事务之后回滚，读取方此前读到的内容就可能是无效数据。

## 5.2 READ COMMITTED：读已提交

一个事务只能读取其他事务已经提交的修改，不能读取其未提交的数据。

- 不会发生脏读。
- 仍可能发生不可重复读和幻读。
- 在 InnoDB 中，普通一致性读通常通过 MVCC 和 Read View 实现。**每次普通 `SELECT` 开始一致性读时，通常都会创建新的 Read View**，因此同一事务两次查询之间，如果其他事务提交了修改，后一次查询就可能看到新数据。

**Read View 是“判断哪个版本可见的规则”，能看到“Read View 创建之前已提交的版本” + “自己事务改的版本（即使未提交）”；看不到“创建之后才提交的”和“别人未提交的”。这样设计是为了保证可重复读、避免脏读，同时让逻辑正常（自己改的能看到）。**

## 5.3 REPEATABLE READ：可重复读

在 InnoDB 中，同一个事务的普通快照读通常**复用同一个 Read View**，因此其他事务后来提交的修改，不会改变该快照读所能看到的数据版本。

- 不会发生脏读。
- 普通快照读通常不会因其他事务后来提交修改而改变查询结果。
- InnoDB 默认隔离级别是 `REPEATABLE READ`。
- 但要注意：**普通快照读的可重复性，不等于事务中所有类型的读操作都使用同一个快照。** `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等当前读相关操作，不能直接套用普通快照读的规则。

## 5.4 SERIALIZABLE：串行化

隔离程度最严格的隔离级别。对于发生冲突的并发读写操作，数据库会通过锁等机制使事务互相等待，让冲突操作表现得像按顺序执行。

- 可以避免脏读、不可重复读和幻读。
- 并发冲突时等待和锁竞争可能更多，吞吐量可能下降。
- 并不意味着整个数据库任何时刻只能运行一个事务；互不冲突的操作仍可能并发执行。

### 四种隔离级别对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 关键理解 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 可能读取未提交的数据 |
| READ COMMITTED | 不会 | 可能 | 可能 | 普通一致性读通常每次创建新的 Read View |
| REPEATABLE READ | 不会 | 普通快照读通常不会 | SQL 标准允许；InnoDB 还会结合 MVCC 与锁机制处理 | 普通快照读通常复用同一个 Read View |
| SERIALIZABLE | 不会 | 不会 | 不会 | 通过锁定和冲突等待实现更严格隔离 |

> 注意：表格中的“幻读”需要结合具体读操作理解。InnoDB 的普通快照读与范围锁定读采用的机制不同，不能只根据 SQL 标准的概括就推断所有 InnoDB 查询行为。

# 6 不同隔离级别下查询结果有什么区别？

假设账户表中有一条记录，余额最初是 100 万。事务 A 负责多次查询余额，事务 B 将余额修改为 200 万。

## 6.1 读未提交

事务 B 把余额改成 200 万，但还没有提交；事务 A 就可能读取到 200 万。

如果事务 B 随后回滚，事务 A 之前读到的 200 万并不是最终有效的数据。这就是脏读。

## 6.2 读已提交

事务 B 修改余额但尚未提交时，事务 A 仍只能读到已提交的 100 万。

等事务 B 提交之后，事务 A 后续开始的新一次普通 `SELECT` 就可以读到 200 万。因此，同一个事务的前后两次查询可能不同。

## 6.3 可重复读

假设事务 A 已经通过第一次普通快照读建立了 Read View，之后事务 B 才把余额改成 200 万并提交。

- 事务 A 后续的普通快照读通常仍然看到 100 万。
- 事务 A 结束后，新事务建立新的快照，就可以看到 200 万。

关键点：**`BEGIN` 只表示“事务开始了”**，**单独执行 `BEGIN` 并不意味着 InnoDB 一定立刻建立普通快照读使用的 Read View。** 在普通 RR 事务中，Read View 通常在第一次一致性读时建立；也可以使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 在事务开启时建立一致性快照。

## 6.4 串行化

在显式多语句事务中，InnoDB 的 `SERIALIZABLE` 隔离级别会让普通 `SELECT` 采用类似锁定读的方式。当事务 A 的读操作与事务 B 的写操作发生冲突时，后者可能需要等待事务 A 结束。

因此，事务 A 在等待期间继续读取时不会看到事务 B 尚未执行的修改；待 A 结束、B 完成修改并提交后，后续事务才能读到新值。

# 7 MySQL 默认隔离级别与 autocommit

## 7.1 默认隔离级别

MySQL InnoDB 默认隔离级别是：

```sql
REPEATABLE READ
```

可以查看当前会话的隔离级别：

```sql
SELECT @@transaction_isolation;
```

实际环境可能被修改，因此需要时应查看当前配置，而不是只记住默认值。

## 7.2 autocommit（自动提交）

MySQL 默认开启 `autocommit`。在没有显式开启事务的情况下，**每条 SQL 通常作为一个独立事务执行并自动提交。**

这意味着：连续**执行多条普通 `SELECT`**，并**不一定是在同一个事务**里，也**不一定共享同一个 Read View**。

如果需要让多条数据库操作处于同一个事务中，通常需要**显式开启事务**，并在完成后提交或回滚：

```sql
START TRANSACTION;

-- 多条数据库操作

COMMIT;
-- 如果需要撤销尚未提交的事务修改，可以使用 ROLLBACK
```

# 8 RR 下，事务 A 提交的数据，事务 B 能看见吗？

**不能只根据事务开启的先后顺序判断，要看 B 是否建立了快照，以及执行的是快照读还是当前读。**

### 情况一：B 已经建立 Read View，之后执行普通 SELECT

如果事务 A 在 B 的 Read View 建立之后才提交修改，那么 B 后续的普通快照读通常仍按旧 Read View 判断可见性，因此看不到 A 后来提交的版本。

### 情况二：B 只执行了 BEGIN，还没有进行第一次快照读

如果 A 在 B 第一次普通一致性读之前已经提交，那么 B 在建立 Read View 时就可能看到 A 已提交的数据。

### 情况三：B 执行当前读

例如：

```sql
SELECT * FROM users WHERE id = 1 FOR UPDATE;
```

这类锁定读读取当前记录并按规则加锁，不是简单地复用普通 SELECT 的旧快照。如果目标记录被其他事务持有冲突锁，当前读可能需要等待。

### 易错点

- RR 不代表事务一开始就必然固定了所有读取的快照。
- 普通 `SELECT` 通常是快照读。
- `SELECT ... FOR UPDATE` 是当前读相关操作。
- 事务自己做出的修改，对自己是可见的。
- 判断可见性时，必须说明具体使用的是哪一种读操作。

# 9 可重复读下的幻读案例
## 9.1 什么是幻读？

事务在相同条件下重复查询，发现符合条件的记录集合发生了变化，就可能出现幻读。它不只是记录数量变化，也可能是符合条件的记录被另一批记录替换。

## 9.2 执行过程

假设表 `t_stu` 中暂时没有 `id = 5` 的记录。

**事务 A：第一次普通快照读**

```sql
BEGIN;

SELECT * FROM t_stu WHERE id = 5;
-- 返回空结果
```

这次普通一致性读建立了 Read View。

**事务 B：插入并提交**

```sql
BEGIN;

INSERT INTO t_stu VALUES (5, '小美', 18);

COMMIT;
```

事务 B 已经提交了 `id = 5` 的记录。

**事务 A：执行 UPDATE，再查询**

```sql
UPDATE t_stu
SET name = '小林coding'
WHERE id = 5;

SELECT * FROM t_stu WHERE id = 5;
```

在原文这个案例中，`UPDATE` 使用当前读相关的机制，能够处理事务 B 已提交的当前记录。事务 A 修改该记录后，自己所做的修改对自己可见，因此后续普通 `SELECT` 能看到这条记录。

## 9.3 为什么会出现前后不一致？

这不是 Read View 自动更新了，而是两类读操作的语义不同：

1. 第一次普通 `SELECT` 是快照读，旧快照中没有 `id = 5`。
2. `UPDATE` 属于当前读相关操作，针对当前记录执行更新。
3. 事务 A 自己修改后的版本对 A 可见。
4. 后续普通 `SELECT` 因而能看到 A 自己修改过的记录。

**如果事务 A 只重复执行相同条件的普通快照读，而不进行 UPDATE 等当前读相关操作，通常仍然看不到事务 B 后来插入的记录。**

**即：在 RR 隔离级别下，即使 Read View 没变，只要事务内部通过 `UPDATE`（当前读）改了数据，就可能打破快照读的“可重复性”，从而在后续普通 SELECT 中看到“幻影”记录。

**Read View 没变，但版本链变了**——Read View 不是“数据副本”，它只是“判断可见性的规则”。查数据时，是拿这个规则去**当前的版本链**里挑版本。UPDATE 之后，版本链里多了一个“**自己改的新版本**”，而**可见性规则里“自己改的对自己可见”优先级最高**，所以这个新版本被挑中，查询就能看到它。所以不是“快照变了”，是“**版本链变了 + 自己改的可见规则生效**”。

# 10 MySQL InnoDB 在 RR 下如何处理幻读？

首先区分两种业务需求。

## 10.1 只需要重复查询同一份快照

如果事务只是重复进行**普通一致性读（即没有写的动作）**，InnoDB 通过 MVCC 和同一个 Read View，使这些快照查询通常保持一致，不会因为其他事务后来插入记录就改变快照结果。

## 10.2 查询后还要修改，并且要阻止范围内出现新记录

#### 在 RR 下幻读的情况

- **只进行普通快照读**：InnoDB 在 RR 隔离级别下通常复用同一个 Read View，因此其他事务后来插入并提交的记录不会出现在原来的快照中。
    
- **查询后还要修改，且需要防止其他事务插入新记录**：可以使用 `SELECT ... FOR UPDATE` 等锁定读。InnoDB 根据索引和扫描范围，可能使用记录锁、间隙锁或 Next-Key Lock，防止相关范围内发生冲突操作。

可以在显式事务中使用**锁定读**。`SELECT ... FOR UPDATE` 是为了在**读取数据**后，**防止其他事务并发修改相关记录，避免后续操作基于过时的数据**，同时也能在适当的范围内防止其他事务插入新记录。例如：

```sql
BEGIN;

SELECT id, balance
FROM accounts
WHERE balance >= 1000000
  AND balance < 2000000
FOR UPDATE;  -- 读的同时加锁

-- 根据查询结果执行后续操作

COMMIT;
```

InnoDB 会根据索引和实际扫描范围，使用相应的记录锁、间隙锁或 Next-Key Lock。锁通常会持有到事务结束。

## 10.3 三种锁的基本概念

- **记录锁（Record Lock）**：锁定索引中的某条记录（索引记录是索引树上的一个条目）。
- **间隙锁（Gap Lock）**：锁定索引记录之间的间隙，主要用于阻止其他事务向相应间隙插入记录。
- **Next-Key Lock（临键锁）**：通常可以理解为**记录锁与其前方间隙锁的组合**，用于锁定索引记录及相关间隙。

实际加锁范围取决于查询条件、索引结构和执行计划：

- 并非每次 `SELECT ... FOR UPDATE` 都一定加 Next-Key Lock。
- 对存在记录的唯一索引等值查询，可能只需要记录锁。
- 缺少合适索引时，扫描和加锁范围可能扩大。
- 锁定读会增加并发事务之间的等待，因此应根据业务需要使用。

# 11 串行化隔离级别是通过什么实现的？

对于 InnoDB，在 `SERIALIZABLE` 隔离级别下，如果使用显式多语句事务，普通 `SELECT` 会隐式变成类似 `SELECT ... FOR SHARE` 的锁定读。

这类读操作会使用共享记录锁或 Next-Key Lock 等机制，与其他事务的冲突写操作形成互斥。

### 示例理解

- 事务 A 读取一段记录，并持有相应的锁。
- 事务 B 想修改被锁住的记录，或者向被锁定的间隙插入数据。
- 如果操作与 A 持有的锁冲突，B 就需要等待。
- A 提交或回滚、释放锁之后，B 才能继续执行。

因此，串行化通过锁和冲突等待，使并发事务的效果更接近按顺序执行，避免脏读、不可重复读和幻读。

### 两个补充点

1. **串行化不等于全库只能同时执行一个事务。** 不发生锁冲突的操作仍然可以并发。
2. 如果开启 `autocommit`，而某条 `SELECT` 本身就是一个独立的只读事务，InnoDB 可以使用非锁定一致性读完成它。判断 SERIALIZABLE 的行为时，需要结合是否处于显式多语句事务等具体条件。

### 面试回答模板

**问：MySQL 的 SERIALIZABLE 隔离级别是怎么实现的？**

答：InnoDB 在 SERIALIZABLE 隔离级别下，会对显式多语句事务中的普通查询采用类似 `SELECT ... FOR SHARE` 的锁定读方式，通过共享记录锁或 Next-Key Lock 与冲突的写操作互斥。其他事务如果要修改被锁定的记录，或向被锁定的间隙插入数据，就需要等待当前事务结束。这样可以避免脏读、不可重复读和幻读，但会增加锁竞争和事务等待。
