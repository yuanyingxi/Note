# 1 什么是消息队列 MQ？
## 1.1 消息队列的定义

消息队列（MQ，Message Queue）是一种用于系统间消息传递的中间件，主要负责接收、存储和转发消息，使生产者与消费者可以通过消息进行通信。

MQ 的核心作用可以概括为：**发送消息、存储消息、消费消息。**

基本模型：

```
生产者 Producer
      |
      | 1. 发送消息
      v
消息中间件 MQ / Broker
      |
      | 2. 存储、转发消息
      v
消费者 Consumer
      |
      | 3. 处理消息
      v
业务处理完成
```

|角色|作用|
|---|---|
|生产者 Producer|产生消息并将消息发送给 MQ|
|消息中间件 Broker|接收、存储和转发消息，供消费者处理|
|消费者 Consumer|获取消息并执行相应业务逻辑|

例如，用户支付成功后，订单服务发送一条支付成功消息，物流服务、积分服务和短信服务可以分别消费这条消息，执行发货、增加积分和发送通知等操作。

常见的开源消息中间件包括：

- **RocketMQ**：适用于订单、支付等业务消息处理场景。
    
- **RabbitMQ**：支持灵活的消息路由和任务分发。
    
- **Kafka**：常用于日志采集、大规模数据传输和流式处理。
    

注意：MQ 并不只是一个简单的先进先出队列。不同消息中间件的消息存储、路由、投递和消费机制有所不同。

# 2 为什么需要消息队列？

引入 MQ 的三个核心目的：

1. 解耦（Decoupling）
    
2. 异步（Asynchronization）
    
3. 削峰填谷（Traffic Shaping）
    

## 2.1 解耦：降低系统之间的直接依赖
### 2.1.1 没有 MQ：同步调用模式

假设电商系统中，用户支付成功后，需要执行以下操作：

- 通知物流服务发货。
    
- 通知积分服务增加积分。
    
- 通知优惠券服务发放优惠券。
    
- 通知短信服务发送支付通知。
    

如果订单服务通过 RPC 逐个调用这些服务，就会产生较强的直接依赖。

存在的问题：

1. **扩展不方便：** 新增一个下游服务时，订单服务通常需要增加相应的调用逻辑。
    
2. **维护成本较高：** 下游接口发生变化，可能需要修改订单服务。
    
3. **故障容易传递：** 下游服务响应缓慢或发生故障，可能拖慢甚至影响订单主流程。
    

### 2.1.2 引入 MQ：消息驱动模式

```
订单服务
   |
   | 发送支付成功消息
   v
  MQ
   |
   +----> 物流服务：发货
   |
   +----> 积分服务：增加积分
   |
   +----> 优惠券服务：发放优惠券
   |
   +----> 短信服务：发送通知
```

订单服务只需要发送一条描述支付成功事件的消息，**下游服务根据约定订阅并处理消息**。

优点：

- **降低直接依赖：** 订单服务不必逐个调用所有下游服务。
    
- **便于扩展：** 新增消费者时，通常不需要修改订单服务的调用逻辑。
    
- **隔离部分故障：** 下游服务暂时不可用时，已可靠保存的消息可以等待后续处理，而不必立即阻塞订单主流程。
    

注意：解耦并不意味着系统之间完全没有依赖。生产者和消费者仍然需要约定消息的字段、格式和业务含义，并保证消息可靠发送。

## 2.2 异步：缩短主流程的响应时间

假设支付成功后，需要依次调用三个非核心服务，每个服务耗时约 50ms。

没有 MQ 时：

```
支付成功
   |
   v
调用积分服务       50ms
   |
   v
调用优惠券服务     50ms
   |
   v
调用短信服务       50ms
   |
   v
返回响应
```

在串行调用且暂不考虑其他开销的情况下，下游调用总耗时约为 150ms。订单服务必须等待这些调用结束后，才能完成整个同步流程。

引入 MQ 后：

```
支付成功
   |
   v
完成主流程的必要操作
   |
   v
发送消息到 MQ
   |
   v
返回主流程响应

              MQ
               |
        +------+------+ 
        |      |      |
        v      v      v
      增加积分 发优惠券 发短信
         后台异步处理
```

订单服务发送消息后，不必同步等待积分、优惠券和短信业务全部完成，就可以返回响应。

优点：

- 缩短主流程的响应时间。
    
- 减少主流程对非核心服务响应速度的依赖。
    
- 让主流程与后续业务独立执行。
    

注意：

1. 发送消息本身仍需要时间，具体取决于网络和消息确认机制。
    
2. 异步不代表业务一定会立即执行，也不代表一定成功。
    
3. 如果业务要求某项操作完成后才能返回，就不能随意将其异步化。
    
4. 必须明确接口返回的是“任务已接收”还是“业务已处理完成”。
    

## 2.3 削峰填谷：缓冲突发流量

削峰填谷是 MQ 在高并发场景中的重要作用，目的是**缓冲短时间内突然出现的大量任务**，让下游根据自身的实际处理能力逐步消费。

要理解这个作用，需要先理解什么是**系统压力**，以及**为什么流量过大可能导致系统不可用**。

# 3 什么是系统压力？为什么请求过多会导致系统崩溃？
## 3.1 什么是系统压力？

在后端开发中，**系统压力**通常是指请求处理过程对 **CPU、内存、线程池、数据库连接、磁盘 I/O 等有限资源造成的负载**。

系统压力不仅与请求数量有关，还与单个请求的计算量、数据库操作、等待时间以及并发程度有关。

例如，同样是 1,000 个请求：

- 如果每个请求只读取一个简单的缓存，可能很容易处理。
    
- 如果每个请求都需要执行复杂 SQL、访问多个下游服务或进行大量计算，系统就可能承受更大的压力。
    

因此，关键不是请求数量本身，而是：

**请求到达速度和资源消耗是否超过了系统能够持续处理的能力。**

## 3.2 什么是系统处理能力？

**系统处理能力**，可以理解为：**在一定的硬件资源、业务逻辑和配置条件下，系统能够持续、稳定地完成多少请求**。

例如，某个订单数据库在特定 SQL、数据量和硬件条件下，每秒能够稳定完成约 2,000 个订单任务。

这表示特定条件下的处理吞吐量，并不意味着数据库在所有情况下都只能接受 2,000 个请求。

系统的处理能力可能受到以下因素限制：

| 资源        | 可能出现的问题                       |
| --------- | ----------------------------- |
| CPU       | 计算任务过多，CPU 使用率持续接近 100%       |
| 内存        | 大量请求和中间数据占用内存，频繁 GC，甚至内存溢出    |
| 线程池       | 工作线程全部被占用，新请求只能等待或被拒绝         |
| 数据库连接池    | 可用连接全部被占用，后续请求无法及时获得连接        |
| 数据库       | SQL 执行变慢、锁竞争、CPU 或磁盘 I/O 成为瓶颈 |
| 网络和磁盘 I/O | 数据传输或读写速度无法满足请求增长             |

**系统的整体处理能力通常受到关键瓶颈限制。**

例如，即使 Java 服务创建了更多线程，只要数据库已经成为瓶颈，继续增加线程也不一定能提高系统吞吐量，反而可能加剧数据库压力。

### 3.2.1 进程与线程的关系

**进程是操作系统进行资源分配的重要单位，线程是 CPU 调度和执行的基本单位之一。**

一个 Java 应用运行起来后，操作系统会为它创建进程，JVM 在进程中管理 Java 堆、类元数据等资源，并创建线程执行程序。

**同一个进程中的线程共享大部分进程资源，但每个线程也有自己的独立资源。**

|资源|是否由同一进程中的线程共享|说明|
|---|---|---|
|Java 堆（Heap）|是|通常存放对象实例，多个线程可以访问同一个对象|
|方法区相关运行时数据|主要共享|JVM 中的类元数据等由多个线程共同使用|
|程序计数器（PC）|否|每个线程独立记录自身执行位置|
|Java 虚拟机栈|否|每个线程拥有自己的 Java 栈帧和局部变量等|
|本地方法栈|通常独立|支持线程执行本地方法，具体实现依 JVM 而异|
|CPU 执行时间|需要竞争|多个线程竞争有限的 CPU 处理能力|

注意：Java 规范对运行时数据区有明确规定，但具体内存布局和实现细节可能因 JVM 而异。

### 3.2.2 为什么线程共享进程资源，创建大量线程还是会耗尽内存？

关键在于：**共享进程的部分资源，不代表每个线程不需要额外内存。**

例如，一个 Java 进程中的多个线程可以**共同访问同一个 Java 堆**，但每个线程通常都**需要自己的线程栈**。

#### 栈（Stack）：存“局部变量”和“执行路径”

- **归属**：**线程私有**。**每个线程都有自己的栈**，互不干扰（这就是为什么线程必须有自己的栈）。
    
- **存什么**：
    
    - **基本数据类型**（如 `int a = 1;`、`boolean flag = true;`），直接存具体的值。
        
    - **对象的引用（地址）**（如 `User user = ...;` 这里的 `user` 变量本身）。
        
    - **方法调用的状态**（每次调用一个方法，就会在栈里压入一个“栈帧”，方法执行完自动弹出销毁）。
        
- **特点**：存取速度极快，**内存自动分配和释放（方法结束就销毁）**，不需要垃圾回收（GC）。
    

#### 堆（Heap）：存“对象实例”

- **归属**：**进程内所有线程共享**。
    
- **存什么**：所有通过 `new` 关键字创建出来的**对象实例**和**数组**（比如 `new User()`、`new int[10]`）。对象里的成员变量（属性）也在这里。
    
- **特点**：内存空间大，但存取相对较慢。**对象的生命周期由 JVM 的垃圾回收器（GC）统一管理**，不会随着方法的结束而立刻销毁。

```text
Java 进程
|
+-- 共享资源
|   |
|   +-- Java 堆：多个线程可以访问对象
|   +-- 类元数据等共享数据
|
+-- 线程 A
|   +-- 独立的程序计数器
|   +-- 独立的 Java 虚拟机栈
|
+-- 线程 B
|   +-- 独立的程序计数器
|   +-- 独立的 Java 虚拟机栈
|
+-- 线程 C
    +-- 独立的程序计数器
    +-- 独立的 Java 虚拟机栈
```

**可以把 Java 堆理解为多个线程共同使用的工作区域，而线程栈则是每个线程各自使用的工作区域。**

因此，创建更多线程时，不仅可能增加线程自身的内存开销，也可能因为更多任务同时执行而增加堆内对象、请求上下文和临时数据的占用。

###  3.2.3 线程栈为什么会占用内存？

#### 什么是线程栈？

Java 虚拟机栈（JVM Stack）是**每个 Java 线程私有的运行时内存区域**。

**线程执行方法时，JVM 通常会为方法调用创建栈帧，用于保存局部变量、操作数栈、方法返回信息等运行时数据**。

例如：

```java
public void processRequest() {
    int count = 10;
    String message = "hello";
    doSomething();
}
```

**当线程执行这个方法时，需要使用自己的调用栈来管理方法执行过程中的局部数据和调用关系。**

如果大量线程同时存在，每个线程通常都需要相应的栈空间。

#### 大量线程如何消耗内存？

为了理解线程数量为什么会影响内存资源，可以假设：

- 创建 10,000 个线程。
    
- 假设每个线程配置的栈大小为 1 MiB。
    

那么，所有线程的栈大小配置总量就是：

**10,000 × 1 MiB = 10,000 MiB，约等于 9.77 GiB。**

这里的计算表达的是所有线程栈大小配置的合计，**不是说这些线程一定会立即占用 9.77 GiB 的物理内存**。

原因有三点：

1. 每个线程的实际栈大小与 JVM 参数、操作系统、运行环境等有关，1 MiB 只是示例。
    
2. 线程栈可能涉及虚拟地址空间预留和实际物理内存提交等不同概念，配置的栈大小不等于已经实际使用的物理内存。
    
3. 创建线程还会带来栈以外的运行时开销，例如线程管理结构和操作系统线程资源。
    

因此，即使 Java 堆还有剩余空间，**创建过多线程也可能因为本地内存或系统线程资源不足而失败**。

### 3.2.4 线程过多为什么会让系统变慢？

线程过多不只影响内存，还会增加 CPU 调度成本。

#### 什么是线程上下文切换？

CPU 在执行线程时，需要维护当前线程的执行状态，例如寄存器状态和执行位置等。

当操作系统调度 CPU 从一个线程切换到另一个线程时，需要保存当前线程的相关执行状态，并恢复另一个线程的状态，这个过程称为**线程上下文切换（Context Switch）**。

上下文切换本身是正常且必要的操作，常见的触发原因包括：

- **时间片用完：** 当前线程暂时让出 CPU，调度器选择其他可运行线程。
    
- **线程阻塞：** 当前线程等待数据库、网络 I/O 或锁等资源，暂时无法继续执行。
    
- **线程唤醒与抢占：** 某个线程重新变为可运行状态，调度器可能根据调度策略切换到该线程。
    
- **主动让出 CPU：** 当前线程主动让出处理器执行机会。
    

#### 为什么线程过多可能增加上下文切换开销？

线程数量增加后，如果大量线程同时处于可运行状态，它们就需要**竞争有限的 CPU 执行时间**。如果线程还频繁**阻塞**、**唤醒**或被**抢占**，调度器就可能需要进行更多的线程切换。

但是，线程数量与上下文切换频率并不是简单的正比关系。假设所有线程都持续等待 CPU，调度方式和时间片保持不变，那么增加可运行线程的数量不一定会明显提高单位时间内的切换次数。

线程过多的主要问题包括：

1. **CPU 竞争加剧：** 每个线程能够获得的 CPU 时间减少，等待执行的时间可能变长。
    
2. **调度开销增加：** 线程状态管理和上下文切换会占用一定的 CPU 时间。
    
3. **缓存利用效率可能下降：** 不同线程切换执行时，可能无法充分复用之前线程使用的数据和指令缓存。
    
4. **线程资源占用增加：** 大量线程需要额外的栈空间和运行时资源。
    

因此，合理控制并发线程数量，有助于减少不必要的资源竞争和调度开销。

#### 为什么线程越多不一定越快？

假设服务器只有 8 个逻辑 CPU，却创建了数千个需要持续进行计算的线程。

CPU 不可能让所有线程在同一时刻都执行计算。操作系统需要安排线程轮流获得 CPU 时间。

```
大量可运行线程
       |
       v
争夺有限的 CPU 执行时间
       |
       v
操作系统调度线程
       |
       v
产生上下文切换等开销
       |
       v
真正用于业务计算的时间比例可能下降
```

如果线程数量远超合理范围，CPU 可能花费更多时间进行线程调度和状态切换，导致业务执行效率下降。

但需要区分两种情况：

- **CPU 密集型任务：** 大量线程同时进行计算，可能因为竞争 CPU 而增加调度开销。
    
- **I/O 密集型任务：** 线程经常等待数据库或网络，适当增加并发有助于利用等待期间的 CPU，但并发过多仍可能耗尽线程、内存和下游资源。
    

因此，线程数量不是越多越好，应根据任务类型、CPU 数量和下游处理能力合理设置。

## 3.3 10,000 个请求为什么可能导致系统过载？

先纠正一个常见误解：

**10,000 个请求不等于一定创建 10,000 个线程。**

这取决于服务器的请求处理模型。

例如，采用传统的线程池处理 HTTP 请求时，服务器可能只有有限数量的工作线程，其余请求进入等待队列、被拒绝，或者在连接层等待。（**线程池**）

如果应用采用每个请求创建一个平台线程的模型，或者使用了没有合理上限的线程创建策略，就可能产生大量线程。

### 3.3.1 请求过载的完整过程

假设某个 Java 服务依赖 MySQL，数据库在当前业务条件下已经接近处理能力上限。

1. 大量请求同时到达 Java 服务。
    
2. 大量请求需要访问数据库。
    
3. 数据库处理变慢，连接被长时间占用。
    
4. Java 请求线程等待数据库结果。
    
5. 如果线程创建没有受到合理限制，线程数量可能持续增加。
    
6. 线程栈和其他运行时资源消耗增加，可能导致本地内存不足或线程创建失败。
    
7. 如果等待请求、业务对象和临时数据还大量占用堆内存，也可能触发频繁 GC，甚至发生 Java 堆内存溢出。
    
8. 系统可能表现为响应变慢、请求超时、拒绝服务，严重时进程崩溃或被重启。
    

```
请求突然增多
      |
      v
大量请求访问数据库
      |
      v
数据库变慢、连接被占用
      |
      v
请求等待时间变长
      |
      v
线程、队列和请求对象不断累积
      |
      v
内存压力与调度开销增加
      |
      v
超时、拒绝服务，严重时资源耗尽
```

这条链路并不是每次都完整发生。实际故障可能先表现为连接池耗尽、线程池耗尽、CPU 饱和或内存不足，取决于最先达到瓶颈的资源。

### 3.3.2 常见的两类内存问题

| 类型          | 主要原因                         | 可能表现                                                           |
| ----------- | ---------------------------- | -------------------------------------------------------------- |
| Java 堆内存不足  | 大量对象、请求上下文、缓存或积压任务占用堆内存      | `java.lang.OutOfMemoryError: Java heap space`                  |
| 本地内存或线程资源不足 | 大量线程、线程栈等消耗本地资源，或操作系统无法再创建线程 | `java.lang.OutOfMemoryError: unable to create native thread` 等 |

注意：出现 `OutOfMemoryError` 不一定代表 Java 堆已经用完。有些情况下，堆仍有剩余空间，但 JVM 或操作系统无法为新线程分配所需资源。

## 3.4 为什么需要线程池？
### 3.4.1 线程池的作用

线程池可以提前创建并复用一定数量的线程，避免每个请求都创建和销毁线程，同时通过线程数量和任务队列等配置控制并发。

```
大量请求
    |
    v
线程池
    |
    +-- 工作线程 1
    +-- 工作线程 2
    +-- 工作线程 3
    |
    v
执行任务
```

当工作线程全部忙碌时，新任务可以根据线程池配置进入等待队列、触发扩容，或者被拒绝。

线程池并不意味着任务永远不会积压，而是提供了控制并发和任务排队的机制。

### 3.4.2 线程池也需要合理配置

如果线程池允许无限制地创建线程，仍然可能发生线程过多的问题。

如果任务队列无限增长，也可能因为大量任务积压而耗尽内存。

因此，需要根据实际场景合理设置：

- 核心线程数和最大线程数。
    
- 任务队列的容量。
    
- 任务的等待时间。
    
- 拒绝策略。
    
- 超时、限流和监控机制。
    

对于数据库访问任务，还应结合数据库连接池容量和数据库实际吞吐量设置并发，避免线程池把过多请求同时压向数据库。

## 3.5 为什么大量请求会导致系统过载？

假设数据库在特定业务条件下，每秒能够稳定处理约 2,000 个任务。促销活动中，短时间内突然涌入 20,000 个请求。

如果大量请求直接访问数据库，可能出现以下过程：

```
大量请求突然到达
        |
        v
数据库负载增加，SQL 执行变慢
        |
        v
数据库连接被长时间占用
        |
        v
Java 请求线程等待数据库
        |
        v
线程池逐渐被占满
        |
        v
新请求排队、超时或被拒绝
        |
        v
系统可能过载，甚至不可用
```

原因在于：系统收到请求后，并不能保证立即完成处理。资源有限时，未完成的请求只能等待、被拒绝，或者最终超时。

这些请求可能处于不同状态：

|请求状态|含义|对系统的影响|
|---|---|---|
|正在处理|正在执行 Java 代码或数据库操作|占用线程、连接、CPU 等资源|
|等待处理|等待线程、连接、锁或前面的任务完成|可能占用内存和等待队列空间|
|超时或失败|未在规定时间内完成，或被系统拒绝|可能产生异常、重试和额外处理开销|

当请求到达速度长期超过处理速度时，等待任务可能越来越多。系统不仅要处理原来的业务，还要承受排队、超时和重试带来的额外开销。

## 3.6 为什么请求超时了，系统还可能崩溃？

这是理解系统过载的关键。

### 3.6.1 请求超时不等于后台任务已经停止

假设用户向 Java 后端发送一个 HTTP 请求：

1. Java 服务收到请求。
    
2. 服务调用数据库执行 SQL。
    
3. 数据库负载过高，SQL 长时间没有返回结果。
    
4. 用户端或网关等待超过限制，判断请求超时。
    
5. 数据库中的 SQL 可能仍然在执行，Java 服务也可能仍在等待数据库返回。
    

```
用户发起请求
      |
      v
Java 服务处理请求
      |
      v
申请数据库连接
      |
      v
执行 SQL
      |
      v
等待数据库返回
      |
      +------> 用户端等待超时
      |
      +------> SQL 可能仍在执行
```

超时只是某一层的等待时间超过限制，不一定代表整个业务操作已经停止。

HTTP 客户端断开连接，并不保证服务器自动取消已启动的业务操作。任务是否真正停止，取决于超时发生在哪一层，以及请求取消、线程中断、数据库语句取消和连接释放等机制是否有效。

### 3.6.2 大量等待任务会耗尽资源

假设 Java 服务有一个最多 200 个工作线程的线程池，数据库连接池最多提供 100 个连接。

当大量请求执行慢 SQL 时：

1. 部分请求占用数据库连接，且连接长时间无法释放。
    
2. 其他请求申请不到连接，只能等待或在超时后失败。
    
3. 等待数据库结果的请求线程无法及时处理新请求。
    
4. 线程池中的工作线程逐渐被占满。
    
5. 新请求只能进入等待队列，或者被拒绝。
    
6. 如果等待任务过多，还可能继续占用大量内存。
    

此时即使部分客户端已经超时，服务端的部分工作仍可能继续。

因此，**请求超时本身未必直接导致系统崩溃，但如果超时请求仍在占用资源，系统又持续接收新请求，就可能进一步发展为资源耗尽和服务不可用。**

### 3.6.3 系统过载的典型后果

| 后果     | 具体表现                          | 主要原因           |
| ------ | ----------------------------- | -------------- |
| 响应变慢   | 接口从几十毫秒变成几秒甚至更久               | 排队、资源竞争和下游变慢   |
| 请求超时   | 客户端或网关等待超过限制                  | 响应时间超过超时阈值     |
| 线程池耗尽  | 新请求无法及时获得工作线程                 | 线程被慢请求长时间占用    |
| 连接池耗尽  | 请求无法及时获得数据库连接                 | 连接长时间被占用       |
| CPU 饱和 | CPU 使用率持续较高                   | 计算任务过多或重试过多    |
| 内存不足   | 频繁 GC，甚至出现 `OutOfMemoryError` | 大量请求和等待任务占用内存  |
| 服务不可用  | 大量请求失败，健康检查异常                 | 关键资源饱和或依赖服务不可用 |

注意：**系统过载不一定意味着 Java 进程必然崩溃。** 即使进程仍然存活，如果它已经无法有效处理新请求，也属于严重的服务故障。

## 3.7 为什么超时重试会放大系统压力？

假设某个接口因为负载过高而响应变慢。客户端等待超时后，自动重新发送请求。

```
原始请求
   |
   v
服务处理缓慢
   |
   v
客户端等待超时
   |
   v
客户端重新发送请求
   |
   v
服务收到更多请求
   |
   v
系统压力进一步增加
```

如果大量客户端都进行重试，就可能形成恶性循环：

**请求过多 → 处理变慢 → 超时增多 → 重试增多 → 请求更多 → 处理进一步变慢。**

如果重试没有次数限制、退避间隔和随机抖动，问题可能进一步放大。

此外，如果业务操作不具备幂等性，重试还可能导致重复下单、重复扣款等业务问题。

## 3.6 什么是级联故障？

级联故障（Cascading Failure）是指一个组件发生故障或性能下降后，影响其他依赖它的组件，最终导致多个服务相继出现问题。

例如：

```
数据库变慢
    |
    v
订单服务请求阻塞
    |
    v
订单服务线程池耗尽
    |
    v
上游服务调用订单服务超时
    |
    v
重试和并发调用增加
    |
    v
多个服务相继过载
```

这说明系统故障不一定只发生在最初出现瓶颈的组件上。

如果缺少超时控制、限流、隔离和合理的重试策略，局部性能问题就可能不断扩大。

# 4 MQ 如何缓解系统过载？
## 4.1 没有 MQ：突发请求直接冲击数据库

假设某个订单系统的数据库，每秒能够稳定处理约 2,000 个任务，而秒杀活动在短时间内产生远高于这一速度的请求。

```
大量突发请求
      |
      v
   Java 服务
      |
      v
    数据库
      |
      v
处理速度跟不上请求到达速度
      |
      v
请求等待、连接占用、超时增加
```

**如果系统没有有效的流量控制，大量请求就可能同时冲击数据库，使数据库成为瓶颈。**

实际结果取决于请求持续时间、SQL 复杂度、并发处理能力、等待队列容量和资源余量。请求数量超过某个每秒吞吐量，并不代表数据库必然立即崩溃。

真正需要关注的是：突发请求是否持续超过系统处理能力，以及系统有没有合理的排队和过载保护机制。

#### 情况 1：数据库有足够的处理能力

假设一个查询平时需要 50 毫秒，数据库在 100 个连接同时工作时仍然能高效处理这些查询。

那么，单次查询可能依然只需要约 50 毫秒。即使来了 10,000 个请求，也不会仅仅因为请求总数增加，就必然让 SQL 本身变慢。

这时主要发生的是：前 100 个请求使用连接，后续请求在连接池前排队。

#### 情况 2：100 个并发查询已经超过数据库适合的负载

现在假设数据库的 CPU、磁盘 I/O 或其他资源比较有限。

**即使只允许 100 个请求同时执行 SQL，这 100 个请求也可能竞争同一组有限资源。**

例如：

- **CPU 竞争**： 许多查询都需要计算，但数据库 CPU 处理不过来。
    
- **磁盘 I/O 竞争**： 查询需要读取大量数据，磁盘无法及时满足所有读写请求。
    
- **锁竞争**： 多个事务要修改同一行库存，其中一些事务只能等待其他事务释放锁。
    
- **内存和缓存压力**： 大量查询操作的数据超出缓存能够有效容纳的范围，可能增加磁盘访问。
    

结果可能是，原本几十毫秒完成的查询，在高并发下需要几百毫秒甚至几秒。

**注意，这不是因为连接数突破了 100，而是因为允许并发的这 100 个查询，本身就足以让数据库的某些资源变得紧张。如果数据库资源充足、查询简单且相互独立，就未必会出现这种情况。**

## 4.2 引入 MQ：把突发流量转化为消息积压

引入 MQ 后，可以将允许异步处理的任务先写入消息队列，再由消费者根据实际处理能力逐步执行。

```
突发业务请求
      |
      v
生产者 / 业务服务
      |
      v
      MQ
  暂存待处理消息
      |
      v
消费者按能力逐步处理
      |
      v
    数据库
```

例如，某个时段产生了大量订单处理任务，而消费者每秒只能完成约 2,000 个任务。MQ 可以暂存暂时无法处理的消息，让消费者在后续时间逐步处理。

两个重要概念：

- **削峰：** 将瞬间到达的流量洪峰缓冲下来，减少下游系统受到的瞬时冲击。
    
- **填谷：** 当流量下降后，消费者继续处理积压的消息，利用后端剩余处理能力。
    

MQ 并不是让数据库突然拥有了更强的处理能力，而是改变任务进入下游系统的节奏。

### 4.2.1 MQ 缓冲的是哪一部分工作？

这是一个重要边界。

只有把耗时操作或下游业务放到消费者侧，MQ 才能有效缓冲这些操作的执行压力。

例如：

```
HTTP 请求
    |
    v
接收并校验请求
    |
    v
发送消息到 MQ
    |
    v
消费者执行业务操作
    |
    v
写入数据库
```

在这个结构中，消息队列可以减少大量业务任务同时访问数据库的情况。

但如果 Java 服务在发送消息之前已经执行了大量数据库操作，那么这些操作的压力并不会因为后续使用 MQ 而自动消失。

另外，MQ 也不能无限接收请求。如果入口服务已经过载、消息发送失败或消息队列达到容量限制，仍然需要限流、拒绝请求或其他保护措施。

## 4.3 MQ 能保证系统不崩溃吗？

不能。

MQ 只能缓冲任务，不能无限提高系统的实际处理能力，也不是无限容量的存储空间。

如果消息生产速度长期高于消费速度，消息就会持续积压。

例如：

|项目|假设值|
|---|---|
|消息生产速度|5,000 条/秒|
|消息消费速度|2,000 条/秒|
|每秒新增积压|3,000 条/秒|

在生产速度和消费速度始终不变的简化场景下，每秒约新增 3,000 条积压消息。

长期下去，可能导致：

- 消息积压数量持续增加。
    
- 消息处理延迟越来越高。
    
- 消息存储占用持续增长。
    
- 消费者无法及时完成业务。
    
- 部分业务出现延迟过高或超出业务时限的问题。
    

因此，MQ 更适合缓冲短时间的流量高峰。

如果长期处理能力不足，还需要结合其他手段：

1. **限流：** 限制系统接收请求或任务的速度。
    
2. **扩容：** 增加服务实例或消费者，但要考虑数据库的承载能力。
    
3. **背压与流量控制：** 当下游处理不过来时，主动降低上游生产速度。
    
4. **容量保护：** 设置合理的队列、线程池和请求等待上限，监控消息积压，必要时拒绝非核心请求。
    
5. **优化瓶颈：** 优化 SQL、减少不必要的调用或改进业务逻辑。
    

## 4.4 为什么不能单纯增加线程或消费者？

假设数据库每秒稳定处理 2,000 个任务，Java 服务的并发处理能力已经足以让数据库持续处于繁忙状态。

此时继续增加线程，可能发生以下情况：

1. Java 服务同时发起更多数据库请求。
    
2. 数据库每秒完成的任务量却没有明显增加。
    
3. 更多请求争抢连接、CPU、锁和 I/O。
    
4. 等待请求和资源竞争更加严重。
    
5. 最终出现更多超时，甚至发生更严重的过载。
    

因此：

**增加线程或消费者只能在现有并发能力不足、下游仍有余量时帮助提升吞吐量，不能突破下游瓶颈。**

如果瓶颈在数据库，单纯增加消费者反而可能让更多 SQL 同时冲击数据库。

# 5 消息队列的缺点与问题处理
## 5.1 消息队列有什么缺点？

消息队列虽然可以实现解耦、异步和削峰填谷，但也会增加系统的复杂性。是否引入 MQ，本质上是一种技术权衡（Trade-off）。

### 5.1.1 系统可用性降低

没有 MQ 时：

```text
系统 A ───────> 系统 B
```

引入 MQ 后：

```text
系统 A ──> MQ ──> 系统 B
```

原本 A 和 B 之间的调用，现在增加了一个中间组件 MQ。

如果 MQ 出现故障，例如 Broker 宕机、网络中断或集群不可用，生产者可能无法正常发送消息，消费者也可能无法获取消息，从而影响业务链路。

**解决思路：**

- 部署 MQ 集群，降低单点故障风险。
- 根据 MQ 类型配置消息持久化和副本机制。
- 对消息发送失败、消费失败等情况设置重试和补偿机制。
- 设计 MQ 不可用时的降级方案，避免故障无限扩大。

注意：部署集群不代表绝对不会发生故障，还需要合理配置、监控和故障恢复机制。

### 5.1.2 系统开发复杂度增加

使用 MQ 后，原本简单的同步方法调用变成了异步消息处理，需要额外考虑多种异常情况。

例如：

- 消息发送失败，生产者如何处理？
- 消息发送成功，但确认响应丢失，生产者重试后会不会产生重复消息？
- 消费者处理消息时发生异常，消息如何重试？
- 消费者处理成功，但确认消息失败，会不会重复消费？
- 消费者处理不过来，消息积压怎么办？

**解决思路：**

- 通过生产者确认机制、消息持久化等手段提高可靠性。
- 通过幂等性设计避免重复消费造成的业务错误。
- 通过重试、死信队列或补偿机制处理失败消息。
- 通过监控、告警和扩容处理消息积压。

### 5.1.3 数据一致性问题

使用消息队列时，业务系统通常需要同时完成两件事：

1. 执行本地业务操作，例如向 MySQL 写入订单。
    
2. 向 MQ 发送消息，通知其他服务执行后续操作。
    

由于数据库和 MQ 是两个独立的系统，各自有自己的提交机制，因此可能出现**本地业务操作成功，但消息发送失败**，或者**消息发送成功，但本地业务操作失败**的情况，导致系统间的数据不一致。

例如，订单服务创建订单后，需要发送消息通知库存服务扣减库存。如果订单创建成功，但消息没有成功发送，库存服务就无法收到通知，订单和库存数据可能出现不一致。

解决这个问题，需要分别考虑生产端的消息发送可靠性，以及消费端的消息处理可靠性。

#### 生产端：保证本地事务与消息发送的一致性

**方案一：MQ 事务消息（以 RocketMQ 为例）**

**核心思路：** 利用 **MQ 的事务消息机制**，通过半消息、本地事务执行结果和事务状态回查，协调本地事务与消息的提交。

流程：

1. 生产者向 MQ 发送半消息，此时消费者不能正常消费该消息。
    
2. 生产者执行本地事务，例如向数据库写入订单。
    
3. 根据本地事务的执行结果，生产者向 MQ 提交事务状态：
    
    - 本地事务成功：提交消息，使其可以被消费者消费。
        
    - 本地事务失败：回滚消息，不再投递给消费者。
        
4. 如果 MQ 没有及时收到明确的事务结果，会**回查**生产者的本地事务状态，再决定提交还是回滚。
    

**注意：** 事务消息并不意味着数据库事务和 MQ 事务真正成为一个跨系统的原子事务，而是**通过事务状态确认和回查机制协调两者的一致性**。

**方案二：本地消息表（Transactional Outbox）**

**核心思路：** 将业务数据和待发送消息记录写入同一个数据库事务，再由后台任务负责把消息发送到 MQ。

流程：

1. 开启数据库事务。
    
2. 在同一个事务中写入业务数据，例如订单，以及本地消息表中的待发送消息记录。
    
3. 提交事务，保证业务数据和消息记录要么同时成功，要么同时回滚。
    
4. 后台任务定期扫描待发送的消息记录，将消息发送到 MQ。
    
5. 发送成功后，将消息记录标记为已发送；发送失败则保留记录，后续重试。
    

**关键理解：** **数据库事务只保证业务数据与本地消息记录的原子性，并不保证数据库操作与 MQ 发送操作的原子性。**本地消息表通过持久化待发送任务和后台重试机制，避免服务宕机导致消息永久漏发。

如果消息已经发送成功，但服务在更新发送状态前宕机，后台任务可能再次发送该消息。因此，消费者仍需要实现幂等性。

**两种方案的对比：**

| 对比维度 | MQ 事务消息            | 本地消息表              |
| ---- | ------------------ | ------------------ |
| 核心机制 | 半消息、事务状态确认与回查      | 数据库事务、待发送记录、后台投递   |
| 主要依赖 | MQ 的事务消息功能         | 本地数据库与后台投递任务       |
| 通用性  | 依赖 MQ 产品提供的事务消息机制  | 通常更通用，可适配不同 MQ     |
| 主要工作 | 处理事务状态确认、回查与异常情况   | 维护消息表、投递状态、重试与清理   |
| 共同点  | 都需要处理异常、重复消息和最终一致性 | 都需要处理异常、重复消息和最终一致性 |

#### 消费端：保证消息被可靠处理

即使生产端成功发送消息，消费端仍可能因为服务宕机、数据库异常或网络故障而处理失败，因此还需要以下机制。

**（1）消息重试**

消费者处理消息**失败**时，可以根据异常类型和重试策略重新消费，避免临时故障导致消息丢失。

**（2）幂等性**

消息可能因为生产端重试、MQ 重投或消费者处理结果不明确而被重复消费。

消费者应通过业务唯一标识、去重记录或数据库唯一约束等方式，**确保同一条业务消息重复处理时，不会重复执行有副作用的业务操作**。

例如，针对同一个订单的扣库存消息，应避免重复扣减库存。

**（3）死信队列与异常处理**

如果消息经过多次重试仍然失败，可以按照 MQ 的机制和业务策略将其转入死信队列，交由后续排查和处理，避免问题消息一直阻塞正常消费。

**（4）对账与补偿**

对于重要业务，可以定期对账，检查业务数据与下游处理结果是否一致。发现遗漏或异常后，通过重试、补偿任务或人工介入进行修复。

#### 最终一致性

**上述机制并不意味着所有系统中的数据会在同一时刻更新，而是通过可靠投递、消费重试、幂等处理和异常补偿，使不同系统的数据最终趋于一致。**

例如，订单创建成功后，库存服务可能暂时没有完成扣减；只要消息能够被可靠处理，失败能够被发现和修复，系统就可以在一定时间后恢复一致。

需要注意，最终一致性依赖于重试和补偿机制能够持续运行、异常能够被发现和处理，并非仅仅引入 MQ 就能自动实现。

**总结：** **生产端**通过**事务消息**或**本地消息表**协调本地事务与消息发送；**消费端**通过**重试**、**幂等**、**死信处理**和**对账补偿**保障消息的可靠处理。两端共同配合，才能降低消息丢失和重复处理带来的风险，实现业务系统之间的最终一致性。

## 5.2 消息队列怎么选型？

选择 MQ 时，不能只看吞吐量，还需要综合考虑业务需求、消息可靠性、顺序性、运维成本和技术栈。

| 对比维度   | RabbitMQ             | RocketMQ                 | Kafka                 |
| ------ | -------------------- | ------------------------ | --------------------- |
| 消息组织方式 | Exchange 路由消息到 Queue | Topic 下包含多个 MessageQueue | Topic 下包含多个 Partition |
| 典型场景   | 灵活路由、任务分发            | 订单、支付、业务事件               | 日志采集、大规模数据流           |
| 主要特点   | 路由机制灵活               | 事务消息、延迟消息等业务功能丰富         | 高吞吐、消息保留与回溯能力强        |
| 选型重点   | 路由规则、队列类型            | 业务特性、消息顺序、可靠性            | 分区规划、吞吐量、消息保留策略       |

常见选型倾向：

- **RabbitMQ**：业务需要复杂的消息路由和任务分发。
- **RocketMQ**：业务需要事务消息、延迟消息、消费重试等能力。
- **Kafka**：需要处理大量日志、埋点或流式数据，并且关注高吞吐和消息回溯。

注意：这只是常见的选型倾向，并非绝对限制。实际性能取决于消息大小、硬件、部署方式、持久化和副本等配置。

## 5.3 消息重复消费怎么解决？
### 5.3.1 为什么会出现重复消费？

**消息重复消费，是指同一条业务消息被消费者处理多次。**

**情况一：生产者重试导致重复消息。**

```text
生产者发送消息
       |
       v
MQ 已经保存消息
       |
       v
确认响应丢失
       |
       v
生产者以为发送失败，重新发送
       |
       v
MQ 中可能出现重复消息
```

由于网络超时或确认响应丢失，生产者无法确定消息是否已经成功保存，因此可能重试发送。

**情况二：消费者处理成功，但确认失败。**

```text
消费者获取消息
       |
       v
执行数据库操作成功
       |
       v
消费者宕机，未提交消费确认
       |
       v
MQ 重新投递消息
       |
       v
同一业务可能再次执行
```

例如，第一次消费已经给用户增加了 100 积分，但消费者还没来得及确认消息就发生故障。消息重新投递后，如果没有防重机制，用户就可能再次获得 100 积分。

### 5.3.2 什么是幂等性？

**幂等性是指同一个操作执行一次或多次，对最终业务状态产生的效果相同。**

例如，同一笔支付成功消息重复到达三次，最终仍然只能给用户增加一次积分。

需要区分两个概念：

- **消息去重**：识别消息是否已经出现或处理过。
- **业务幂等**：即使同一业务被重复触发，也不会重复产生业务效果。

实际业务中，**通常通过业务幂等来应对重复消费**。

### 5.3.3 如何实现幂等？

| 方案       | 实现思路                    | 适用场景       |
| -------- | ----------------------- | ---------- |
| 唯一索引     | 对业务唯一标识设置数据库唯一约束        | 创建订单、创建发货单 |
| 消费记录表    | 记录已经成功处理的业务消息           | 积分发放、支付通知  |
| 条件更新     | 只有满足特定状态时才允许更新          | 订单状态流转     |
| Redis 防重 | 使用 `SET NX` 等方式辅助识别重复请求 | 并发请求防重     |

以积分业务为例，可以使用订单号和业务类型构成幂等键，例如 `order123_add_points`。

消费时，在同一个数据库事务中完成：

1. 插入消费记录。
2. 增加用户积分。
3. 提交事务。

如果消费记录的唯一键已经存在，说明该业务已处理成功，可以跳过重复的业务操作。

注意：

- 不能简单地采用“先查询是否存在，再执行操作”的方式，因为多个消费者可能同时查询到记录不存在，随后重复执行。
- 应利用数据库唯一约束和事务保证并发安全。
- Redis 的 `SET NX` 可以辅助防重，但要考虑防重记录与业务执行之间发生故障的情况。
- 分布式锁可以控制并发，但不能单独保证幂等。锁释放后，重复消息仍然可能再次执行。

## 5.4 消息丢失怎么解决？

消息从产生到被处理，主要经过三个环节：

**生产者 → MQ（Broker）→ 消费者**

因此，需要分别保障三个环节的可靠性。

### 5.4.1 生产者：确保消息成功发送

生产者不能只调用发送方法，就认为消息一定发送成功。

应该：

- 检查发送结果和异常。
- 根据 MQ 类型使用生产者确认机制。
- 发送失败时，按照策略重试。
- 对发送超时的情况谨慎处理，因为消息可能已经保存，只是确认响应丢失。

**还有一种容易忽略的情况：业务数据已经写入数据库，但程序在发送 MQ 消息之前就宕机了。这里就可以使用之前提到的事务消息（半消息 + 回查）或者本地消息表来解决这个问题**

此时，消息根本没有到达 MQ。可以使用**事务消息或本地消息表**等方案，处理业务数据与消息发送之间的一致性问题。

### 5.4.2 MQ：确保消息可靠保存

MQ 需要根据具体产品和业务要求配置：

- **消息持久化**：将消息保存到可靠的存储介质。
- **副本机制**：通过多个副本降低单个节点故障导致数据丢失的风险。
- **可靠确认**：明确发送成功的确认代表什么。
- **容量与保留策略**：避免消息因过期、存储空间不足或清理策略而丢失。

**MQ 的持久化，通常就是把消息保存到 MQ 服务器管理的磁盘文件中，而不是把每条消息都写入 MySQL 这样的业务数据库。**

例如，Kafka 可以通过合理配置副本、`acks` 和 `min.insync.replicas` 提高可靠性。

注意：部署集群不代表绝对不会丢消息，具体保障程度取决于配置和故障场景。

### 5.4.3 消费者：业务成功后再确认

**消费者应当在业务处理成功后，再提交消费确认或消费进度。**

```text
获取消息
   |
   v
执行实际业务逻辑
   |
   ├── 成功：确认消息 / 提交消费进度
   |
   └── 失败：重试或进入异常处理流程
```

如果消费者一收到消息就确认，之后业务处理失败，那么 MQ 可能认为消息已经处理完成，导致业务无法通过正常重投恢复。

如果消费者业务已经成功，但确认前发生故障，则可能出现重复消费。因此，还需要配合幂等性设计。

### 5.4.4 总结

| 环节   | 主要措施              |
| ---- | ----------------- |
| 生产者  | 发送确认、异常处理、合理重试    |
| MQ   | 持久化、副本机制、合理的保留策略  |
| 消费者  | 业务成功后确认、失败重试、幂等处理 |
| 业务整体 | 事务消息、本地消息表、对账与补偿  |

**核心思路：生产端确保消息有记录、可补发；MQ 确保消息可靠保存；消费端确保处理成功后才确认。**

## 5.5 消息队列的可靠性与顺序性怎么保证？

这两个概念需要区分：

- **可靠性**：消息是否能够被可靠地保存并最终处理。
- **顺序性**：消息是否按照业务要求的先后顺序处理。

### 5.5.1 如何保证可靠性？

主要依赖以下机制：

1. **生产者确认**消息发送结果。
2. MQ 通过**持久化**和**副本**机制降低消息丢失风险。
3. **消费者**在业务成功后**确认消息**。
4. 通过**重试**、**死信队列**和**补偿机制**处理异常。

可靠性不是单独依靠某一个配置就能保证的，而是生产者、MQ 和消费者共同配合的结果。

### 5.5.2 如何保证顺序性？

假设一个订单需要按照以下顺序处理：

```
创建订单 → 支付成功 → 订单完成
```

如果后续消息先于前面的消息被处理，就可能导致业务状态错误。

**核心思路：让同一业务的消息进入同一个有序队列，并按照顺序消费。**

1. **确定顺序范围**：通常只需要保证同一个订单的消息有序，不同订单之间可以并行处理。
    
2. **让消息进入同一个队列**：生产者可以根据订单 ID 等业务标识选择队列，确保同一订单的消息进入同一个队列。
    
3. **按顺序消费**：MQ 按队列顺序投递消息，消费者配合顺序消费机制，避免并发处理导致顺序错乱。
    
4. **处理失败情况**：前一条消息处理失败时，需要根据 MQ 的重试机制和业务设计，避免后续消息提前执行。
    

例如，Kafka 可以通过相同的消息 Key 将同一订单的消息发送到同一个 Partition；RocketMQ 则可以通过消息队列选择机制和顺序消费机制实现类似的效果。

**注意：** 有序队列并不意味着消息一定按顺序完成业务处理。还需要消费者配合顺序消费，处理好失败重试等情况。顺序消费会限制并行处理能力，因此通常只保证必要范围内的顺序。

## 5.6 MQ 的消息存储与分发
### 5.6.1 MQ 存储的是什么？

MQ 存储的是**消息**，而不是直接存储和执行完整的业务逻辑。

例如，订单服务创建订单后，可以向 MQ 发送一条消息：

```json
{
  "eventType": "OrderPaid",
  "orderId": "O1001",
  "amount": 99
}
```

这条消息表示订单已支付，可以通知其他服务执行后续操作。

需要区分以下三个概念：

- **业务数据**：例如订单记录，通常保存在 MySQL 等业务数据库中。
    
- **消息**：用于传递业务事件及相关数据，由 MQ 负责存储和分发。
    
- **业务处理**：消费者收到消息后，通过自己的代码执行具体操作，例如扣减库存、发送通知。
    

消息可以包含业务数据，也可以只包含业务标识。MQ 不会自动执行消息所代表的业务。

### 5.6.2 MQ 如何分发消息？

**MQ 通常通过 Topic（主题）、队列和订阅关系组织及分发消息。**

例如，订单服务发布一条 `OrderPaid` 消息到 `order-events` 主题：

```text
订单服务（生产者）
        |
        v
MQ：order-events
        |
        +----------+
        |          |
        v          v
   库存消费者组   统计消费者组
        |          |
        v          v
     扣减库存     更新统计
```

处理过程：

1. **生产者将消息发送到指定主题**。
    
2. MQ 根据**订阅关系**，将消息提供给**对应的消费者组**。
    
3. 消费者收到消息后，执行自己的业务逻辑。
    

**关键理解：** MQ 根据**主题、队列和订阅关系**分发消息，不会自动理解业务含义并决定调用哪个服务。

**不同消费者组通常各自处理一份消息；同一个消费者组中的多个消费者实例通常分担消息，而不是重复处理每一条消息。**
	
#### Topic、Queue 与顺序消费

**Topic 和 Queue 的区别**

- **Topic（主题）**：用于对消息进行分类，例如 `order-events` 表示订单相关消息。
    
- **Queue（队列）**：Topic 内部用于存放和读取消息的队列。
    
- 一个 Topic 通常包含多个队列或分区，以支持消息的并行处理。
	
- 同一个 Topic 下的多个 Queue，通常存储的是**同一类业务消息**，只是这些消息被分散到不同的队列中。
    
- **消费者订阅 Topic 即可**，不需要自己为每个 Queue 单独编写监听器。 RocketMQ 会根据消费者组和负载均衡策略分配消息。


**为什么同一业务的消息要进入同一个队列？**

假设同一个订单需要按以下顺序处理：

```
创建订单 → 支付成功 → 订单完成
```

如果这些消息进入不同队列，就可能被**并行处理**，**导致业务顺序错乱**。

因此，可以**根据**订单 ID **等业务标识选择队列**，让同一订单的消息进入同一个队列，再配合顺序消费机制依次处理。

**顺序消费需要注意什么？**

保证顺序性需要：

1. 同一订单的消息进入同一个队列。
    
2. 生产者按业务要求的顺序发送消息。
    
3. 消费者按照顺序处理消息，并正确处理失败重试。
    

**注意：** **同一个 Topic 不等于同一个队列**。同一个队列提供局部顺序的基础，但不能自动保证业务处理顺序，也不能保证不同消费者组之间的业务执行顺序。

#### 消费者组与消费者实例的区别

- **不同消费者组**：可以分别消费同一条消息，适用于不同业务都需要处理同一个事件的场景。例如，库存服务扣减库存，统计服务更新统计数据。
    
- **同一个消费者组中的多个消费者实例**：通常共同分担消息，提高消费并发能力，而不是每个实例都重复处理同一条消息。
    

例如，库存服务启动三个消费者实例，这三个实例共同处理库存消息；统计服务使用另一个消费者组，也可以独立消费同一批消息。

**注意：** 同一个消费者组通常会分配消息，避免多个实例主动重复消费同一条消息，但故障重试等情况仍可能导致重复处理，因此消费者需要考虑幂等性。

#### 消费者组与顺序消费

**消费者组的作用**

- **一个消费者组通常对应一种逻辑上的消费职责**，可以包含**多个消费者实例**，共同分担该组的消费任务。
	
- **一个消费者组可以订阅一个或多个 Topic**，并通过统一的消费逻辑处理订阅范围内的一种或多种消息

例如：

- 库存消费者组：处理库存变更消息。
    
- 统计消费者组：更新订单统计数据。
    

不同消费者组可以独立消费同一条消息，各自完成不同的业务处理。

**如何实现顺序消费**

如果同一个订单的多条消息需要按顺序处理，需要让这些消息**进入同一个队列**，并**由同一个消费者组按照顺序消费**。具体还需要 MQ 支持顺序消费，并保证相关消息由同一消费通道串行处理。

例如：

```
订单消息：创建 → 支付成功 → 订单完成
                    |
                    v
                 同一队列
                    |
                    v
              按顺序逐条处理
```

这里的顺序不仅是消息先后被获取，还要求**前一条消息处理完成后，再处理后一条消息**，避免业务处理发生乱序。

同一个消费者组仍然可以并行处理其他队列中的消息，因此不代表整个消费者组只能串行处理所有消息。

**不同消费者组之间的顺序**

不同消费者组**独立消费消息**，不会天然地相互等待，也不会自动协调各自的业务执行进度。

例如，库存消费者组负责扣减库存，发货消费者组负责生成发货任务。即使两条消息按顺序进入同一个队列，也不能仅凭队列的顺序，就保证库存扣减成功后发货服务才开始处理。

如果必须先扣减库存成功，再生成发货任务，可以设计为：

```
库存扣减成功
      ↓
发布「库存扣减成功」事件
      ↓
发货服务收到事件
      ↓
生成发货任务
```

这样，发货服务收到后续事件时，库存扣减业务已经成功完成。实际系统还需要考虑事件可靠投递、重复消费和失败重试等问题。

**核心区别**

- **消息顺序**：消息在队列中的先后顺序，以及消费者按顺序获取、处理消息的顺序。
    
- **业务执行顺序**：业务操作实际开始、完成的先后关系。
    
- **跨消费者组的业务依赖**：不能仅依赖 MQ 的顺序消费，需要通过事件通知、状态校验等业务机制协调。
    

**注意：** 顺序消费可以保证指定队列中的相关消息按顺序处理，但不能自动保证不同消费者组之间的业务操作按指定顺序完成。

### 5.6.3 消息在 MQ 中如何存储？

MQ 通常将消息存储在**磁盘文件**、**日志结构**或其他内部存储结构中，并使用内存缓存、索引等机制辅助读写。

消息一般按照 MQ 的存储机制写入队列或分区。每个队列或分区通常有自己的消息顺序，但不同队列之间不一定存在统一的全局顺序。

需要注意：

- 普通消息队列并不意味着消息在存储时随机排列。
    
- 消息有存储顺序，不代表消费者一定按该顺序完成业务。
    
- 多个队列可以提高并行处理能力，但不能仅凭单个队列内的顺序推断所有消息的全局顺序。
    

### 5.6.4 普通消息模式与顺序消费

假设一个订单产生了以下三条消息：

```
M1：订单创建
M2：支付成功
M3：订单完成
```

**普通消费模式：**

MQ 按照自身的分发和消费机制处理消息。消费者可以并发处理，因此即使 M1 先发送，也可能出现 M2、M3 先完成业务处理的情况。

如果这些消息之间没有业务依赖，并发处理通常没有问题。

**顺序消费模式：**

如果同一订单的消息必须按顺序处理，可以让它们进入同一个有序队列，并配合顺序消费机制。

```
同一订单的消息
        |
        v
同一个有序队列
        |
        v
按顺序消费
        |
        v
依次处理业务
```

例如，Kafka 可以通过相同的消息 Key 将同一订单的消息发送到同一个 Partition；RocketMQ 可以通过消息队列选择机制，将同一订单的消息发送到同一个 MessageQueue，并配合顺序消费机制处理。

保证顺序性需要以下条件：

1. 同一业务的消息进入同一个队列或分区。
    
2. 生产者按照业务要求的顺序发送消息。
    
3. 消费者按照顺序处理，避免并发执行导致业务完成顺序错乱。
    
4. 正确处理失败重试，避免前一条消息失败后，后续消息提前执行。
    

**注意：** 顺序消费通常会限制并行处理能力，因此一般只保证必要范围内的局部顺序，而不是所有消息的全局顺序。

### 5.6.5 总结

理解 MQ 的工作机制，需要区分三个层面：

|层面|主要职责|
|---|---|
|消息存储|MQ 保存消息，并管理队列或分区中的消息位置|
|消息分发|MQ 根据主题、队列和订阅关系，将消息提供给消费者|
|业务处理|消费者执行具体业务逻辑，必要时配合顺序消费和状态校验|

普通消息模式允许并发处理；顺序消费则通过消息分配和消费机制，保证指定范围内的处理顺序。

**核心结论：MQ 负责消息的存储与传递，消费者负责业务执行；消息的存储顺序、投递顺序和业务完成顺序是不同的概念。**

## 5.7 如何保证幂等写？

幂等写是指多次执行同一业务写操作，最终业务状态仍然正确。

常见实现方式有三种。

### 5.7.1 插入类业务：使用唯一约束

例如，同一个订单只能创建一张发货单。

给发货单表的 `order_id` 设置唯一索引，即使同一条消息重复消费，数据库也会阻止重复创建。

### 5.7.2 状态流转：使用条件更新（乐观锁）

例如，订单只能从“待支付”更新为“已支付”。

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = ?
  AND status = 'UNPAID';
```

第一次更新成功后，订单状态变为 `PAID`。重复执行时，由于状态已经改变，通常不会再次更新成功。

注意：后续业务操作只能由成功完成状态转换的那次请求触发，并且需要根据业务规则处理其他更新失败的情况。

### 5.7.3 累加类业务：使用业务流水去重

**累加类业务**是指每次执行都会在原有数值上增加或减少一定数量的操作，例如积分增加、账户余额变更、商品销量累加等。

例如，给用户增加 100 积分：

```
UPDATE user_points
SET points = points + 100
WHERE user_id = 123;
```

这个操作本身不具备幂等性。同一条消息重复消费两次，就可能增加 200 积分。

**解决方案：通过业务流水记录识别同一笔业务，防止重复执行。**

**什么是业务流水？**

业务流水是记录每一笔业务变更的明细。例如，积分流水表 `points_flow` 可以记录：

|字段|含义|
|---|---|
|`business_id`|业务唯一标识，用于识别同一笔积分业务|
|`user_id`|被变更积分的用户|
|`points`|本次积分变动值|

例如，用户参加活动获得 100 积分，业务编号为 `ACTIVITY_001`。流水表记录这笔业务后，就可以判断该业务是否已经处理过。

**如何利用流水记录防重？**

```text
收到积分变更请求
        |
        v
使用稳定的业务编号插入流水记录
        |
        v
   是否成功插入？
   +----+----+
   |         |
  成功      失败
   |         |
   v         v
积分 +100   不再累加
   |
   v
事务提交
```

- 第一次请求：业务编号 `ACTIVITY_001` 尚不存在，插入流水成功，积分增加 100。
    
- 重复请求：仍然使用 `ACTIVITY_001`，唯一约束阻止重复插入，因此不会再次增加积分。
    

**如何保证并发和事务安全？**

- 为流水表的 `business_id` 建立**唯一约束**，确保同一笔业务只能成功登记一次。
    
- 将**流水插入**和**积分更新**放在**同一个数据库事务**中，确保两者一起提交或一起回滚。
    
- **同一笔业务的重试必须使用相同的业务编号**，不能每次请求都生成新的编号。
    

注意：业务编号应该来自稳定的业务身份，例如订单奖励可以使用 `ORDER_123_REWARD`。如果同一订单允许多笔不同的积分变更，还需要为每种变更设置不同的标识。

**其他注意事项：**

- Redis 的 `SET NX` 可以辅助防重，但不能单独保证防重记录与数据库业务操作的一致性。
    
- 分布式锁可以控制并发，但不能代替业务幂等记录。
    
- 涉及第三方支付等外部系统时，还需要使用对方支持的幂等键，或结合查询、对账机制处理异常情况。

## 2.8 如何处理消息队列的消息积压问题？
### 2.8.1 什么是消息积压？

**消息积压是指生产者产生消息的速度持续高于消费者处理消息的速度，导致尚未处理的消息不断累积。**

例如：

- 生产者每秒产生 5,000 条消息。
- 消费者每秒只能处理 2,000 条消息。

那么每秒净增加 3,000 条积压消息。

如果这种情况持续存在，消息等待时间就会越来越长，最终可能导致磁盘空间不足、业务延迟超时等问题。

### 2.8.2 第一步：排查积压原因

出现积压时，不能一上来就增加消费者机器，而是应该先判断问题出在哪里。

重点排查：

- **生产速度是否突然增加**：例如促销活动导致消息量骤增。
- **消费者是否异常**：例如消费者宕机、掉线或消费线程不足。
- **单条消息处理是否过慢**：例如业务逻辑复杂、频繁调用远程接口。
- **数据库是否存在瓶颈**：例如慢查询、锁等待、连接池耗尽。
- **是否存在异常消息反复重试**：错误消息不断重试，可能拖慢正常消息的处理。

可以结合消费速率、消息积压量、最老消息等待时间、消费失败率等指标定位问题。
	
### 2.8.3 第二步：优化消费者的处理能力

如果问题出在消费逻辑，就应该先优化消费逻辑。

常见方法：

1. **优化业务代码**：减少不必要的计算、远程调用和重复操作。
2. **优化数据库操作**：优化 SQL、索引和事务，减少慢查询。
3. **批量处理消息**：如果业务允许，可以将多条消息合并处理，降低单条消息的固定开销。
4. **增加消费者实例**：在消息队列分配规则和下游承载能力允许的情况下，增加并行消费能力。

需要注意：**消费者机器数量增加，并不一定意味着消费能力就会增加。**

以 RocketMQ 的传统队列分配消费模式为例：

```text
Topic：chat-message
队列数量：4

消费者 A ← 队列 1
消费者 B ← 队列 2
消费者 C ← 队列 3
消费者 D ← 队列 4

再增加消费者 E、F、G……
如果没有可分配的队列，它们就无法获得对应的队列进行消费。
```

所以，**当队列数量不足时，单纯增加消费者实例无法充分提高并行度。**

另外，如果瓶颈已经在数据库，继续增加消费者反而可能加重数据库压力。因此，需要同时考虑整个下游链路的承载能力。

### 2.8.4 第三步：扩展队列或分区

如果消费者处理逻辑已经优化，但并行度仍然不足，可以考虑扩展队列或分区，并增加消费者。

```text
原来：4 个队列
        |
        v
可分配的消费并行度受到限制
        |
        v
评估后扩展到更多队列
        |
        v
增加消费者实例
        |
        v
提高并行处理能力
```

注意：**增加队列数量，不会自动把原有队列里的历史积压消息重新分配到新队列。**

新增队列主要可以提高后续消息的分布能力。对于已经积压的旧消息，如果需要更快处理，可以在保证消息可靠性和业务顺序的前提下，考虑临时转发到新的 Topic 或队列。

### 2.8.5 第四步：海量积压时，临时转发到新 Topic

如果出现数百万条消息积压，普通扩容仍然无法及时恢复，可以考虑**临时重分发方案**。

基本思路：

```text
原 Topic
大量历史积压消息
        |
        v
临时转发消费者读取旧消息
        |
        v
临时新 Topic
配置更多队列，提高可并行处理能力
        |
        v
多个消费者并行处理
        |
        v
逐步清理历史积压
```

操作步骤：

1. 先修复导致消费缓慢的程序或基础设施问题。
2. 创建临时 Topic，并配置更多队列。
3. 编写临时转发程序，将旧 Topic 中的消息重新发送到临时 Topic。
4. 在新 Topic 发送成功并得到确认后，再确认旧消息，避免转发失败时丢失消息。
5. 根据业务要求部署更多消费者，提升处理速度。
6. 积压清理完成后，恢复正常消费架构，并检查数据一致性。

这个方案需要注意：

- 转发过程中可能出现重复消息，因此消费者必须具备幂等性。
- 不能随意打乱同一业务键的消息顺序。
- 新 Topic 和更多消费者会增加 Broker、网络、数据库等组件的压力。
- 不是所有业务都适合临时转发，必须先评估顺序性、幂等性和消息保留策略。

### 2.8.6 第五步：必要时评估跳过非关键消息

在某些情况下，如果积压的是允许丢弃的非关键数据，例如部分统计埋点，可以在经过业务确认后，考虑跳过历史积压消息或对其进行归档。

但对于订单、支付、库存等关键业务消息，**不能为了清理积压而直接跳过消费进度**，否则可能造成业务数据不一致。

是否允许跳过，必须由业务重要性和数据补偿能力决定，而不是单纯看积压数量。

### 2.8.7 第六步：计算积压恢复时间

消费者恢复后，除了处理历史积压消息，还需要处理生产者持续产生的新消息。因此，真正用于消化积压的速度，并不等于消费者的总消费速度。

假设：

- 当前积压：1,000,000 条消息
    
- 消费者每秒处理：5,000 条消息
    
- 生产者每秒产生：3,000 条消息
    

**计算积压的净消化速度**

每秒消费 5,000 条消息，但生产者同时产生 3,000 条新消息，因此积压每秒实际减少：

$$  
\text{净消化速度}=\text{消费速度}-\text{生产速度}  
$$

$$  
5000-3000=2000\text{ 条/秒}  
$$

**计算理论恢复时间**

$$  
\text{恢复时间}=\frac{\text{当前积压量}}{\text{净消化速度}}  
$$

$$  
\frac{1,000,000}{2,000}=500\text{ 秒}  
$$

即理论上需要 **8 分 20 秒** 才能清空当前积压。

**如何理解这个计算结果？**

消费者每秒虽然能处理 5,000 条消息，但生产者同时又产生了 3,000 条新消息。因此，积压不是每秒减少 5,000 条，而是每秒减少 2,000 条。

经过 500 秒，当前积压才会被全部消化。这里假设生产速度和消费速度始终稳定，并且没有其他处理瓶颈。

**不同情况下，积压会怎样变化？**

|消费速度与生产速度的关系|积压变化|
|---|---|
|消费速度大于生产速度|积压逐渐减少，最终可以清空|
|消费速度等于生产速度|积压量基本不变，无法自然清空|
|消费速度小于生产速度|积压继续增加|

因此，处理消息积压时，不能只关注消费者每秒能处理多少条消息，还要关注生产者持续产生多少条消息。

核心公式：

$$  
\text{净消化速度}=\text{消费速度}-\text{生产速度}  
$$

$$  
\text{理论恢复时间}=\frac{\text{当前积压量}}{\text{净消化速度}}  
$$

**计算的意义：**

1. **判断积压能否恢复：** 只有消费速度大于生产速度，积压才会逐渐减少。
    
2. **估算恢复所需时间：** 帮助判断消息延迟还会持续多久，以及是否满足业务要求。
    
3. **评估扩容效果：** 如果增加消费者后，消费速度提高到每秒 8,000 条，那么净消化速度就是每秒 5,000 条，理论恢复时间缩短为 200 秒，即 3 分 20 秒。
    

注意：理论恢复时间只是估算值。实际恢复速度还可能受到数据库性能、下游服务处理能力、消息重试等因素影响。

### 2.8.8 消息积压的完整处理流程

```text
发现消息积压
      |
      v
排查原因：生产突增、消费者异常、处理过慢？
      |
      v
修复故障，优化消费逻辑
      |
      v
是否仍然积压？
   /       \
  否        是
  |          |
恢复监控   扩容消费者
             |
             v
       队列或分区是否足够？
             |
             v
       必要时扩展并行度
             |
             v
       海量积压时评估临时转发
             |
             v
       检查数据、顺序与幂等性
             |
             v
       持续监控直到恢复正常
```
